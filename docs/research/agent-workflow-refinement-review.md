# 0.1.44 이후 고도화 검토와 보완 결론

2026-10-09. [현재 설계](agent-coding-system-direction.md), [완료 기준](agent-workflow-completion-design.md), 고정 [pstack 조사](pstack-analysis.md), local main `95c4f9e`와 패키지 `0.1.44`, 기존 실행 기록 및 수정 없는 연두라벨 UI 시험을 대조했다. 현재 문서는 설계·실행 인계이며 다음 개선을 구현하거나 그 효과를 검증한 결과가 아니다.

다음 실제 구현은 [R0–R4](agent-workflow-completion-design.md#review-driven-refinement)와 [현재 실행 프롬프트](agent-workflow-next-session.md)를 따른다. G1–G6의 과거 실행 상태는 [구현 결과](agent-workflow-implementation-results.md)가 소유한다. 이미 수리한 0.1.43 review/findings 승계 문제를 현재 결함으로 다시 올리지 않는다.

## 판단과 현재 근거

핵심 방향은 옳다. Agent의 요구·원인·시각·검사 가치 판단, CLI의 상태·실행·근거 유효성 처리, 프로젝트의 정답·runner·UI 소유권을 유지한다. task/context, 요청 연결, 6셀 scope, prepare/execute/lookup/resume, feedback/prevention, ui_systems, maintain/check_retirements는 이미 구현돼 있다. 기능 존재와 일반적인 위임 신뢰성 입증은 구분한다.

| 근거 | 관찰과 한계 |
| --- | --- |
| 기존 범용 과업 | 실제 API/Chromium/SQLite/재시작 조회, 피드백 수리·공유 UI 재사용, 읽기 전용 조회·완료 실행 재개 기록이 있다. 감독·개입을 포함한 범위 한정 사용이다 |
| 수정 없는 UI 시험 | 29개 화면 그룹·172개 복합 상태 항목을 분모로 유지했다. 29개 그룹은 모두 부분 확인이며 전체 조사 완료가 아니다. 후보 3건과 정상/의도된 비교 9건은 사용자 검수 전이다 |
| 미설정 연결 | 0.1.44 `start --intent ui`는 `workflow_not_configured`로 task context 생성 전에 차단됐다. 조사 목록·근거·재개·검수 HTML은 Agent가 별도 보완했다. 구성된 workflow의 고장을 재현한 결과는 아니다 |
| host/도구 | `codex.exe plugin list`는 CODEX_HOME 접근 거부(os error 5). Impeccable engine은 바이너리 부재와 bootstrap 연결 실패로 실행되지 않았다. 환경 제약이며 플러그인 설치 부재나 엔진 품질 결함으로 단정하지 않는다 |
| 기록 소유권 | [테스트 정책](../testing.md)은 같은 task 기록의 단일 writer만 검증했다. atomic replace는 부분 JSON 노출 방지이며 동시 읽기-수정-쓰기 보장이 아니다. 동시 lost update는 코드상 위험 검토이고 실행 재현은 하지 않았다 |
| 자동 근거 결합 | [repair 계약](../../authoring/references/repair-and-reuse.md)의 상세 feedback/retirement 결합은 prepared native-JSON을 요구한다. 다른 runner는 필요한 프로젝트별 binding을 연결해야 하며 새 범용 parser가 답은 아니다 |
| 검사 폐기 | active Feature 내 check 제거는 이전 prevention과 대체 검출 보존을 요구한다. Feature 전체 폐기는 reconciliation이 있다. 살아 있는 Feature 내 요구 일부 폐기의 불필요한 차단 여부는 실행 재현 전 후보다 |

UI 시험은 실제 React 화면과 합성 API를 사용했다. 앞선 실제 Worker/D1 시험과 혼동하지 않는다. 잘못된 합성 응답·selector/튜토리얼 조작·캡처/정리 오류는 시험 도구 또는 Agent 판단으로 분리했다. 상태별 근거 과포함을 독립 검토에서 발견해 직접 관찰 하위 상태를 연결하고 3항목을 미확인으로 낮췄다. 링크가 있다는 사실만으로 근거의 충분성이 보장되지 않는다.

원시 자료는 원본 저장소의 `.work/ui-consistency-trial-20261009`, `.work/plugin-maturity-review-20261009`, `.work/generic-completion-delivery-20261009`에 있다. HTML과 screenshot은 작업 기록이며 필수 durable 설계의 유일한 저장소로 삼지 않는다. 사용자 UI 검수 결과는 아직 없고 후보를 확정 결함이나 제품 수정 승인으로 승격하지 않는다.

## 앞선 W1–W7 제안의 보정

| 제안 | 보정 |
| --- | --- |
| W1 호스트·도구 doctor | 선택한 능력의 preflight/오류 안내를 기존 경로에 통합. 권한 오류 한 건으로 범용 진단 플랫폼을 먼저 만들지 않음. 최신 native 진입 인수는 별도로 유지 |
| W2 조사·범위·재개 | 구체적인 공백이므로 유지. 요청 범위의 최소 진단 기록과 기존 context 연결로 제한하고 전체 설정·별도 장부를 강제하지 않음 |
| W3 계획·결과 보기 | 기존 viewer 결과의 정확성과 실제 관찰 범위를 먼저 확인. HTML은 얇은 파생 표현이며 새 결과 상태 엔진이 아님 |
| W4 UI 검수 | 후보 ID·근거·의견·결정을 기존 feedback/ui_systems에 연결. 새 후보 DB·자동 제품 수리 흐름은 불필요 |
| W5 원인·가드레일 | 새 기능으로 재구현하지 말고 분류·원인·후속 선택의 실제 인수 공백을 수리 |
| W6 검사 가치 | 기존 maintain 유지. 정리 사유별 필요한 근거를 구분하고 재현된 차단/누락만 보완 |
| W7 자연어/CI | CI의 결정적 영향 회귀와 별도 자연어·host 인수를 구분. 모든 작은 작업에 Full/브라우저/Agent 평가를 강제하지 않음 |

수동 Domain 검사라는 사실만으로 selector 결함이 되지 않는다. 선언한 요구·영향상 필요한 검사가 선택되지 않는지 먼저 확인한다. BE/API를 무조건 별도 셀로 늘리지 않고 기존 셀 안의 API 계약·서비스/저장 책임을 구분한다.

## 의미·근거·범위의 보완

- 사용자 요구·업무 규칙이 정답 출처다. 코드/테스트가 동일한 잘못된 기대값을 공유할 수 있다. 요구 충돌은 표시하고 제품 결정이 필요한 부분만 확인하며 모든 작업에 새 승인 단계를 만들지 않는다.
- 6셀은 관점별 판단이다. 중요한 사용자 흐름은 실제 입력→API→Domain→저장→fresh read의 ID/값을 연결한다. mock UI·실제 API/DB·정적 구조 검토를 구분한다. API-only에는 이유 있는 FE 비적용을 허용한다.
- 사업 성과 가설과 소프트웨어 업무 규칙을 구분한다. 단위 테스트가 실제 사용자 가치·수익 개선을 증명하지 않는다.
- 전체 조사 요청은 전체 진입점 분모와 미확인을 유지한다. 작은 요청은 영향 기반으로 수행하며 전체 setup을 시작 조건으로 만들지 않는다. 화면×역할×viewport×상태의 무조건적인 조합 생성도 하지 않는다.
- 검사 실행, 의미 검토, 요청 범위 충족, 현재 재사용, host 수락 수준을 하나의 PASS로 압축하지 않는다. 실제 비용 없는 점수·신뢰도 백분율도 만들지 않는다.
- 같은 task의 단일 writer 정책을 지키고, 여러 태스크는 기록을 분리한다. 동시 동일 기록 쓰기를 새로 지원하려면 별도의 충돌 검출·보존 인수가 필요하다.

## 피드백·UI·가이드의 개선 순환

| 종류 | 처리와 완료 기준 |
| --- | --- |
| 기존 요구 위반 | 기대값을 고정하고 caller/state/data 흐름의 원인 owner 수리. 같은 실패 RED/GREEN, 정상 반례, 활성 예방과 후속 소비 |
| 요구 변경/새 선호 | 요청 권한·근거와 기준 revision을 갱신. 새 기대와 유지해야 할 계약 검증. 이전 동작을 소급해 버그라고 부르지 않음 |
| 의도된 차이 | 정상적인 공통 variant 또는 범위·사유·근거·재검토 조건이 있는 예외. 불필요한 수리·검사 추가 없음 |
| 기준/도구 오류 | 독립 근거로 확인하고 기준·runner·adapter를 수리하여 실제 재확인. 제품 위반을 guide/expectation 완화로 숨기지 않음 |
| 환경/원인 미확인 | 실제 실패·진입/재개 조건을 보존. 근거 없는 해결 처리 금지 |

가드레일은 원인에 맞는 validation/type/schema/transaction/DB constraint/단일 상태 owner/shared component·token/회귀 검사에 둔다. 같은 지침 추가나 등록만으로 완료하지 않는다. 다음 관련 요청에서 실제 소비되는지 확인하며, 무관한 요청을 막는 예방책은 적용 범위를 줄인다. 알려진 실패와 미검증 조건을 명시하며 무조건적인 재발 불가를 보장하지 않는다.

UI guide는 의도·용어·variant·상태·반응형·접근성·예외와 코드 참조를 소유하고 값·동작은 코드가 소유한다. 가이드 생성 시 현재 구현을 무조건 정답으로 추출하지 않는다. 반복되는 정상 차이를 화면별 예외로 늘리지 않는다. 사용자 검수 의견은 원 후보·근거에 연결하며 동의는 자동 수정 권한이나 원인 확정이 아니다. 승인된 개선은 공유 owner·소비 화면·가이드를 함께 갱신하고 fresh-context 후속 사용을 확인한다.

검증 guide는 실제 명령·기준·fixture·Launch/Doctor/Drive/Evidence/Cleanup을 연결한다. 기능/runner/환경 변화에 영향 부분을 갱신한다. 같은 자료를 다시 조사·기록하거나 전체 문서를 매번 다시 쓰지 않는다. 검증 전에 기준·지도 변경을 정리해 불필요한 동일 행동 재측정부터 줄인다. 전체 Git 무효화는 의존 범위 증명 없이 좁히지 않는다.

## 정리 사유에 맞는 증명

| 사유 | 필요한 근거 |
| --- | --- |
| 중복 통합 | 남는 검사/구조가 해당 보호 책임·알려진 실패·경계·정상 사례를 보존 |
| 요구/기능 폐기 | 유효한 요구 변경 근거, 사라진 진입점·호출자, 남은 요구/소비자 영향 확인, active 연결 정리와 이력 보존. 폐기한 요구의 대체 검사 강제 금지 |
| 구조적 예방으로 이동 | 새 타입/제약/경계가 해당 잘못된 상태를 거부하고 정상 사용을 허용한다는 실제 근거. 우회·호출 경로 검토 |
| flaky/낡은 runner | 제품/도구 실패 분리와 runner 수리. 임시 제외·skip은 검증 공백이며 PASS가 아님 |
| 비용 대비 가치 불명확 | 보호 범위·독자 검출·정상 반례와 실측 비용 검토. 오래 실패하지 않았다는 이유만으로 제거하지 않음 |

## 인수 사례와 판단 기준

| ID | 검출할 실패 | 정상 반례 |
| --- | --- | --- |
| E1 | 낡은 코드/테스트의 기대값을 요구보다 우선 | 명시적 요구 변경은 새 기준으로 처리 |
| E2 | BE/Domain PASS가 FE 전달 오류를 숨김 | FE 없는 프로젝트의 비적용 |
| E3 | 미설정 조사 중단 후 범위·미확인 소실 | 조회 원본/근거 불변, 검사 0회 |
| E4 | 의도된 UI variant를 결함으로 수리 | 같은 의미·상태의 실제 차이는 검수 후보 |
| E5 | 공유 owner 수리 후 다음 요청에서 예방 누락 | 무관한 변경에 불필요한 고비용 검사 없음 |
| E6 | 독자 검사를 중복으로 삭제 | 입증된 중복·폐기된 요구의 정당한 정리 |
| E7 | stale/raw 누락/skip을 현재 PASS로 표시 | 유효 결과의 읽기 전용 재사용 |
| E8 | 직접 패키지 사용을 native 자동 호출로 보고 | 실제 host 진입/context 전달 별도 인정 |

기존과 후보에 같은 요구·source·fixture·host/모델 조건을 적용하고 평가 Agent에게 CLI 순서·정답 패치를 주지 않는다. 거짓 완료·결함 누락·정상 과업 오탐·개입·재작업·중복 실행·시간을 함께 기록한다. 측정하지 않은 비용과 사용자 검수 전 UI 오탐률은 산정하지 않는다. 작은 표본의 성공을 일반적 성능으로 확대하지 않는다. pstack은 고정 소스의 원칙 참고이며 동일 조건 비교 실행 없이 우열을 주장하지 않는다.

이번 검토는 문서·코드·과거 실행 기록을 읽었으며 제품/플러그인 시험을 재실행하지 않았다. 현재 단계의 Feature 영향은 문서·인계(`documentation`)이며 런타임·배포 패키지의 동작 변경은 없다.
