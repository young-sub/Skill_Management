R0의 기준을 먼저 고정하고 R1–R3를 필요한 기능 단위로 구현하며 R4로 수용한다. 기존 충족 항목은 근거로 유지하고 신규 엔진으로 다시 만들지 않는다. W1–W7은 일곱 신규 시스템 목록으로 채택하지 않는다. 별도 범용 doctor·원인 엔진·pruning 체계·추가 셀·두 번째 token/task 저장소는 만들지 않는다. HTML은 필요한 검수 표현이며 근거 충분성의 대체물이 아니다.

전체 조사 요청은 전체 진입점/미확인을 유지하고, 작은 요청은 영향 범위만 조사한다. UI의 가능한 모든 조합을 기계적으로 생성하거나 대표 관찰을 전체 완료로 올리지 않는다. 기존 범위 밖 요구를 만들기 위해 모든 작업에 승인·Full·Agent 평가를 강제하지 않는다.

기존 [단일 writer 지원 범위](../testing.md)는 유지한다. 같은 task를 여러 Agent가 동시에 갱신하는 기능은 이번에 신설하지 않는다. 설계 검토 당시 요구 일부 폐기의 차단은 후보였고, 후속 focused 재현과 사유 분기 수정은 구현 결과에 기록했다. 동시 갱신은 여전히 미지원이며 재현된 제품 결함으로 쓰지 않는다. 전체 Git 무효화는 의존 범위 증명 없이 완화하지 않는다.

연두라벨 UI 후보는 사용자 검수 전이며 원본 제품 수리는 이번 범위가 아니다. 기존 캡처는 결과 조회·검수 입력으로 재사용할 수 있으나 새 버전의 최초 조사·효과를 입증한 근거로 바꾸지 않는다. 필요한 실제 제품 인수는 범용 구현·독립 검증·패키지 고정 뒤 격리 소스/합성 데이터로 수행한다. 상세 로그·HTML·스크린샷은 작업 기록으로 보존하고 지속되는 기준은 현재 docs·코드·활성 검사에 남긴다.

## 0. 2026-10-09 합의: 범용 기능 완성 후 실제 제품 인수

이 절은 G1–G6 실행에 사용한 범용 우선 순서와 시험 대상 역할을 보존한다. 현재 후속 구현은 위 R0–R4이며, 뒤의 U1–U7 기능·책임 기준은 유지한다. 과거 Labeler 파일럿이나 임시 설치 순서를 다음 구현의 선행 작업으로 가져오지 않는다. 문서 갱신은 기능 구현이나 제품 인수 완료가 아니다.

### 목적과 책임

사용자는 Skill 이름이나 CLI 순서를 조립하지 않고 구현·검증·조회·피드백 수리·UI 기준 개선·검증 유지보수를 맡길 수 있어야 한다. 무엇을 확인했고 무엇이 남았는지 같은 작업에서 확인하고 다음 관련 업무에 유효한 근거와 예방책을 재사용한다.

| 소유자 | 책임 |
| --- | --- |
| Agent | 요구 의미, 기능 발견, 영향 범위, 원인, 설계, 의미·시각적 충분성, 검사 가치 판단과 실제 수정 |
| 공통 코드/CLI | 명시적 작업 연결·상태·누락, 결정된 검사 선택, 실행·수집·유효성·재사용·읽기 전용 조회 |
| 프로젝트 | 업무 정답, 실제 명령·runner, 데이터·환경·자원 수명주기, UI 기준·공유 구현, 필요한 최소 adapter |
| 플러그인 | 위 능력의 발견·조합·반복 사용과 버전이 고정된 패키징 |

범용 최초 연결도 구현 범위다. 처음 보는 프로젝트의 기존 문서·코드·검사에서 기능과 실행 방법을 조사하고, 부족한 지도·가이드·연결을 작성한 뒤 실제 실행으로 확인한다. 필요한 최소 adapter는 프로젝트에 두고 공통 capture/선택/수집을 재구현하지 않는다. 작은 작업에 Harness 계약이나 설치를 강제하지 않는다. 지원 범위는 실제 실행·관찰 능력으로 명시하며 FE가 없는 프로젝트의 이유 있는 제외를 허용한다.

### 실행 전 출발점과 확인된 공백

다음 항목은 2026-10-09 실행 전 기준이다. 후속 검토·미해결 문제 승계, 요청 연결, hook 길이 및 inventory root 결함은 0.1.43에서 수리·검증했다. 재사용의 전체 Git 무효화는 완전한 의존 범위 증명이 없어 유지한다. [현재 구현 결과](agent-workflow-implementation-results.md)가 실행 상태를 소유한다.

당시 확인한 구현 기준은 `wp-20261007-connected-workflows`, `23e5d152038abf30765a019729c02bc05f640b5d`, 소스 버전 `0.1.42`다. 원본 checkout은 `172dfa3`였으므로 경로 이름만으로 최신 여부를 판단하지 않는다. 다음 세션에서는 main·작업 브랜치·설치본의 현재 상태를 각각 다시 확인한다.

- 이미 구현된 작업 context, prepare/execute/bundle/lookup, scope matrix, 실제 브라우저 시험 runner, 피드백·UI·검사 유지보수 연결을 재사용한다. 범위별 실제 근거는 [구현 결과](agent-workflow-implementation-results.md#connected-actual-product-use-2026-10-07)를 따른다.
- `project_workflow.begin()`의 일반 후속 작업은 `reviews`를 비운다. 두 Feature의 유효 검토를 만든 읽기 전용 메모리 재현에서 하나만 대상으로 새 작업을 시작해도 무관한 Feature의 `map_review`가 다시 생겼다. Harness `begin_work()`에는 유효 검토를 승계하는 별도 경로가 있다.
- 같은 재현에서 이전 `reviews.<Feature>.product_findings`의 미해결 항목이 후속 작업 조회에서 빠졌다. 이전 기록은 남아 있으나 현재 작업에서 누락되는 결함이다. 제품 결함 자체를 새로 발견한 시험은 아니다.
- 검토는 기준 유효성 확인 후 재사용하고 새 요청의 적용·범위 판단만 다시 한다. 미해결 문제는 검토의 유효성 만료와 별개로 명시적 해결·처리까지 이어져야 한다. 단순히 모든 `scope_reviews`를 복사해 현재 판단으로 삼지 않는다.
- 작업 후보는 ID/intent/target 중심이다. 일반 작업의 요청 요약·기대 결과 참조를 같은 상태에 연결하고, Harness 계약이 있으면 참조해 중복 요구 장부를 만들지 않는다.
- `verification_results._git_snapshot()` / `_execution_conditions()`는 전체 HEAD/diff/untracked 상태를 결과 조건으로 사용한다. 의존 범위를 입증한 검사에 한해 재사용을 좁히고, 미확인·공통 의존성은 보수적 무효화를 유지한다. 일반적인 시간 절감 효과는 아직 측정하지 않았다.

G1–G4를 먼저 완료한다. 서로 결합된 수정은 같은 기능 단위로 검증·커밋하되 G5를 앞당겨 연두라벨 전용 준비를 구현 수단으로 삼지 않는다. 공통 기능이 미완료이면 그 부분을 완료하고 제품 인수는 대기한다. 지원 불가능한 호스트의 보호 수락은 별도 BLOCKED/미검증으로 남기고 일반 기능 개발을 막지 않는다. 이 단계는 새 workflow 엔진이나 별도 상태 장부를 요구하지 않는다.

### 연두라벨 이전의 검증

기존 독립 시험 프로젝트부터 재사용한다. 실제 FE → API → Domain → 저장 → fresh read 경로와 FE 없는 CLI/API 경로, UI 기준 유무, 비-Harness 사용을 확인할 수 있는 최소 차이를 둔다. JSON에 PASS를 적는 fixture는 사용자 기능 근거가 아니다. 비즈니스/아키텍처 × FE/BE/API/Domain의 적용·미판단·미연결·제외·실패·차단·STALE와 의미 검토를 구분한다.

G3는 여섯 사용자 업무를 각각 수정·검증·후속 소비까지 확인한다. 피드백은 동일 실패와 가까운 정상 사례, UI는 공유 기준의 영향 화면과 다음 화면의 재사용, 검증 유지보수는 실제 낡은 연결의 수리, 검사 정리는 통합 전후 검출 보존과 근거 부족 시 유지를 포함한다. 필요한 검사만 실행하고 첫 전체 지도 조사와 매 요청의 영향 갱신을 구분한다.

직접 CLI 시험과 Agent가 요청에서 절차를 발견·선택한 시험을 따로 기록한다. 사용 가능한 호스트에서 패키지 위치·업무 요청·허용 범위를 주되 Skill 이름·CLI 순서·정답 패치를 알려주지 않는다. 임시 호스트 사용이 불가능하면 그 범위만 미검증으로 표시한다. 기존 설치 갱신, 전역 설정 변경, 관리자 sandbox 구축이나 광범위한 native Agent 평가는 선행 조건이 아니다.

### 연두라벨 인수와 자가 개선

연두라벨은 사용자가 제공한 실제 제품 시험 대상이다. G4 이전에 제품 전용 테스트 경로·기능 지도·Skill을 미리 작성해 범용 기능을 보충하지 않는다. G5에서는 고정한 코드 기준을 새 격리 공간과 새 시험 데이터로 실행하고 기존 제품 문서·코드·검사를 정상 입력으로 읽는다. 과거 파일럿의 맞춤 지도·adapter·정답 패치·DB·인증 정보를 가져와 최초 연결 성공으로 보고하지 않는다. 제품 자체에 원래 있는 자원은 재사용한다.

최초 연결 과정에서 생성되는 프로젝트별 설정·가이드·최소 adapter는 완성된 setup 기능의 산출물이다. 사람이 사전에 만들어 줘야 진행되면 최초 연결 미완료로 기록한다. 명령·순서를 추가로 알려준 개입, 실패한 연결, 잘못된 완료, 누락한 문제와 중복 실행을 숨기지 않는다. 화면을 합성 API로 확인한 증거와 실제 API/저장 관찰도 구분한다. 전체 지도는 합의한 제품 범위에서 조사하되 실제 실행·수리는 대표 업무와 그 영향으로 제한한다.

자가 개선의 처리 위치는 제품 결함 → 프로젝트 소유 코드·예방책, 연결 결함 → 프로젝트 명령·가이드·adapter, 공통 결함 → 플러그인 canonical 코드·기존 절차다. 같은 실패·정상 반례로 확인하고 다음 업무에서 소비한다. 장기 예방책은 코드·공유 구현·등록 검사·현재 가이드에 남기며 임시 `.work` 기록에만 의존하지 않는다. 공통 결함은 원래 제품 사례와 다른 프로젝트의 정상 사례로 재검증하고, 새 버전의 결과를 이전 고정 패키지의 무개입 성공으로 바꾸지 않는다.

설치 가능한 패키지와 업무를 안정적으로 위임할 수 있는 플러그인은 별도로 판정한다. 제한된 성공을 모든 프로젝트·장기 효과로 일반화하지 않는다. pstack 비교 기준은 `0.15.6 / 23e4138daa01c42d4969f7a5465f82704e64f798`이며 같은 과제의 실제 비교 실험 없이 우열을 주장하지 않는다.

## 1. 최상위 원칙과 결론

후속 구현은 `864ee4f`에서 시작하여 공통 런타임·검증·설치 보존을 `b1b710c`, 중단된 상태 저장의 재개 수리를 `b3d01d9`로 로컬 커밋했다. 아래 수용 기준은 유지하며, 실제 구현·설치·행동 검증과 남은 PARTIAL/BLOCKED 범위는 [구현 결과](agent-workflow-implementation-results.md)의 U1–U7 기록에 구분한다. 설계 당시의 미구현 설명은 당시 상태 기록이며 전체 인수 완료를 뜻하지 않는다.

목적은 **Agent에게 업무를 맡겼을 때 요구를 더 정확하게 달성하고, 사용자의 개입·재작업·불필요한 실행을 줄이는 것**이다. 규칙 수, 검사 수, Skill 수, 차단 횟수는 성과가 아니다. 환경 제약도 이 목적을 위한 수단이며 정상 업무를 불필요하게 막는 제약은 수정하거나 범위를 줄인다. 기존 권한·사용자 데이터 보호는 성과 비교를 이유로 완화하지 않는다.

결론은 다음과 같다.

1. 최초 Feature Map은 프로젝트의 모든 기능을 대상으로 완성한다. 큰 프로젝트는 최초 setup 안에서 분할·재개하며 전체 통합 전에는 setup 완료로 표시하지 않는다.
2. 모든 고도화는 영향 Feature의 지도·기준·검증 연결을 함께 갱신한다. 무조건 재조사·전체 테스트·무의미한 문구 변경을 요구하는 뜻은 아니다.
3. 요청 분류·작업 조정·구현·검토·검증·조회·피드백·UI·유지보수·설치/배포·재개 전반에서 책임과 처리 방식을 나눈다. 의무를 발생·추적·집행하는 것은 환경이고 Agent는 필요한 의미 판단과 실제 작성·수리를 맡는다. 기계적으로 정해진 작업은 코드가 직접 처리하고 Agent를 호출하지 않는다. 우회 불가가 필요한 효과는 Agent가 통제하지 못하는 실행·수락 경계가 맡는다.
4. 실수와 피드백은 원인 소유 위치의 수정과 적용 가능한 예방책으로 전환한다. 같은 지침을 추가하거나 모든 사건을 전역 금지 규칙으로 만드는 것으로 끝내지 않는다.
5. 각 개선은 결함 검출·정상 허용·사용자 개입·중복 실행·비용을 함께 평가한다. 지원 범위에서 온전한 사용자 업무를 제공하는 단위로 구현한다.

연두라벨은 §0의 G1–G4 완료 후 사용하는 실제 제품 인수 대상이다. 제품의 기능 확장·전체 품질 개선·운영 적용은 후속 구현의 목표가 아니다. 전체 지도 작성 능력을 시험할 때에는 합의한 시험 범위의 전체 기능을 조사하지만 모든 기능을 고도화하지 않는다.

## 3. 전체 Feature Map 초기화

### 3.1 전체 기능의 범위

제품/저장소 경계와 기준 revision을 먼저 정하고, 그 경계 안의 모든 사용자·운영 기능을 대상으로 한다. 요구 문서·사용자 결정, 화면/route/navigation, API/CLI, background job/event, 권한/역할, feature flag/설정, 외부 연동, 데이터 변경·가져오기/내보내기, 기존 테스트를 교차 조사한다. UI가 없는 기능과 관리자 기능도 포함한다.

파일 하나를 기능 하나로 세지 않는다. 사용자 결과를 기준으로 안정적인 Feature ID를 부여하고 역할·상태·플랫폼 차이는 필요한 변형으로 연결한다. 공통 모듈은 관련 Feature의 의존 관계로 둔다. 폐기된 기능과 아직 구현되지 않은 요구는 활성 기능과 구분한다. 조사 중 발견한 항목은 Feature, 변형, 공유 기반, 폐기/범위 밖 중 어디에 속하는지 근거를 남겨 누락이 조용히 사라지지 않게 한다.

`전체`는 **정한 제품 경계와 현재 조사 가능한 기준에서 빠짐없이 대조한 전체**를 뜻한다. 코드 검색 하나나 Agent의 선언으로 절대적인 완전성을 증명하지 않는다. 접근할 수 없는 영역·미해결 기능 후보·중요한 요구 충돌이 있으면 그 공백을 남기고 초기화는 PARTIAL/BLOCKED로 둔다. 어려운 영역을 임의로 범위 밖으로 돌려 완료하지 않는다.

### 3.2 모든 Feature에 필요한 최소 의미

| 항목 | 필요한 내용 |
| --- | --- |
| 정체성과 범위 | 안정 ID, 사용자/역할, 진입점·계기, 포함하는 하위 흐름·변형 |
| 요구와 동작 | 요구 출처/revision, 기대 결과, business invariant, 중요한 정상·경계·실패 조건 |
| 책임과 연결 | FE·BE/API·Domain 책임, 실제 호출·상태·데이터 흐름, 저장·외부 효과, 관련 기능/공통 구현 |
| 구조상 보장 | 상태·검증·transaction·외부 접근의 소유 경계, 이미 존재하는 type/validation/constraint/공통 component 등 |
| 검증 | 확인할 주장, 기존 native/flow/manual 방법과 명령 참조, 검사 없는 부분과 추가 연결할 범위, UI 기준/상태 참조 |
| 현재 연결 상태 | 조사 완료 여부, 실행 연결 여부, 마지막 검증 근거 참조와 현재 유효성, 발견된 공백 |

비즈니스와 아키텍처는 관점이고 FE/BE/Domain은 구현 책임이다. 열을 채우거나 층별 PASS를 모으는 것으로 전체 흐름을 판정하지 않는다. 해당 없는 영역은 이유를 갖는다. 명령·token 값·raw·상세 요구를 지도에 다시 복제하지 않고 소유 위치를 참조한다.

**지도 완성과 모든 테스트의 실행 완료는 서로 다른 상태다.** 최초 setup 완료에는 전체 Feature의 위 정보와 누락 검사 현황이 필요하다. 아직 자동 검사가 없는 기능도 지도에는 포함하며 `미연결`로 표시한다. 모든 기능의 자동화/외부 실환경 PASS를 초기 지도 작성의 전제 조건으로 만들지는 않는다. 첫 실제 흐름은 실행 연결의 작동 확인이며 전체 지도 작성을 대체하지 않는다.

### 3.3 큰 프로젝트의 분할과 완료

1. 전체 조사 대상·기준 revision·기능 후보·영역 의존 관계를 먼저 작성한다. 일부 영역만 조사한 목록을 전체라고 부르지 않는다.
2. 사용자 흐름/업무 영역 단위로 나눈다. FE/BE만 따로 나눠 연결 책임을 잃지 않게 한다. 예: 계정, 상품, 주문 각각에 UI/API/저장 흐름이 포함된다.
3. 각 묶음은 같은 최소 항목과 안정 ID를 사용한다. 기존 작업 기록에 조사 범위·진행·공백·다음 경계만 남겨 context가 바뀌어도 이어간다. 별도 관리 엔진은 만들지 않는다.
4. 묶음 완료 시 후보 대비 누락·중복·죽은 참조를 확인한다. 공통 자산/문서는 한 소유자가 통합한다. 병렬 Agent는 분리 가능한 조사에 도움이 될 때만 쓴다.
5. 전체 묶음 후 영역 간 흐름, 공유 상태, 권한, 데이터 효과를 다시 연결한다. 변경된 source가 있으면 무효화된 조사 묶음만 갱신하고 최종 기준 revision을 맞춘다.
6. 미분류 후보·미조사 영역·끊긴 필수 참조·중복 정체성이 해소되고 의미 검토까지 끝나야 전체 init 완료다. 일부 묶음은 먼저 사용 가능하지만 전체 상태는 완료 전까지 PARTIAL이다.

자동 도구는 ID/참조/명령 존재/분할 진행/관측된 진입점 대조 같은 닫힌 사실을 확인한다. 어떤 항목이 진짜 기능인지, 요구가 충분한지, 숨은 흐름이 있는지는 Agent의 교차 조사와 검토가 필요하다. 관측한 목록의 100%를 제품의 절대적 완전성으로 표시하지 않는다.

### 3.4 모든 고도화에서 필수 갱신

기능 추가·수정·삭제, 버그 수리, 공통 UI·아키텍처·검증 방법 개선은 같은 기능 단위에서 영향 Feature와 그 기준/검증 연결을 반드시 갱신한다. 공통 모듈 변경은 소비 Feature까지 확인한다. 삭제는 활성 연결을 제거하고 과거 정체성과 결과를 보존한다.

요구·의미가 그대로인 리팩터링도 해당 Feature의 구현/검증 참조와 검토 기준 revision을 갱신한다. 의미가 없는 문구나 timestamp 변경으로 의무를 충족하지 않는다. 기존 Git/diff·실행 기록을 재사용하고 한 canonical 정보를 갱신해 파생 표현을 만든다. 구현자가 자유 문구로 `영향 없음`을 제출하는 것만으로 기능 고도화의 갱신을 면제하지 않는다.

제품 동작을 바꾸지 않는 오탈자·작업 기록 정리는 실제 영향 근거에 따라 지도 내용 불변을 허용한다. 이는 모든 기능 고도화의 갱신 의무를 없애는 예외가 아니다. 직접 CLI 경로에서도 같은 결정적 무결성 검사를 사용할 수 있어야 한다.

이 의무는 Agent가 지시문에서 기억하거나 스스로 체크리스트에 추가하는 것에 의존하지 않는다. 환경이 작업 범위·실제 diff·기존 지도/정책에서 갱신 의무를 만들고 미해결 상태를 유지한다. Agent는 전달받은 영향 Feature의 의미와 변경 내용을 조사하여 지도를 갱신한다. 이후 환경이 새 상태를 확인하고 의무를 해소한다. 의미 판단 없는 단순 갱신·생성은 코드가 수행할 수 있지만 요구/업무 의미를 코드가 추정해 완성했다고 표시하지 않는다.

## 4. Agent 판단과 환경 집행의 경계

### 4.0 전체 체계에 적용할 두 가지 분류 기준

**책임/권한의 위치와 실행의 결정성은 서로 다른 축이다.** 환경=모든 결정론, Agent=모든 비결정론으로 단순 치환하지 않는다. Skill 전체를 한쪽으로 분류하지 않고 그 안의 요청 해석·선택·실행·관찰·판정·수락·상태 보존을 각각 나눈다.

| 분류 축 | 구분 | 배치 기준 |
| --- | --- | --- |
| 책임·권한 | 환경의 의무/상태/정책 집행, Agent의 의미 판단/작성/수리 | 누가 기억하고 누락을 막으며 상태·권한을 소유하는가, 누가 실제 업무 내용을 판단·변경하는가 |
| 처리 방식 | 정형 규칙의 결정적 처리, 해석·설계의 의미 판단, 관찰 대상 자체의 변동성 | 이미 정한 입력·규칙으로 코드가 처리할 수 있는가, 새로운 맥락 판단이 필요한가, 외부 상태가 변하는 것인가 |

공통 결정 순서는 다음과 같다.

1. **자동으로 잊지 않아야 하는 의무와 효과 경계인가?** 발생 조건·진행·완료/거절·재개·권한은 환경이 소유한다. 의무의 발생 조건이 의미 해석을 필요로 하면 Agent에게 그 해석만 요청하고 미해결 상태와 최종 집행은 환경에 남긴다.
2. **입력·규칙·출력이 정해졌는가?** 기존 코드/CLI/script로 직접 처리한다. 해시·diff·schema·명령 실행·정형 판정·집계·생성에 LLM 판단을 중복 삽입하지 않는다. 임의 자연어 업무 의미를 정형 규칙인 것처럼 가정하지 않는다.
3. **요구 이해·설계·영향·원인·시각 품질 등 맥락 판단이 필요한가?** Agent가 담당한다. 필요한 근거와 적용 조건만 받고 구체적인 내용이나 변경을 만든다. Agent의 결론은 정형 검증을 거친 사실 및 필요한 독립 관찰과 구분한다.
4. **결과만 비결정적인 외부 실행인가?** 브라우저 timing·네트워크·외부 API 결과가 변한다는 이유로 수집·재시도·상태 판정까지 LLM에 맡기지 않는다. 환경은 정해진 timeout/재시도/식별·기록을 수행하고 의미가 불명확한 실패만 Agent에게 넘긴다. 실행 성공을 보장한다고 주장하지 않는다.
5. **여러 성격이 섞였는가?** 기계 처리→필요한 의미 작업→기계 검증/수락으로 나누고 동일 사실을 다시 조사·기록하지 않는다. 실제 작업의 일부가 생성·복사 같은 정형 작업이면 그 부분도 도구가 직접 수행한다.
6. **누가 정책을 바꾸거나 예외를 허용할 수 있는가?** 기존 권한 경계를 적용한다. Agent는 수정안/근거를 제안할 수 있으나 수락 정책을 자기 편의로 해제할 수 없다. 기존 승인 범위의 정상 수정마다 새 승인 단계를 만들지 않는다.
7. **분리의 실익이 있는가?** 오탐·누락·context·개입·실행 비용을 비교한다. 일회성 단순 작업 때문에 거대한 자동화 체계를 만들거나 의미 없는 gate를 늘리지 않는다.

이 기준은 전체 기능 목록과 각 구현 단위의 입력/출력·호출자·상태·정책·실행 경로를 검토할 때 적용한다. 기존 docs/소유권 표에 `환경 의무·계기 / Agent 판단·행위 / 직접 코드 경로 / 불확실성·실패 처리 / 권한·수락 / 검증 근거`를 연결하고 별도 중복 registry나 새로운 범용 오케스트레이터부터 만들지 않는다.

### 4.1 의무·작업·실행의 책임 분리

환경과 코드는 별도 제품 두 개가 아니라 책임 구분이다. 환경은 정책·작업 상태·완료/효과 경계를 소유하고 그 정형 처리를 CLI/script로 구현한다. Agent는 그 환경이 요청한 의미 작업을 수행한다. 모든 실행에 LLM을 가운데 둘 필요는 없다.

| 사안 | 환경이 소유하는 의무·집행 | Agent가 하는 실제 의미 작업 | Agent 호출 없이 코드가 하는 일 |
| --- | --- | --- | --- |
| 요청·작업 조정 | 허용된 scope·역할·미해결 작업·의존 관계와 재개 상태 유지 | 자연어 의도·모호함·업무 분해·필요 능력 판단 | 명시된 명령 라우팅, 등록 상태·의존 조건 확인, 동일 작업 중복 제거 |
| 구현·설계 변경 | 영향 조사·검증·문서 갱신 의무와 사용자 변경 보존, 누락 수락 거절 | 요구 기반 설계/코드 작성, 호출·상태·데이터 책임 판단 | baseline/diff·변경 경로·생성물 동기화·정적 검사 |
| 최초 Feature Map | 전체 조사/분할 의무와 미완료 영역 유지, 일부만으로 init 완료 거절 | 요구·진입점의 기능 해석, 영역 분할, 불변조건·책임·검증 연결 작성 | 후보/파일 수집, ID·참조 대조, 묶음 진행 집계·병합 무결성 |
| 기능 고도화 후 지도 갱신 | 작업 diff와 연결에서 갱신 의무 발생, 누락/오래된 갱신이면 완료 거절 | 영향 의미와 공유 소비자를 조사하고 실제 Feature 내용·구현/검증 참조 수정 | diff/기준 식별, 기존 연결의 후보 계산, 누락·중복·끊긴 명령 검사 |
| 검증 | 필요한 검사·근거 제출 의무 유지, 미실행/실패/유효하지 않은 결과로 완료 거절 | 비즈니스·아키텍처 영향 판단, 필요한 새 검사의 설계, 실패 원인 해석 | 이미 정해진 명령 실행, 실제 exit/count/skip 수집, raw 연결·정형 판정 |
| 독립 검토와 수정 | 필요한 검토·수정·재검증 의무 유지, 검토 대상과 쓰기 범위 제한 | 요구/diff/실제 결과의 독립적 의미 검토와 발견 사항 수리 | 대상 snapshot·근거 연결 확인, 바뀐 범위의 근거 무효화·재검증 실행 |
| 피드백·재발 방지 | 등록된 예방책의 적용 조건에서 해당 검사/제약을 자동 적용하고 미해결 후속 작업 유지 | 근본 원인 추적, 적합한 code/type/constraint/component/검사 수정 | 등록된 validation·constraint·회귀 실행, 해당 범위의 위반 검출 |
| UI 기준 | 영향 공통 자산의 기준 갱신/상태 검증 의무 발생, 누락 확인 | 디자인 의도·예외 판단, 실제 guide/token/component·화면 개선 | token 파생물 생성, 정해진 viewport/interaction 검사와 결과 수집 |
| 결과 조회 | 조회 요청에 실행/수리 권한을 부여하지 않고 결과 유효성 정책 적용 | 필요할 때 결과 의미를 사용자에게 설명, 불명확한 원인 조사 | 기존 결과 읽기·정형 집계·상태 출력. 구조화 결과만 요청하면 LLM 없이 종료 |
| 유지보수·검사 정리 | 적용되는 drift 점검과 변경 후 재검증 의무, audit-only 범위 유지 | 의미적 drift·중복/고유 검출력·제거의 타당성 판단과 실제 수리 | 죽은 명령/참조·배포 drift 검출, 선택한 대조 실행, 같은 raw 재사용 |
| 설치·배포 자산 | 설치 대상·버전/일관성·권한·실패 복구 조건, 무권한 외부 효과 거절 | 새로운 호환성 문제 진단, 패키지/정책 수정안 설계 | canonical/generated 동기화·트리 비교·정해진 설치/복구 실행·결과 기록 |
| 실행 자원·중단/재개 | 소유 프로세스·출력·작업 상태·보존·미완료 의무 유지 | 불명확한 환경 실패 진단과 허용된 대안 선택 | 정해진 launch/readiness/timeout/cleanup·상태 저장/복원, 만료된 근거 표시 |
| 권한·완료 | Agent가 바꿀 수 없는 권한과 정책으로 효과/수락을 거절, 의무 누락 여부 재계산 | 허용 범위 안의 작업 수행, 의미 검토와 미해결 사항 설명 | 정확한 후보/정책 revision 및 근거 일치 확인, 허용/거절 결과 생성 |

Feature Map으로 예를 들면 `갱신해야 한다`는 규칙의 소유자는 환경이고 `무엇을 어떻게 갱신한다`는 판단과 실제 편집의 소유자는 Agent다. 같은 구분이 검증 수행·피드백 수리·UI 기준 개선·설치 일관성 등에도 적용된다. 단순히 Skill에 “항상 수행하라”를 추가하거나 Agent가 `done: true`를 쓰는 것으로 구현했다고 하지 않는다. 의미 완전성은 기계 검사만으로 보장되지 않으며 필요한 검토를 함께 연결한다.

결정적 처리는 **같은 입력·버전·실행 조건에서 같은 규칙과 판정**을 제공한다. 외부 서비스·브라우저 timing·LLM 출력까지 항상 동일하다고 약속하지 않는다. 관련 fixture/환경을 통제하고 불확실한 관찰을 드러낸다. 환경 처리가 가능한 값을 LLM에게 다시 계산·복사·판정시키지 않는다.

### 4.2 지침, 검사, 우회 불가 통제는 다르다

| 수준 | 예 | 적절한 주장 |
| --- | --- | --- |
| Agent 지침 | Skill의 조사/판단/작업 순서 | 따르도록 안내하며 행동 평가가 필요 |
| 로컬 결정적 검사 | schema, lint, viewer, 선택적으로 실행하는 wrapper/hook | 실행된 경로에서 같은 규칙으로 거절. Agent가 생략·수정 가능하면 우회 불가 아님 |
| 보호된 수락/효과 경계 | Agent 쓰기 권한 밖의 정책·검증 실행자, 분리된 DB 권한, 실제 host 권한 집행 | 명시한 우회 경로를 시험한 지원 범위에서 효과 또는 수락을 거절 |

Git의 `pre-commit`은 우회 옵션이 있고 hook 위치도 설정할 수 있다. 따라서 로컬 hook을 설치한 것만으로 강제 경계를 구현했다고 하지 않는다. [Git hooks 공식 문서](https://git-scm.com/docs/githooks#_pre_commit), [Git 설정 공식 문서](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corehooksPath).

환경에서 막으려면 적용 지점, 허용되는 행위, 실패 시 거절되는 효과, 정책 변경 권한, 우회 경로가 구체적이어야 한다. 구현 Agent에게 정책 변경·결과 위조·대상 쓰기·수락 권한이 모두 있으면 같은 디렉터리에 검사 파일을 추가하는 것으로 해결되지 않는다.

초기 구현은 기존 host/운영체제의 권한과 로컬 격리를 우선 사용한다. 실제 제공할 host 하나에서 다음을 확인한다.

- 구현자는 후보 source와 필요한 tests/docs를 수정한다. 초안·중간 실패·로컬 작업은 가능하다.
- 승인된 기준과 canonical 수락 결과는 구현자가 임의로 바꿔 채택할 수 없는 위치/권한이 소유한다. 보호된 실행자는 고정한 후보 snapshot을 검증하고 그 snapshot에만 결과를 연결한다.
- 프로젝트 코드·테스트·자식 프로세스에도 보호된 정책/결과의 쓰기 권한이나 외부 효과 권한을 넘기지 않는다. 실행자만 분리하고 그 권한으로 후보 스크립트를 그대로 실행하면 우회 통로가 남는다. 검증 Agent의 context만 새로 만드는 것도 운영체제/host 권한 분리를 대신하지 않는다.
- 프로젝트 테스트·설정 변경은 금지하지 않는다. 변경 내용을 검토 대상으로 드러내며, 기준·보호 정책의 변경은 기존 권한에 맞는 별도 경로로 반영한다. 후보가 검증 중 바뀌면 결과를 재사용하지 않는다.
- 검증 도구를 건너뛰거나 다른 shell/직접 파일·DB 접근을 시도해도 금지한 효과는 거절되는지 확인한다. 자체 성공 JSON이나 정책 완화 diff가 그대로 공식 수락이 되면 실패다.
- 사용자/상위 host는 기존 승인 경계를 소유한다. 지원하지 않는 host에서는 `advisory/검사 수준`을 명시하고 강제 보장을 BLOCKED로 남긴다. 막힌 경로를 동일 권한의 새 wrapper로 우회해 성공 처리하지 않는다.

이것은 Agent가 임의의 나쁜 코드를 작성하지 못하게 하겠다는 약속이 아니다. **허용되지 않은 효과와 기준 미충족 결과의 수락을 차단하는 경계**다. 조건이 불명확한 의미 판단은 검토하며, 단순 정형 검사만으로 안전·정확성을 확정하지 않는다. 일반 설치·전역 정책·원격 보호 설정을 이번 문서 변경으로 적용하지 않는다.

### 4.3 모든 업무의 공통 처리 흐름과 예시

1. **환경이 계기와 사실을 수집한다.** 요청, 실제 diff, 실패/피드백, 기준 변경, 설치/재개 등에서 현재 정책과 작업 상태를 확인한다. 사용자의 미커밋 baseline은 구분한다. 지원 host의 작업·실행·수락 경계에 연결하며 Agent가 선택적으로 호출하는 체크에만 의존하지 않는다.
2. **환경이 적용되는 의무를 만든다.** 지도 갱신, 영향 검증, 실패 수리/재검증, UI 기준 연결, 설치 무결성 등 해당 의무만 발생시킨다. 모르는 영향은 필요한 의미 조사로 남기고 자동 제외하거나 Full로 승격하지 않는다.
3. **정형 작업은 코드가 직접 수행한다.** 기존 도구/기준으로 사실 수집·실행·검사·집계를 끝낼 수 있으면 LLM 없이 처리한다. 같은 대상·조건의 유효 실행을 재사용한다.
4. **의미 작업만 Agent에게 전달한다.** 발생 이유, 현재 대상과 적용 조건, 관련 참조, 필요한 판단/산출물만 준다. Agent가 조사·설계·실제 코드/지도/UI/검사 수리를 수행한다. 이미 수집한 사실을 다시 만들지 않는다.
5. **환경이 새 결과를 확인한다.** 정형 요건·실행/대상/기준 연결과 필요한 의미 검토 근거를 검증한다. 파일 존재·timestamp·자체 성공 문자열만으로 해소하지 않는다. 의미적 정답은 요구/관찰/필요한 독립 검토와 구분한다.
6. **해소·재개·수락을 환경이 관리한다.** 충족한 의무만 관련 기준에 연결하여 해소하고 변경으로 무효화된 부분만 다시 연다. 미해결은 context를 바꿔도 유지한다. 초안/독립 작업은 계속 허용하되 누락된 범위의 완료 수락은 거절한다.

Feature Map에서는 환경이 갱신 의무를 만들고 Agent가 실제 내용을 수정한 뒤 검증한다. 피드백에서는 환경이 미해결 수리·재검증을 유지하고 Agent가 원인을 고친 뒤 기존/새 회귀를 코드로 실행한다. 설치 무결성은 이미 명령과 기준이 정해졌다면 트리 비교·동기화·검증을 LLM 없이 끝내고 새로운 충돌의 해석만 Agent에게 넘긴다. 이들은 공통 원칙의 서로 다른 적용 예다.

의무의 최소 정보는 종류, 대상/base 또는 입력 revision, 발생 근거·영향 기능/자산, 필요한 산출물·근거, 현재 상태다. 기존 Harness/작업 기록과 프로젝트 설정에 통합하고 Skill별 체크리스트나 별도 범용 작업 엔진을 중복 생성하지 않는다. Agent가 제안한 `영향 없음`·예외는 근거로 검토할 입력이며 정책 해제 권한이 아니다. 권한 있는 범위 수정/기준 교정은 이유와 새 revision을 보존하는 경로로 처리한다.

### 4.4 Agent 호출과 context를 줄이는 기준

이미 정의된 입력/출력과 규칙으로 처리할 수 있는 후보 수집, 구조·참조 검사, 명령 실행, raw 수집, 정형 결과 조회, resource sync, 파생 색인/목록 생성은 code/CLI/script 경로가 바로 수행한다. 이를 설명하거나 승인받기 위해 LLM 단계를 끼워 넣지 않는다. CLI/CI에서 직접 호출해도 같은 처리가 가능해야 한다.

요구의 의미가 달라지거나 새 검사가 필요하거나 원인·설계·시각 판단이 불명확할 때 Agent를 호출한다. 환경은 필요한 차이와 참조, 적용되는 조건만 제공하고 전체 정책·Feature Map·raw 이력을 매번 context에 넣지 않는다. Agent에는 작업 방식과 관련 의미 기준을 안내하되 모든 의무를 기억하고 순서대로 되풀이할 책임을 맡기지 않는다.

코드가 할 수 있는 부분/Agent가 필요한 부분을 혼합한 요청에서는 앞의 결과를 재사용한다. 같은 diff의 동일 의무·실행은 합치고, 재개 시 완료된 조사를 반복하지 않는다. 감소 효과는 실제 전달 context, 모델/도구 호출, 중복 실행과 개입 기록으로 확인한다. deterministic-only 경로의 모델 호출이 없음을 실행 경로로 검증하며 임의의 `llm_calls: 0` 필드는 증명이 아니다.

Skill은 환경에서 받은 제한된 작업을 잘 수행하는 방법을 맡는다. 환경은 Skill이 호출되지 않아도 의무 누락을 드러내고 지원되는 수락 경계에서 차단한다. 반복 안내문을 늘려 이 역할을 대체하지 않는다.

## 5. 피드백을 환경의 재발 방지로 전환

`피드백 → 요구와 재현 → 실제 원인/기존 예방책의 실패 이유 → 최소 소유 위치 수정 → 예방 수단 → 원래 실패와 정상 반례 → 활성 경로 연결 → 다음 작업의 소비`를 한 기능 단위로 완료한다.

| 원인 예 | 적합한 개선 | 피해야 할 대체 |
| --- | --- | --- |
| 입력과 저장 금액 불일치 | 변환 소유자 수정 + 경계/저장·재조회 검사 | 전역 “금액에 주의” 문구만 추가 |
| 불가능한 데이터/상태 | 실제 불변조건에 맞는 type·runtime validation·DB 제약 | 모든 데이터 쓰기를 막거나 정상 상태까지 금지 |
| 검증 누락·거짓 성공 | required check와 producer 연결, 결정적 판정, 필요 시 보호된 수락 | PASS 문장을 더 길게 요구 |
| 지도/명령 갱신 누락 | diff와 영향 ID·활성 명령의 무결성 확인 + 의미 검토 | 문서 timestamp 변경만 강제 |
| UI 반복 불일치 | 공통 component/token·상태 API와 실제 interaction 회귀 | 모든 화면에 한 규격을 강제해 의도된 예외 제거 |
| 권한 밖 효과 | 지원 host의 실제 접근/효과 제한 | 금지 지침을 반복하거나 사후 검사만 수행 |
| 지침 미발견/과잉 또는 도구 오탐 | 발견 경로·도구·적용 범위 교정, 중복 규칙 제거 | 같은 규칙을 다른 Skill에 복사 |

한 번의 사건도 재현·영향이 명확하면 즉시 구조적으로 예방한다. 반대로 의미가 불명확한 사건을 억지 정형 규칙으로 바꾸지 않는다. 강제할 수 있는 부분과 독립 검토가 필요한 부분을 설명한다. 모든 버그에 새 hook/정책/프레임워크를 추가하지 않는다.

정답 기준이나 관찰 도구 자체가 잘못된 경우에는 독립 근거로 이를 교정하고 이전 실패/기준 변경을 보존한다. 올바른 기준 수리를 금지하는 통제도, 구현에 맞춰 정답을 낮추는 자동 수정도 채택하지 않는다.

예방책은 기존 Feature/검사/정책 소유 위치에서 실패 유형, 적용 범위, 검출/차단 경로, 정상 예외, 재검토 조건을 추적한다. 별도 수동 장부를 중복 생성하지 않는다. 규칙 변경·폐기는 같은 결함 검출과 정상 허용 근거로 판단하고 기존 권한 범위를 지킨다. 장기적으로 “다시는 어떤 형태로도 재발하지 않음”을 보장하지 않으며 차단한 실패 유형을 명확히 한다.

## 6. 결과 생산·조회와 UI 기준

현재 viewer/capture/프로젝트 adapter를 재사용해, 실행 전 선택한 요구·검사를 실제 실행·원본·판정까지 자동 연결하는 최소 경로를 구현한다. 동일 facts를 JSON/Markdown에 손으로 반복 입력하지 않는다. 조건 식별값은 측정하여 수집하고, 프로젝트별 의미·허용 예외는 기준에서 가져온다.

원래 결과, 현재 재사용 가능성, 확인된 실패, 미검증 범위를 함께 보여준다. 실제 현재 PASS를 만들고 source/기준/명령/의존성/fixture/runtime 변경 시 영향을 받은 근거만 무효화하는 정상·실패 대조가 필요하다. 저장 흐름에는 UI→API→저장→재조회와 필요한 DB producer를 연결한다. 조회만 요청하면 새 실행이나 과거 근거 수정이 없어야 한다. 원본 만료는 현재 확인 불가로 남긴다.

현재 모든 조건 그룹을 요구하는 viewer를 완화해 성공을 만들지 않는다. 향후 적용 불가능한 조건이 실제로 있으면 프로젝트 검사 유형의 명시적 계약과 정상·우회 반례로 판단한다. Agent가 임의로 `not_applicable`을 써서 필수 관찰을 없애는 방식은 허용하지 않는다.

UI는 기존 기준 개선뿐 아니라 기준이 없는 상태의 생성도 수용한다. 디자인 의도·대표 화면·loading/empty/error·responsive·접근성·의도된 예외를 기존 token/component와 연결한다. 값은 코드가 소유한다. 두 번째 fresh context의 다른 화면 요청에서 실제 재사용되는지 확인하고 자동 수치 검사와 시각적 판단을 구분한다.

## 7. 효율·효과·정확성의 수용 기준

새 제약이나 검사는 이득을 가정하지 않고 아래를 함께 평가한다. 평가 범위와 허용 부담은 결과를 보기 전에 과업의 위험·비용에 맞춰 정한다. 보편적인 실행 시간/점수 기준은 만들지 않는다.

| 확인할 것 | 비교 방법 | 채택 판단 |
| --- | --- | --- |
| 결함과 거짓 완료 | 같은 기준의 정상/결함/우회 사례를 기존·후보 환경에 실행 | 명시한 결함/금지 효과가 남거나 거짓 수락하면 미완료 |
| 정상 사용과 오탐 | 가까운 정상 반례, 의도된 예외, 작은 수정·조회 | 정상 작업을 잘못 차단하면 적용 범위를 고치고 재검증 |
| 실제 위임 | Skill/순서/정답 패치 없는 요청, fresh context, 중단·재개 | 추가 사용자 지시·검토자 구조 요청을 기록. 개입을 숨긴 무감독 성공 주장 금지 |
| 수행 부담 | 실제 경과 시간, 도구/모델 호출과 사용량이 제공되면 기록, 반복 실행·재시도·사용자 개입 | 검출/재작업 감소 이득 없이 부담만 늘면 통합·축소·제거 |
| 재사용/지속성 | 후속 요청·관련 변경·설치 갱신 | 기준·공통 구현·검사가 실제 활성 경로에서 소비되어야 함 |

같은 host/모델 설정·대상 snapshot·fixture·과업·요구를 사용하고, 후보 통제만 달라지는 비교를 우선한다. 알려진 정답 패치를 평가 Agent에게 주지 않는다. 모델 변동성은 반복 관찰로 구분하며 소수 사례에서 일반적 속도·비용 우월성을 주장하지 않는다. 제공되지 않은 비용을 추정해 측정값으로 쓰지 않는다.

적법한 권한 경계는 비교에서도 유지한다. 새 guardrail이 정상 과업을 방해하면 원인을 수정하거나 불필요한 guardrail을 제거한다. 핵심 위험 통제를 제거해야만 빠른 경우에는 위험·지원 범위를 명시하고 기존 승인을 따르며, 시스템이 제약을 스스로 풀어 점수를 높이지 않는다.

전체 지도는 초기 한 번 완성하고 이후 영향 기반으로 갱신한다. 매 요청 전체 조사/Full/고정 Agent 수/추가 승인 단계를 요구하지 않는다. 한번의 유효 실행을 여러 주장에 재사용한다. 결정적 CLI도 적용 범위를 벗어난 확인은 실행하지 않는다.

## 8. 온전한 기능 단위와 구현 순서

아래는 후속 구현의 인수 기준이며 이번에 실행한 결과가 아니다. 기존 세 Skill과 도구를 우선 고치며 단위별 새 Skill/서비스를 만들지 않는다. 각 단위는 source/tests/generated/관련 map·guide와 임시 설치·실제 업무 근거를 함께 완료한다.

| 단위 | 제공할 사용자 업무 / 주요 소유 위치 | 단위 완료 기준과 반례 |
| --- | --- | --- |
| U1 전체 init과 필수 갱신 | “프로젝트의 전체 기능과 검증 지도를 마련해줘.” setup/maintain·공유 참조·기존 프로젝트 명령/지도 연결 | 알려진 전체 기능 oracle을 가진 fixture에서 UI/API/CLI/숨은 역할 흐름 포함. 큰 지도 분할·context 재개·최종 통합. 환경이 초기화/갱신 의무를 발생·유지하고 Agent가 실제 작성. 누락/중복/기준 변경에서 완료 거절. 이후 추가·수정·삭제·공통 변경에 실제 지도 갱신, 문서 오탈자 정상 허용 |
| U2 환경 집행과 실행 수락 | “허용한 작업만 실행하고 검증된 결과만 받아들여줘.” 기존 capture/adapter/설치·지원 host 경계 | task-local 실제 경계에서 금지 쓰기/직접 명령·정책 변경/위조 결과·대상 교체를 거절하고 정상 편집·검사·실패 분석은 허용. 소유 자원 정리와 설치 갱신/복구 확인. 로컬 검사만 가능한 host는 강제 완료로 처리하지 않음 |
| U3 실제 검증과 조회 | “이 기능을 검증하고 확인한 내용을 보여줘.” workflow/viewer와 프로젝트 adapter | 사전 기준에서 실제 현재 PASS 생성. 의미·계층별 결과와 end-to-end 관찰 연결. 0/필수 skip/다른 대상/raw 누락/변경 기준 거절. 기존 결과 조회는 재실행 없음; U2의 수락 수준과 advisory 결과 구분 |
| U4 피드백과 재발 방지 | “동작이 의도와 달라. 원인을 고치고 재발을 막아줘.” diagnose·공유 원인/예방 지침·실제 소유 코드 | 업무 규칙과 상태/경계 원인을 각각 다루고 코드/제약/검사 중 적절한 수단 선택. 같은 실패 RED→GREEN·정상 예외·독립 검토 수정·다음 요청 재사용. 지침만 추가해 완료 불가 |
| U5 UI 기준 생성·발전 | “UI 기준을 만들거나 개선하고 화면에 적용해줘.” 기존 UI 능력·프로젝트 guide/token/component | 기준 없는 작은 UI와 기존 기준이 있는 UI 모두 확인. 공통 수정·desktop/mobile·interaction/상태·의도된 예외. 다른 fresh context의 후속 화면 재사용. 수치/스크린샷만으로 시각 품질 완료 불가 |
| U6 유지보수와 검증 가치 | “체계의 누락과 불필요한 검사를 개선해줘.” product/Harness maintain·직접 검증 | 제품·Harness drift를 함께 수리, audit-only·비-Harness 정상 반례. 통제된 중복 사례 하나를 실제 통합해 동일 결함 검출/정상 허용 보존. 고유 검사 삭제 거절. 제약 없는 비교 대비 오탐·개입·실행 부담 확인 |
| U7 최종 패키지 인수 | Skill 이름 없는 연속 업무·조회·재개. 기존 canonical 배포·임시 host 검증 | 실제 제공할 패키지/host에서 U1–U6 연결. fresh install·update·중단/재개·사용자 변경 보존·중복 발견 방지. 지원/미지원 host와 enforcement 수준 명시. 일반 설치/공개 배포는 별도 승인 범위 |

후속 작업은 먼저 전체 능력과 각 단계에 §4의 두 분류 축을 적용해 현재 소유 위치·실행 경로·미구현 경계를 확인한다. 이는 기존 파일·호출자에 연결한 짧은 구현 조사이며 새로운 분석 프로젝트로 멈추지 않는다. 지원 host의 가능성을 확인하고 환경 상태/의무·직접 실행·Agent handoff·수락 연결에서 공통으로 필요한 부분을 기존 도구에 반영한다.

이 기준은 U1–U7 모두의 필수 인수 조건이다. U1→U2→U3→U4/U5→U6→U7의 의존 순서를 참고하되 공통 경계와 직접 결합된 기능은 같은 온전한 단위로 구현한다. Feature Map, 검증/조회, 피드백, UI, 유지보수, 설치/재개 각각에 역할 분리와 직접 실행을 실제 적용하고 확인한다. 어떤 단위부터 시작하더라도 다음 실행 범위를 Feature Map에만 제한하거나 다른 기능의 책임 분리를 부수 작업으로 미루지 않는다. 단위별 완료와 전체 완료는 별도이며 host가 막힌 강제 보장은 BLOCKED로 남긴다. 상세 실행은 [전체 체계 고도화 프롬프트](agent-workflow-next-session.md)를 따른다.

U1의 전체 init 능력은 먼저 제품 독립 시험 프로젝트에서 확인한다. 연두라벨의 전체 지도 작성은 §0의 G4 패키지 고정 후 G5에서 시험한다. 나머지 수용은 필요한 기존 흐름과 작은 통제 결함으로 제한한다. 다른 기술 스택/비-Harness/기준 없는 UI도 G4 전에 확인하며, 연두라벨 연결을 먼저 개발해 공통 기능의 완성을 대신하지 않는다.

각 단위는 필요한 native/설치 검사와 실제 Agent 요청을 구분해 기록하고 검증한 기능 단위로 커밋한다. 초안/중간 작업은 허용하며 필수 기준이 빠진 단위를 완료·정식 수락으로 승격하지 않는다. 새 실패·미해결 영향 없이 검사 범위를 반복 확대하지 않는다.

## 10. 이번 문서 변경과 다음 행동

문서 작업에서는 전체 기능에 공통인 책임/처리 방식 분류와 다음 실행 프롬프트를 정리하고 관련 진입 문서를 갱신한다. runtime, Skill 지시문, generated, 일반 설치, Labeler와 host 권한은 변경하지 않는다. 해당 source/generated 개선은 전체 능력의 분류를 바탕으로 U1–U7의 실제 기능 단위에 적용·검증한다. Feature Map만 구현해 전체 역할 분리가 완료되었다고 하지 않는다.

문서 검증은 기존 `python -m unittest tests.distribution.test_repository_docs`와 `git diff --check`, 그리고 기존 결론과의 충돌·현재/예정 상태·링크를 수동 대조한다. 이는 문서의 구조/정합성 확인이며 U1–U7의 행동 검증이나 우회 불가 보장이 아니다.
