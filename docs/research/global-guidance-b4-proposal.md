# B4 개정안과 확인 방법

상태: **아래는 실행 전 고정한 제안과 기준이며, 이후 4세션을 수행했다.** [실제 결과와 최종 판단](global-guidance-b4-results.md)을 우선한다. [B4 전역 후보](global-agent-instructions-b4.md)는 운영 파일과 분리했다. [B3 결과](global-guidance-b3-trial.md)의 미완료를 전반적으로 해결했다고 주장하지 않는다. 이전 후보와 원시 자료를 보존한다.

## 구체적인 수정

B1의 12개 조항 중 아래 3개를 교체한다. 나머지 권한, 사용자 변경·데이터 보존, 맥락 해석, 필요에 따른 계획·위임, 소유권, 변경 종류별 검증, 문서 책임과 간결한 전달은 유지한다.

| 조항 | 교체하는 판단 기준 | 확인할 행동 |
| --- | --- | --- |
| 실행·관찰 | 작업 크기는 절차의 양을, 바뀐 동작은 필요한 근거를 결정한다. 사용자가 도구를 지정하지 않아도 실행 경로를 찾는다. | 작은 API 변경을 diff나 컴파일만으로 끝내지 않고 실제 응답을 확인하는가? |
| 장애 대응 | 결과가 없으면 실행 상태와 근거로 원인을 구분한 뒤 다음 행동을 선택한다. 실제 권한 제한과 불필요한 절차를 구분한다. | 명령 하나의 실패를 목표 전체의 불가능으로 확대하지 않는가? 실제 사용자 조치가 필요하면 실행 가능한 안내를 하는가? |
| 충분성·계승 | 요청한 결과를 뒷받침하는 근거가 충분하면 마무리한다. 유효한 근거를 재사용하고 관련 없는 잔여로 범위를 넓히지 않는다. | 필요한 결과를 확인한 뒤 같은 확인을 반복하거나 전체 프로젝트 정비를 요구하지 않는가? |

이는 새 금지 목록을 추가하는 변경이 아니다. Windows 명령·세션 조회법·커밋 정책은 전역에 넣지 않는다. pstack correct의 판단/구조 책임 분리와 hillclimb의 원인별 비교를 선택적으로 참고했다. 고정 모델·인원·플레이북 전체는 도입하지 않는다.

## 이미 수행한 확인

기존 독립 평가기 `check_api.py`를 수정하지 않고 실제 앱에 실행했다. service 필드가 빠진 기준 코드는 해당 관찰에서 실패하고, 올바른 구현은 15개 HTTP·Domain·SQLite·정리 관찰을 통과했다. 기대값을 바꾸거나 검사를 제거하지 않았다. 이는 평가기의 구분 능력 확인이지 B4의 행동 개선 증거가 아니다.

후보는 B1과 비교해 정확히 세 bullet만 달라졌고 총 12개다. 원문 A와 B1, B4, 두 diff, 현재 운영 파일 해시, 실행 입력은 `.work/global-guidance-b4-20261018/`에 보존한다. 현재 운영 원본과 설치본은 바꾸지 않는다.

## 다음 비교: 네 개의 새 세션

| 조건 | A | B4 | 무엇을 분리하는가 |
| --- | --- | --- | --- |
| 기존 프로젝트 안내에서 실행 경로를 스스로 발견 | 1회 | 1회 | 전역 지침이 경로 선택·실제 관찰을 바꾸는가? |
| 같은 과제에 기존 실행기 사용법을 명시 | 1회 | 1회 | 경로 발견 문제인가, 경로를 알아도 실행·결과 판단을 못 하는가? |

두 번째 조건에는 양쪽에 동일하게 기존 `run_project.py --report` 사용법과 서비스/브라우저 결과가 별도로 남는다는 프로젝트 사용 정보만 준다. 정답 패치·평가기·채택 의도는 주지 않는다. 안내받은 성공은 무도움 성공으로 집계하지 않는다. 후보 경로는 north/south/east/west처럼 중립적인 프로젝트 이름으로 준비했다.

두 조건 사이의 차이는 사용 안내뿐이다. 각 A/B4 쌍은 같은 seed·사용자 변경·모델·추론·도구·권한·스킬을 사용한다. 모델은 작은 과제에 맞춘 `gpt-6-luna / medium`으로 고정하며 임의 대체하지 않는다. 실제 로딩 지침·모델·스킬 목록을 확인한다. 런타임의 스킬 자동 노출이 달라지면 해당 비교를 무효로 표시하고 중단한다. 이를 맞추려고 설치본이나 운영 설정을 변경하지 않는다.

부모 개입 없이 작업을 끝낸 후 raw 도구 호출과 최종 산출물을 읽는다. 문구 준수 자기보고나 실행 시도만으로 통과시키지 않는다. 매번 독립 평가를 하고, 후보 스스로 얻은 관찰과 분리해 기록한다.

## 채택 기준과 결과 해석

우선 기준은 정확한 구현·사용자 변경 보존·권한 준수·후보가 얻은 실제 응답 관찰이다. 필요한 근거 없이 성공을 주장하거나, 실행 중 결과를 회수하지 않거나, 전체 BLOCKED만 보고 이미 얻은 유효 관찰을 놓치면 미완료다. 실제 사용자 권한이 필요한 경우의 구체적인 다음 행동은 별도로 평가한다.

시간·입력/캐시/출력 토큰·질문·불필요한 검사·부모 지원도 함께 기록한다. 필요한 확인을 생략해서 빨라진 실행은 개선이 아니다. 실패·타임아웃·사용량 누락·스킬 미사용은 실행 목록에서 빼지 않는다.

- B4만 무도움 완료하고 보존·권한·범위 기준을 지키면, 이 과제에서의 제한적인 채택 근거로 삼는다.
- 안내를 줬을 때 양쪽만 성공하면, 전역보다 실행 경로의 발견 가능성을 우선 개선한다.
- 안내 후에도 둘 다 실패하면, 전역 문구를 더 늘리지 않고 도구 사용·실행 상태·모델 역량을 별도 원인으로 조사한다.
- 양쪽 모두 성공하거나 차이가 불명확하면 B4의 성능 우위를 주장하지 않는다. 문서의 명료성·중복 감소 판단과 행동 개선 판단을 분리한다.

이 네 번은 원인 분리용 진단이며 일반적인 성능 검증이 아니다. 중단·재개, 리팩터링, 전체 운영 플러그인 조합은 이번 소규모 비교로 검증되지 않는다. 최종안이 실험 문구와 달라지면 영향받은 행동의 근거 없이 실험 결과를 그대로 붙이지 않는다.

## 실행 예산과 적용 경계

이전 4세션 한도는 소진됐다. 새 비교는 추가 승인 전 실행하지 않는다. 제안은 최대 4세션, 각 6분·합계 24분, 누적 입력 800,000 또는 출력 16,000에 도달하면 신규 실행 중단이다. 진행 중 세션은 토큰 문턱을 넘을 수 있다. 예상은 모델 실행 2–6분, 입력 400,000–700,000(캐시 포함), 출력 4,000–10,000이며 보장은 아니다. 실패도 세션 한도에 포함하며 자동 재시도 예산은 없다. 새 유료 서비스를 사용하지 않고 실제 금액은 unknown으로 둔다.

승인 범위에서 실행·독립 확인·분석·최종 제안 갱신까지 수행한다. 운영 전역 교체, 설치 스킬/플러그인 수정, 전체 readiness 종료, push는 포함하지 않는다. 운영 반영은 결과 검토 후 별도로 [기존 전역 개정 절차](../agents/global-guidance.md)를 따른다.
