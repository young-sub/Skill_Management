  canonical/generated·설치/복구, 자원 정리·중단/재개·완료.
- 각 영역의 단계를 아래 두 축으로 분류하고 현재 구현·빠진 연결을 기존 소유 위치에 연결해라.

3. 모든 요소를 분류할 공통 기준
- 책임/권한 축: 환경은 의무 발생·상태·누락 차단·권한·재개·수락을 소유한다.
  Agent는 요구/영향/원인/설계/시각적 의미를 판단하고 실제 내용과 코드를 작성·수리한다.
- 처리 방식 축: 입력·규칙·출력이 정해진 단계는 코드/CLI/script로 직접 처리한다.
  맥락 해석·새 설계가 필요한 부분만 Agent에게 맡긴다.
  환경/Agent의 구분과 결정론/비결정론의 구분은 같은 축이 아니다.
- 브라우저/외부 API 결과가 변한다는 이유로 수집·timeout·정형 판정까지 LLM에 맡기지 마라.
  환경은 정한 규칙으로 실행 사실을 수집하고 의미가 불명확한 실패만 Agent에게 넘긴다.
- 혼합 업무는 기계 처리 → 필요한 의미 작업 → 기계 검증/수락으로 나눠라.
  입력과 정책이 정해진 경로는 Agent 호출 없이 직접 실행·조회할 수 있어야 한다.
- 예를 들어 “지도 갱신이 필요하다”는 환경의 의무이고 실제 갱신 내용 작성은 Agent의 일이다.
  같은 원칙을 검증 누락 방지, 재검증, 피드백 수리, UI 기준 갱신,
  설치 무결성, 자원 정리·재개에도 적용해라. 예시 하나로 범위를 제한하지 마라.
- 단계마다 환경 의무/계기, Agent 판단/행위, 직접 코드 경로, 불확실성 처리,
  권한/수락 경계와 실제 검증 근거를 식별해라.
- 환경은 필요한 의무·대상·발생 이유·관련 참조·산출물만 Agent에게 전달한다.
  같은 조사·raw를 복제하거나 전체 정책/지도/이력을 매번 context에 넣지 마라.
- 규칙을 기억하라는 Skill 지시만 늘리지 말고 실제 역할 분리를 구현해라.

4. 구현 방식
- 시작할 때 짧은 계획, 실제 사용할 host/설치본/권한 경계/행동 검증 경로를 확인해라.
  명확한 통상 구현 선택으로 설계 전체를 다시 승인받지 마라.
- 기존 Harness/프로젝트 설정/작업 상태, setup·maintain·agent-workflow,
  capture/viewer/native adapter와 source/generated를 우선 재사용해라.
  범용 정책 엔진·새 서비스·별도 중복 장부·절차별 Skill을 먼저 만들지 마라.
- 요청·실제 변경·실패/피드백·기준/설치 변경·재개에서 적용되는 의무를 만들고,
  미분류/미연결 변경도 조사 대상으로 남겨라. 모든 요청에 모든 절차를 강제하지 마라.
  path는 후보이며 업무 의미와 Full 여부를 자동 확정하지 않는다.
- Agent의 수정 후 최신 대상/기준/명령/근거를 재검증해라.
  updated:true, 자체 PASS, 파일 수정 여부, timestamp만으로 어떤 의무도 해소하지 마라.
  정형 검증과 필요한 의미 검토/행동 근거를 구분해라.
- 의무 해소는 해당 대상과 요구/정책/실행 기준에 연결하고 이후 변경이 무효화한 부분만
  다시 열어라. 동일 의무·조사·실행은 재사용해라.
- 새 의무를 문서와 Skill에 적는 것으로 환경 구현을 대신하지 마라.
  초안 편집·정당한 테스트/기준 수리는 허용하면서 누락 결과의 수락을 막아라.
- 지원 host에서 구현자가 바꿀 수 없는 수락/권한 경계와 실제 연결해라.
  정책·근거 파일과 후보 코드·테스트/자식 프로세스의 권한을 구분해라.
  로컬 hook/wrapper 생략이나 같은 권한의 파일 수정으로 우회되면 강제 보장이 아니다.
  host가 지원하지 않으면 advisory/결정적 검사와 강제 집행을 나누어 보고해라.
- 의미 있는 행동 변경은 집중 RED 후 같은 기준의 GREEN과 가까운 정상 반례를 확인해라.
  행동 보존은 baseline/equivalent GREEN을 사용해라.
  assertion/기준/skip을 완화하거나 성공 출력을 조립하지 마라.

5. 전체 능력의 실제 수용 검증
완성 설계의 U1–U7 기준과 아래를 함께 수행해라.
파일/schema/native 통과나 역할 표만으로 Agent 업무 성공을 주장하지 마라.

A. 요청·구현·전체 init과 변경
- Skill/순서/정답 패치 없는 요청에서 필요한 절차만 선택되는지 확인한다.
- 전체 기능 정답을 가진 작은 fixture와 독립 Labeler에서 전체 지도 작성/기존 자산 재사용을 확인한다.
- UI 외 API/CLI/역할 변형, 큰 지도 분할·context 재개·통합,
  기능 추가/수정/삭제/공통 소비자 변경, 누락/중복/도중 기준 변경을 포함한다.
- 갱신을 다시 요청하지 않아도 환경이 의무를 만들고 Agent가 실제 수정하는지 확인한다.
- 지도를 빠뜨린 수락은 거절하고 정상 수정 후 수락한다.
  오탈자/의미 불변 정상 사례에 불필요한 전수 조사·Full·내용 날조를 강제하지 않는다.

B. 검증 계획·실행·조회와 독립 검토
- Agent가 비즈니스/아키텍처 영향과 필요한 FE/BE/Domain/전체 흐름 기준을 판단하고,
  환경이 필수 검사와 근거 의무를 유지하며 코드는 실제 native/browser/저장·재조회를 실행한다.
- 실행 전 기준과 측정한 조건에서 실제 현재 PASS를 생산하고 조회까지 연결한다.
  0건/필수 skip/다른 대상/raw 누락/stale/위조 요약으로 완료 수락하지 않는다.
- “기존 결과만 보여줘”에서는 실행·수리 없이 조회한다.
- 독립 의미 검토의 발견→Agent 수정→환경의 영향 근거 무효화/재검증을 확인한다.

C. 피드백과 예방
- 짧은 불편 설명에서 Agent가 원인과 소유 경계를 추적하고 실제 코드/제약/검사를 고친다.
- 환경이 해결·재검증 의무를 유지하고, 등록한 예방책은 다음 적용 상황에 자동 검사/집행한다.
- 같은 실패 RED→GREEN·가까운 정상 반례·fresh context의 재사용을 확인한다.
  지침만 추가하거나 모든 피드백을 전역 금지로 바꾸어 완료하지 않는다.

D. UI 기준과 재사용
- 기준이 있는 UI의 개선과 없는 UI의 초기 생성을 모두 다룬다.
- 환경은 영향 기준/검증 의무를 유지하고 Agent는 의도/예외를 판단해 guide·공통 구현을 수정한다.
- 측정 가능한 검사/파생물은 코드가 처리하고 시각적 판단과 구분한다.
- desktop/mobile·interaction/상태·정상 예외 및 새 context의 다른 화면 재사용을 확인한다.

E. 유지보수·검사 정리
- 제품/Harness 양쪽의 실제 drift를 수리하고 audit-only·비-Harness 반례를 구분한다.
- 기계적 drift 탐지/비교와 Agent의 의미·검출 가치 판단을 분리한다.
- 통제된 중복 사례를 실제 통합해 같은 결함 검출·정상 허용을 유지하고,
  고유 검출력이 있는 검사 삭제는 거절한다.

F. 설치·실행 자원·재개·수락
- canonical/generated 검사, 임시 설치/갱신/복구의 실제 트리와 host 발견·Agent 사용을 구분한다.
- 소유 자원 정리와 context/프로세스 중단 후 상태·의무·유효 근거 재사용을 확인한다.
- 선택적 명령 생략, 직접 파일 수정, 정책/성공 기록 조작, 대상 교체,
  후보 테스트/자식 프로세스를 통한 우회에도 지원하는 효과/수락 경계가 유지되는지 시험한다.
- 정상 편집·권한 있는 기준 수리는 허용한다.
  환경 불가이면 해당 보장은 BLOCKED다. advisory 검사를 강제 집행이라고 하지 않는다.

G. 모든 영역의 직접 처리·context·성과
- 역할 분리를 지도 한 사례에서만 확인하지 말고 A–F 각 영역에 적용 근거를 남긴다.
- 정해진 검사 실행·정형 조회·resource sync/트리 비교 등 의미 판단 없는 경로는
  CLI로 직접 수행하고 실제 모델 호출이 없음을 확인한다.
- 의미 작업은 필요한 context만 Agent에게 전달하고 이미 처리한 사실을 반복하지 않는다.
- 필요한 실제 Agent 위임과 독립 검증은 허용하되 공통 수정은 한 소유자가 맡는다.
- 같은 요구/대상/fixture/host에서 기존 방식과 후보의 정상·결함·누락/우회를 대조한다.
  실제 개입·context·모델/도구 호출·중복 실행·시간을 관측 가능한 만큼 기록한다.
- 규제로 정상 업무가 더 나빠지면 적용 범위를 고친다. 추가 규칙 수를 성과로 삼지 않는다.
  필수 권한 경계를 완화하지 않고 일부 성공으로 보편적 품질/속도/비용 향상을 주장하지 않는다.
