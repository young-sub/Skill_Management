2. 이번에 완성할 사용자 업무
“프로젝트의 전체 기능과 검증 지도를 마련해줘.”
그 후 사용자가 지도 갱신을 다시 말하지 않고 기능을 변경해도,
환경이 갱신 의무를 발생·유지하고 Agent가 실제 지도를 수정하며,
누락된 결과는 공식 완료로 수락되지 않아야 한다.

- 최초 init은 모든 사용자/운영 기능을 대상으로 한다.
  요구, 화면, API/CLI, job/event, 역할/flag, 저장/외부 효과를 교차 조사해라.
  모든 Feature에 요구·불변조건·FE/BE/Domain 책임·실제 흐름·검증 연결 또는
  미연결 상태를 포함해라. 한 중요 흐름의 실행만으로 전체 init 완료라고 하지 마라.
- 큰 지도는 업무 영역별로 분할하고 context 교체/중단 후 재개할 수 있게 해라.
  모든 묶음과 영역 간 연결을 통합하기 전 전체 상태는 PARTIAL이다.
  모든 기능의 테스트 PASS와 지도 작성 완료는 구분해라.
- 기능 추가/수정/삭제, 공통 UI/아키텍처/검증 개선의 영향 Feature는
  같은 기능 단위의 코드·지도·guide·활성 검사 연결에서 갱신해라.

3. 가장 중요한 책임 구분
- 환경: 갱신해야 한다는 정책, 실제 변경에서의 의무 발생,
  미해결 의무 보존/재개, 누락·오래된 근거 탐지, 완료 수락/거절을 소유한다.
  Agent가 규칙을 기억하거나 선택적 검사 명령을 호출하는 데만 의존하지 마라.
- Agent: 요구·변경·영향·숨은 연결을 해석하고 실제 지도/guide/필요한 구현을 수정한다.
  환경이 “갱신이 필요하다”고 전달하면 관련 내용과 기준을 확인해 수행한다.
- 코드/CLI/script: 후보·diff 수집, ID/참조/명령 검사, 기존 규칙의 판정,
  정해진 명령 실행, raw 수집·정형 조회, 파생물 생성은 LLM 없이 수행한다.
  정형 처리를 위해 굳이 Agent에게 계산·복사·결과 판정을 시키지 마라.
- 환경은 현재 의무, 대상 revision, 발생 이유, 필요한 관련 참조와 산출물만
  Agent에게 제공해라. 모든 정책·전체 지도·과거 raw를 매번 context에 넣지 마라.

4. 구현 방식
- 시작할 때 짧은 계획, 실제 사용할 host/설치본/권한 경계/행동 검증 경로를 확인해라.
  명확한 통상 구현 선택으로 설계 전체를 다시 승인받지 마라.
- 기존 Harness/프로젝트 설정/작업 상태, setup·maintain·agent-workflow,
  capture/viewer/native adapter와 source/generated를 우선 재사용해라.
  범용 정책 엔진·새 서비스·별도 중복 장부·절차별 Skill을 먼저 만들지 마라.
- 실제 변경에서 의무를 만들고, 미분류/미연결 변경도 조사 대상으로 남겨라.
  path는 후보이며 업무 의미와 Full 여부를 자동 확정하지 않는다.
- Agent의 수정 후 최신 diff/지도/명령/근거를 재검증해라.
  updated:true, 파일 수정 여부, timestamp만으로 갱신 의무를 해소하지 마라.
  정형 검증과 필요한 의미 검토/행동 근거를 구분해라.
- 의무 해소는 대상 diff와 지도/정책 기준에 연결하고 이후 변경이 무효화한 부분만
  다시 열어라. 동일 의무·조사·실행은 재사용해라.
- 새 의무를 문서와 Skill에 적는 것으로 환경 구현을 대신하지 마라.
  초안 편집·정당한 테스트/기준 수리는 허용하면서 누락 결과의 수락을 막아라.
- 지원 host에서 구현자가 바꿀 수 없는 수락/권한 경계와 실제 연결해라.
  정책·근거 파일과 후보 코드·테스트/자식 프로세스의 권한을 구분해라.
  로컬 hook/wrapper 생략이나 같은 권한의 파일 수정으로 우회되면 강제 보장이 아니다.
  host가 지원하지 않으면 advisory/결정적 검사와 강제 집행을 나누어 보고해라.
- 의미 있는 행동 변경은 집중 RED 후 같은 기준의 GREEN과 가까운 정상 반례를 확인해라.
  행동 보존은 baseline/equivalent GREEN을 사용해라.
  assertion/기준/skip을 완화하거나 성공 출력을 조립하지 마라.

5. 실제 업무 수용 검증
아래 관찰을 서로 구분해 남겨라. 파일/schema/native 통과만으로 Agent 업무 성공이라 하지 마라.

A. 전체 init
- 전체 기능 정답을 알고 있는 작은 fixture에서 UI 외 API/CLI/역할 변형도 누락 없이 지도화.
- 큰 범위를 묶음으로 나누고 중간 context를 바꿔 재개·통합.
- 누락/중복/미조사/도중 기준 변경을 탐지하고 불완전한 init은 완료 거절.
- 독립 Labeler에서도 전체 지도 작성과 기존 자산 재사용을 수행.
  Labeler 제품 기능 고도화는 목표가 아니며 필요한 검증용 변경만 허용한다.

B. 환경 의무와 Agent 수정
- “이 기능을 변경해줘”라는 짧은 요청에 지도 갱신 지시를 덧붙이지 않는다.
- 환경이 의무를 만들고 Agent가 관련 지도를 실제로 고치는지 확인한다.
- 추가/수정/삭제/공통 소비자 변경과 미연결 변경을 포함한다.
- 갱신을 의도적으로 빠뜨린 후보는 수락을 거절하고,
  올바른 Agent 수정 뒤 같은 기준으로 수락되는지 확인한다.
- 단순 오탈자·의미 불변 정상 반례에서 불필요한 전체 조사/Full/내용 날조를 하지 않는다.

C. 정형 처리의 직접 경로와 context
- 참조 검사·이미 정해진 검증 실행·정형 결과 조회를 CLI로 직접 수행하고
  실제 실행 경로에서 모델 호출이 없음을 확인한다.
- 의미 작업만 Agent에게 전달되며 전달 context와 관련 참조를 기록한다.
- context 교체 후 의무가 유지되고 완료된 조사/실행을 중복하지 않는지 확인한다.

D. 집행 경계
- 선택적 명령을 건너뛴 경우, 직접 파일 수정, policy/성공 기록 조작,
  후보 revision 교체, 후보 테스트/자식 프로세스를 통한 우회를 시험한다.
- 권한 있는 기준 수리와 정상 수정은 허용되는지도 확인한다.
- 의미 검토와 정형 검사의 한계, advisory와 강제 집행을 구분한다.
  환경이 막히면 해당 업무는 BLOCKED로 남기고 강제 완료라 하지 않는다.

E. 분포와 위임 성과
- canonical/generated 검사, 임시 설치의 실제 파일 비교,
  설치본을 소비하는 fresh Agent의 짧은 요청 수행을 각각 확인한다.
- 평가 요청에는 Skill 이름/호출 순서/정답 패치를 주지 마라.
  필요한 실제 Agent 위임과 독립 검증을 하되 공통 수정은 한 소유자가 맡아라.
- 같은 요구·대상·fixture에서 기존 방식과 후보의 결함/정상/누락을 대조한다.
  실제 개입·context·모델/도구 호출·중복 실행·시간을 관측 가능한 만큼 기록한다.
  규제 때문에 정상 작업이 더 나빠지면 적용 범위를 고쳐라.
  일부 성공으로 보편적 효율 향상을 주장하지 마라.
