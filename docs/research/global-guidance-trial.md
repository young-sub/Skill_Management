독립 확인은 후보가 수정할 수 없는 controller 측 oracle로 변경된 앱을 실행하고 HTTP 입력 → Domain → SQLite → 새 API/DB 조회를 관찰했다. 작은 변경 세 실행은 각각 15개, 버그 두 실행은 각각 14개, 리팩터링 두 실행은 각각 23개 관찰을 통과했다. 재개는 별도 새 SQLite 연결로 각 값의 건수와 receipt를 대조했다. 이 **부모 확인은 작은 과제에서 에이전트가 스스로 확인을 완결했다는 증거가 아니다.** 모든 실행에서 기존 CSS 변경과 미추적 사용자 메모의 바이트를 보존했다.

사후 원인 확인에서도 모델을 추가 호출하지 않았다. 같은 native sandbox에서 Python `TemporaryDirectory`를 작업 폴더 안으로 옮기는 것만으로는 접근 실패가 해결되지 않았다. 반면 이미 있는 `run_project.py`는 변경된 앱을 실행하여 `/health`의 `service: Inventory`와 기존 필드를 실제로 읽고 서비스도 종료했다. 전체 브라우저 검사는 여전히 EPERM으로 BLOCKED였다. 즉 작은 API 과제의 필요한 관찰은 권한 변경 없이 가능한 경로가 있었지만 후보들이 이를 사용해 완결하지 못했다. 이 후속 확인도 부모의 관찰로 구분한다.

검토한 세 A/B 쌍에서는 코드·요구·사용자 변경·모델/추론·도구·스킬·권한을 동일하게 유지했다. 실제 초기 메시지는 과제 경로와 전역 A/B 본문만 정규화하면 동일했다. 모든 실제 세션에서 해당 전역 원문의 로딩을 확인했다. 부모 대화·개정 이유·비공개 oracle은 과제 프롬프트에 전달하지 않았다. 같은 small-A의 코드/요구/환경/모델이 유효하므로 B2 비교에서 A를 재실행하지 않았다.

불필요한 질문과 별도 계획/계약 문서 생성의 차이는 관찰하지 못했다. 모든 세션에서 설치 Skill 본문을 명시적으로 읽은 호출은 없었으며 이 실행들을 제외하지 않았다. 도구 호출 수는 small A/B1/B2 4/7/8, bug A/B1 8/7, refactor A/B1 5/8, resume B1 합계 16이었다. 재개 중 반복적인 짧은 대기는 토큰 증가에 기여했지만, 단일 표본으로 전역 문구의 원인이라고 판단하지 않는다. 과제 도중 정답 제공·부모 수리는 0회였고 부모의 사후 검증·환경 준비는 별도로 기록했다.

## 예산과 미완료 범위

사용자는 최초 12세션과 개선 최대 6세션, 실행 최대 144분을 승인했다. 누적 입력 150만 또는 출력 8만 도달 시 신규 실행을 중단하며 진행 중 응답은 초과할 수 있다는 조건이었다. 실제로 **초기 8세션 + 개선 1세션 = 9세션**, 모델 실행 총 407.3초를 수행했다. 입력 1,681,977(그중 캐시 1,503,104), 비캐시 입력 178,873, 출력 16,507토큰이다. reasoning 출력 1,741은 출력에 포함되며 다시 더하지 않는다. 실제 금액·크레딧은 unknown이다.

재개 2단계가 시작할 때 입력은 한도 아래였고, 그 진행 중 한도를 넘었다. 이후 새 모델 세션은 실행하지 않았다. A 재개 2세션과 환경·하네스 A/B 2세션은 **NOT_STARTED_USAGE_BUDGET**으로 남았다. 따라서 5종 전체 비교 완료 또는 12세션 완료로 보고하지 않는다. 중단된 B 재개 첫 세션은 삭제하지 않고 9세션에 포함했다. 모델 시간 초과는 없었다. 준비·검사 실패와 모델 결과는 구분했으며 전체 준비 시간은 정밀 측정하지 않아 unknown이다.

## 환경과 운영 권고

Codex CLI 0.160.0, 기존 ChatGPT 인증 테스트 홈, workspace sandbox, approval never, memory/delegation 비활성, 새 app-server thread를 사용했다. 정확한 모델은 `gpt-6-luna`와 `gpt-6.1-sol`, 모두 medium으로 반환됨을 확인했다. 테스트 홈에서 40개 Skill과 agentic-coding 0.1.75의 trusted hook이 발견되었지만, 실제 세션의 hook 문맥 전달은 확인되지 않았다. 운영 홈은 0.1.76과 Ponytail 5.3.2를 포함해 54개 Skill이 발견됐다. 독립 Skill과 플러그인 Skill이 공존했고 확인한 경로에 TDD 중복 설치본은 없었다. 설치본은 변경하지 않았다.

이 차이 때문에 테스트 결과를 운영 홈의 Ponytail 조합에 일반화하지 않는다. 운영 채택 전 필요한 순서는 **추가 예산 확보 → 남은 대조 수행 → 운영 조합과 동일한 격리 조건의 small 확인 → 별도 운영 반영 검토**다. 현재 테스트 홈의 Chromium은 실제 spawn EPERM으로 막혔고, 부모 환경의 브라우저 확인은 통과했다. 사용자에게 막연히 재시도를 요구할 문제가 아니라 호스트 실행 경계의 차이다.

독립/플러그인 Skill 출처 우선순위, 비동기 도구의 진행 상태·결과 회수, 브라우저 capability fallback은 스킬·플러그인 운영 체계에서 다룰 후속 항목이다. 전역에 개별 오류별 금지 조항을 더 붙이지 않는다. pstack은 호출자·소유권 추적, 실행 가능한 관찰 경로, 독립 판정 기준을 필요한 곳에 선택적으로 참고할 것을 권한다. 고정 모델·인원·플레이북이나 새 프레임워크 도입은 이번 근거로 정당화되지 않는다.
