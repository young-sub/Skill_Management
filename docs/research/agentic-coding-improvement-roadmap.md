# Agentic coding 플러그인 고도화 로드맵

작성일: 2026-10-18. 0단계는 [호환성 결과](stage0-compatibility-results.md), 1단계는 [작업별 검증 결과](stage1-task-verification-results.md), 2단계는 [교정·성공 재사용 결과](stage2-feedback-reuse-results.md), 3단계의 UI 발견·비교·실행 가이드 수리와 후속 소비는 [UI·가이드 재사용 결과](stage3-ui-guide-reuse-results.md)에 기록한다. 4단계 이후는 계획이며 이 문서는 설치·벤치마크·후속 구현을 승인하지 않는다.

## 목적과 문서의 역할

많은 업무를 위임해도 무엇을 왜 검증했는지 확인할 수 있고, 사용자 피드백으로 개선한 구조·UI 기준·검증 방법이 다음 업무에 재사용되는 플러그인을 만든다. 검사 수나 문서량 대신 잘못된 완료, 결함 누락, 사용자 개입, 재작업과 중복 실행의 감소를 판단한다.

[현재 설계](agent-coding-system-direction.md)는 목적·책임·완료 조건의 단일 기준이다. 이 문서는 앞으로의 도입 순서와 단계별 채택 기준을 소유한다. [기존 실행 지시서](plugin-continuous-improvement-next-session.md)와 결과 문서는 이전 업무의 재개·증거를 소유한다. 과거 요청의 설치·통합 권한이나 완료 결과를 새 작업으로 이전하지 않는다.

문서 작성 기준은 clean `wp-20261018-global-guidance-trial@3e85fe5b92da7fc6e62597b07a9c257a78af30b9`이다. 구현을 시작할 때 실제 branch·dirty state·활성 작업과 관련 근거를 다시 확인한다.

## 현재 기반과 남은 확인

현재 설계·스킬·공통 실행기에는 다음 능력이 존재한다. 아래는 기존 구현과 기록의 요약이며 이번 로드맵 작업의 실행 결과가 아니다.

| 목표 | 재사용할 기반 | 다음 확인 |
| --- | --- | --- |
| 위임·검증 가시성 | task/context, Feature·검사 이유·raw·현재성·미확인 연결, 읽기 전용 조회 | 자연어 요청에서 적절한 경로를 발견하고 실제 결과를 설명하는가 |
| 업무 규칙·아키텍처 × full stack | 영향 지도, owner 검토, 연결 제품 검증 | 실제 관련 제품 변경에서 FE/API/Domain/저장/재조회가 연결되는가 |
| 피드백·예방 | 원인 분류, owner 수리, 구조·타입·자동 회귀 근거, 후속 계승 | 다른 관련 요청에서도 예방이 유지되고 정상 사용을 막지 않는가 |
| UI 기준 | 가이드와 token/component·소비자 연결 | 다른 화면에서 기준을 발견·재사용하고 시각적 일관성을 유지하는가 |
| 검증 가이드 | 기존 runner/parser, 준비·행동·관찰·정리 연결 | 실행에서 발견한 오류를 고친 가이드가 다음 업무에서도 작동하는가 |
| 검사 유지보수 | 비용·중복 관찰, 검사 제거 시 검출력 보존 기준 | 실제 통합·제거 후보에서 같은 결함 검출과 정상 허용을 유지하는가 |

0.1.76의 도움받은 모델 수리와 무실행 후속 조회는 [기존 native 결과](native-plugin-use-results.md)에 기록돼 있다. 무도움 발견, 일반적인 비용·재작업 감소와 광범위한 무감독 위임의 증거로 확대하지 않는다. 프로젝트 전체 PARTIAL이나 미선언 셀은 관련 없는 작은 업무의 공통 차단 조건이 아니다.

## 목표 검증 체계

| 관점 | FE | BE/API | 비즈니스 로직·Domain |
| --- | --- | --- | --- |
| 업무 요구·규칙 | 사용자 행동·결과·오류 안내 | 권한·입출력 계약·외부 연동 결과 | 계산·정책·상태 전이·데이터 불변 조건 |
| 코드 아키텍처 | 공통 UI 재사용·상태/효과 소유권 | 경계 검증·계층 의존·트랜잭션 책임 | 타입·모듈 경계·규칙의 단일 소유권 |

프로젝트는 전체 지도로 누락을 관리하고, 각 작업은 변경 영향에 해당하는 검사·의미 검토만 선택한다. 해당하지 않는 범위와 미확인을 구분하며 모든 작업에 여섯 선언·검사를 강제하지 않는다. 계층 연결 변경은 입력 → API → Domain → 저장 → 새 조회를 정상·실패 경로에서 확인한다. 계층별 PASS만으로 연결 성공을 대신하지 않는다.

사업 가치·수익성 가설은 별도 요구로 추적한다. 예를 들어 사용자 과업 완료율, 전환, 처리 비용과 관찰 기간·데이터 출처를 정의하고 제품 행동과 연결한다. 소프트웨어 테스트 성공은 사업성의 증명이 아니다. 실제 지표 수집이나 외부 실험은 해당 권한·데이터가 있을 때 수행한다.

결과는 요청 행동·기대 결과 → Feature/영향 → 검사 선택 이유 → 실제 관찰·raw → 현재 유효성 → 미확인·다음 행동으로 설명한다. 기존 조회를 재사용하며 별도 dashboard나 상태 DB를 만들지 않는다.

## 도입 순서

일정 대신 완료 근거로 다음 단계에 진입한다. 0단계에서 평가 기준을 정하고 매 단계 집중 검증을 수행한다. 종합 비교를 뒤에 한다는 이유로 중간 검증을 미루지 않는다.

| 단계 | 도입·고도화 | 산출물과 담당 | 완료 기준 |
| --- | --- | --- | --- |
| 0. 기준·호환성 정리 | 전역 AGENTS와 기존 스킬의 중복·충돌 확인, 평가 기준선 선택 | `agent-workflow`, 계약 스킬, 공통 참조의 역할 정리; 기존 과제·근거 선정 | 작은 수정·조회·진단이 불필요한 setup/계약/실행을 유발하지 않음. 필요한 검증과 권한 경계는 보존 |
| 1. 작업별 검증과 가시성 | feature/bug-fix/refactoring 절차, full-stack 영향 선택, 실행 가능한 가이드 | `agent-workflow`, 검증 setup/maintain, 기존 Feature Map·runner·결과 조회 | 신규 기능은 완료·실패 사례, 버그는 재현·수리·회귀, 리팩터링은 동작 보존을 관찰. 무엇을 왜 확인했는지 사용자에게 설명 |
| 2. 피드백·구조적 예방과 성공 절차 재사용 | correct 방식 통합, reflect 방식의 교훈 반영, automate-me 방식의 성공 절차 추출 | `diagnose`, 기존 feedback/prevention, 원인 소유 코드 및 작은 피드백/절차화 스킬(가칭 `reflect`); 기존 스킬 작성 도구 재사용 | 원래 실패·우회 차단과 정상 허용 확인. 후속 업무가 예방을 계승하고, 새 문맥에서 짧은 요청·필수 자료만으로 만족한 결과를 재현. 기록·스킬 생성만으로 완료하지 않음 |
| 3. UI·검증 가이드의 재사용 | 스타일 기준 보완, visual-parity, 실행 기반 가이드 갱신 | `impeccable`·접근성·React, 검증 setup/maintain | 다른 관련 화면/작업이 기준을 발견·재사용. 가이드 오류 수리 후 실제 실행 성공. 시각·키보드·상태별 결과 확인 |
| 4. 설계 능력 보강 | architect 도입, blast-radius 공통 절차 | 독립 `architect`; 설계·검토 공통 참조 | 실제 복잡한 변경에서 호출자·타입·데이터 소유권·모듈 경계를 정하고 구현·회귀로 확인. 작은 변경에는 설계 의식 강제 없음 |
| 5. 효과 평가와 정리 | eval, benchmark-checklist, 필요할 때 perf-issue/hillclimb | 기존 평가 도구와 `maintain-project-verification` | 동일 조건 비교로 채택·수정·보류 결정. 검사 통합/제거 시 기존 결함 검출과 정상 허용 보존. 미입증 후보는 유지 |
| 6. 병렬 위임 확대 | swarm, 중단·재개 절차 고도화, 필요 시 CI/전달 절차 | 독립 `swarm`, 기존 task/context·실행 흐름; `multi-agent-review`는 독립 검토 | 분리된 업무가 통합 뒤에도 통과하고 충돌·중복 효과·중단 후 누락을 방지. 순차 수행 대비 개입·재작업·비용을 비교 |

2·3단계는 1단계 기반 위에서 독립 범위로 병행할 수 있다. 4단계 설계 판단은 앞선 작업의 실제 복잡성이 요구하면 먼저 적용하되 독립 스킬 배포는 검증 후 결정한다. 6단계의 대량 위임 확대는 앞선 검증·예방·재사용의 근거를 전제로 한다. 이 순서는 기존에 허용된 유용한 병렬 작업을 금지하지 않는다.

## 2단계 추가 결정: 인간의 교정과 성공 경험을 재사용하기

2026-10-18 사용자 결정. 목표는 인간이 잘못된 방향을 교정한 뒤 같은 개입을 반복하지 않고, 만족한 턴이나 최종 결과물을 다음에는 긴 배경 설명 없이 재현하는 것이다. 개인 취향 기억에 한정하지 않는다. 아래 범위의 구현과 제한된 검증은 [2단계 결과](stage2-feedback-reuse-results.md)에 기록하며 일반 효과·무도움 발견은 별도 미확인이다.

| 입력 | 반영 경로 |
| --- | --- |
| “그 방향은 아니야”, 실패·불편에 대한 피드백 | 기대 행동과 실제 원인을 구분하고 기존 `diagnose`·feedback으로 소유자를 수리한다. 구조→타입/제약→자동 검사→필요한 문서 순으로 재발을 막는다. 명확한 첫 교정도 반영하며 두 번째 실수를 기다리지 않는다. |
| “이번 판단/방식은 좋았어” | 무엇이 어떤 조건에서 좋았는지 확인한다. 오래 유효하고 다음 판단을 바꾸는 교훈만 기존 스킬·프로젝트 가이드에 반영한다. 단순 칭찬이나 우연한 성공을 보편 규칙으로 확대하지 않는다. |
| “이 결과/방식으로 다음에도 해줘”, “절차로 남겨줘” | 해당 턴·결과물의 성공 절차를 재사용 가능한 스킬·가이드·템플릿으로 추출한다. 명시적인 재사용 요청은 한 사례로도 시작할 수 있으며, 일반적인 개인 취향으로 추정하지 않는다. |
| “이번만 이렇게 해줘” | 현재 작업의 예외로 남긴다. 지속 규칙으로 승격하지 않는다. |

반영 위치는 실제 소유권으로 정한다. 제품 결함은 코드·검사, 프로젝트 고유 규칙은 프로젝트 문서, 공통 작업 판단은 기존 스킬, 반복 호출할 독립 절차는 신규 스킬이 맡는다. 스킬이 있는데 호출되지 않았다면 발견·설명·라우팅을 고치고 같은 규칙을 중복 추가하지 않는다. 기존에 맞는 소유자가 없을 때만 새 스킬을 만든다. 피드백 분류·반영 진입점은 작게 두고 기존 작성 도구에 연결하며 별도 학습 DB·범용 runner는 만들지 않는다.

성공 절차에는 다음 실행에 필요한 정보만 남긴다: 호출 조건·짧은 요청 예시, 필수 입력·최소 질문, 준비 조건·기존 도구·작업 순서, 결과물 형식·템플릿·좋은 예시, 완료·검증 기준, 적용 범위·예외·실패 시 대응. 당시 값·파일명은 입력으로 바꾸고 중요한 판단 기준은 보존한다. 원본 대화 전체·비밀·불필요한 시행착오는 복사하지 않는다. 결과물만으로 실제 제작 절차를 알 수 없으면 추측을 사실로 쓰지 않고 필요한 자료나 최소 확인을 요구한다.

소비 검증은 실행 전에 판정을 정한다. 교정 사례는 같은 실패·우회가 막히고 가까운 정상 사용이 유지되는지, 성공 절차는 이전 대화나 정답 패치를 주지 않은 새 문맥에서 짧은 요청·필수 자료만으로 결과 기준을 만족하는지 확인한다. 발견 여부, 추가 인간 개입, 실패·재시도·미실행을 남기고 도움받은 소비와 무도움 발견을 구분한다. 한 사례를 모든 재발 방지의 보증으로 확대하지 않는다.

조사한 pstack의 [correct](https://github.com/cursor/plugins/blob/main/pstack/skills/correct/SKILL.md), [reflect](https://github.com/cursor/plugins/blob/main/pstack/skills/reflect/SKILL.md)와 [채택 기준](https://github.com/cursor/plugins/blob/main/pstack/skills/reflect/references/synthesizer.md), [automate-me](https://github.com/cursor/plugins/blob/main/pstack/skills/automate-me/SKILL.md)를 선택적으로 참고한다. 이는 이번 대화에서 읽은 공개 `main` 소스이며 앞선 고정 리비전 조사와 구분한다. 실제 이식 때 사용할 리비전을 고정한다. automate-me의 개인 mode 전체를 복제하지 않고 성공 절차 추출·기존 스킬 우선·짧은 호출 방식을 적용한다. 고정 리뷰어 수·모델, 일률적인 재승인·PR, 외부 backlog 자동 등록은 가져오지 않는다. 기존 승인 범위 안에서 수정하되 설치본·전역 설정·외부 게시 권한은 별개다.

## 전역 AGENTS와의 호환 규칙

- 전역 AGENTS는 권한·자율 수행·검증 원칙, 스킬은 작업별 판단·절차, 프로젝트는 업무 규칙·명령·UI 기준을 소유한다. 이번 로드맵은 전역 파일을 다시 개정하지 않는다.
- `agent-workflow`는 요청과 필요한 능력을 연결한다. 모든 요청에 상태 생성·플레이북 기록·계약을 요구하지 않는다.
- `design-goal` → `execute-codex-goal` → `close-goal`은 지속 계약이 유용하거나 요청된 작업에만 적용하고 기존 승인·증거를 이어받는다.
- `swarm`의 위임 정보는 목적, 허용 범위/파일 소유권, 의존성, 완료 조건, 요구 증거, 검토·통합 책임이다. 기존 task/context와 필요한 brief를 쓰고 별도 상태 시스템을 만들지 않는다.
- 독립 리뷰와 병렬 구현을 구분한다. 인원·모델은 업무·호스트·사용자 선택에 맞추며 리뷰어 수로 결론을 결정하지 않는다.
- 실행·준비·조회·재개를 구분한다. 읽기 전용 요청은 제품 명령 0회, 미확인 launch는 중복 실행하지 않는다. 오래된 PASS를 현재 성공으로 표시하지 않는다.
- 신규 의무는 막으려는 실패와 유지 비용을 설명할 수 있어야 한다. 권한·데이터 보호·필수 검증을 효율 개선 명목으로 약화하지 않는다.

## 평가와 채택 기준

기존 도구·과제를 우선 사용한다. 새 기준선 실행은 결과가 채택 결정을 바꾸거나 기존 조건이 유효하지 않을 때 수행한다. 유료 호출·외부 자원·설치·신뢰 변경은 별도 승인 범위이며 이 문서만으로 시작하지 않는다.

| 대표 과제 | 확인할 실제 행동 |
| --- | --- |
| 신규 full-stack 기능 | 자연어 요구에서 기준 발견, 정상/실패 동작, 저장 후 재조회, 미검증 설명 |
| 사용자 버그와 후속 요청 | 원인 추적·공통 owner 수리, 실패/우회/정상 근거, 다음 요청의 예방 재사용 |
| 인간의 방향 교정과 후속 요청 | 기존 스킬 누락·미호출·일회성 예외를 구분하고 적절한 소유자에 반영; 같은 교정을 반복하지 않으면서 정상 작업 허용 |
| 만족한 결과의 절차화와 새 문맥 실행 | 호출 조건·필수 입력·결과 기준을 가진 절차를 추출; 이전 대화 없이 짧은 요청·자료만으로 재현, 부족한 맥락과 개입 기록 |
| 동작 보존 리팩터링 | 호출자·계약 유지, 관련 회귀, 불필요한 전체 검사 방지 |
| 공통 UI 변경과 다른 화면 변경 | 가이드·token/component 발견, 실제 화면·접근성, 후속 재사용 |
| 검증 가이드 오류와 검사 통합 | 제품/관측기 오류 구분, 가이드 재실행, 동일 결함 검출과 정상 허용 |
| 조회·중단·병렬 통합 | 조회 무실행, 중복 효과 방지, 유효 증거 보존, 통합 후 동작 |

비교는 과제·요구·평가기·코드/패키지·환경·모델/추론 설정을 고정하고 변경한 요인을 명시한다. 실패·시간초과·재시도·스킬 미사용도 분모에 남긴다. 도움받은 실행과 무도움 발견, fixture/package/product/native-host 결과를 분리한다. 비용·사용량을 수집하지 못하면 unknown이며 평가기 출력 없이 성공률을 추정하지 않는다.

우선 지표는 잘못된 완료·결함 누락·정상 사용 차단, 다음은 사용자 개입·재작업·중복 실행·시간·비용이다. 과제별 합격 조건은 실행 전에 정한다. 안전성·검출력 회귀가 있으면 기본값으로 승격하지 않는다. 효율 개선이 관찰되지 않으면 개선됐다고 주장하지 않고 유지 비용에 따라 수정·보류한다. 한 사례의 성공을 일반 효과로 확대하지 않는다.

검사 삭제는 같은 실패의 검출과 가까운 정상 사례의 허용을 남은 장치로 증명하거나, 승인된 요구 폐기로 정당화한다. 비용·개수·커버리지 수치만으로 삭제하지 않는다. 후보가 없으면 없는 이유를 남기고 삭제 실적을 만들지 않는다. 자동 수집·자가개선은 무조건 규칙을 추가하는 기능이 아니라 관찰→원인 수리→검증→후속 재사용→유지/폐기의 과정이다.

## 구현 단위와 다음 착수 범위

0·1·2·3단계의 구현과 한계는 위 결과 문서에 보존한다. 2단계는 `wp-20261018-stage0-compatibility`에서 1단계 `0e126428e3bd14d6f1768a9dfb6cce06b0e12b80`과 추가 결정 `5e8de29`를 이어 구현했다. 3단계는 같은 브랜치의 2단계 `02a354d`에서 시작해 기존 스킬 연결과 fixture 관측기·가이드를 수리하고 새 문맥 소비를 확인했다. 4단계 이후는 별도 착수 범위이며 이번 구현에 포함하지 않았다. 후속 시작 시 실제 HEAD·dirty state를 재확인하고 사용자 변경·활성 작업·기존 증거를 보존한다. 별도 `20261018-plugin-readiness` 계약을 이 단계의 계약으로 간주하거나 완료 처리하지 않는다. 검증된 기존 능력과 경량 수정·조회·진단 경로를 유지하고 새 Router·범용 runner·상태 DB·dashboard·전수 검사 체계를 만들지 않는다.

각 구현 단위는 원본 스킬/참조 → 필요한 runtime 수정 → 관련 회귀·실제 소비 → Feature Map·현재 문서 → 생성 리소스·패키지 검증 순서로 마무리한다. `authoring/resource-map.json`의 원본/생성 관계를 따르고 이미 있는 TaskStore, 공개 API, 증거 결속·현재성 보호는 재현된 문제가 있을 때만 수정한다. 변경 영향에 맞는 검사를 실행하며 Full은 실제 영향이나 명시 요청으로 선택한다.

새 스킬 배포 시 catalog·리소스 매핑·자가완결성·발견/라우팅을 함께 확인한다. 검증된 단위는 저장소 Git 정책에 따라 커밋한다. 설치본 갱신, protected branch 통합, push·배포·전역 설정 변경은 이 로드맵의 범위가 아니다.

로드맵 자체를 구현 증거로 취급하지 않는다. 실제 구현은 해당 Feature 행과 검증 연결을 같은 단위에서 갱신한다. 로드맵의 단계 상태는 실제 결과 링크가 생길 때만 변경하고 원본 로그·진행 장부는 `.work/`에 보존한다.
