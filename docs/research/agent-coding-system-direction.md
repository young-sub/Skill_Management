# Agent 업무 위임·검증·지속 개선 설계

이 문서가 현재 설계의 단일 기준이다. 버전별 실행과 한계는 [후속 소비와 검사 통합](workflow-followup-results.md), [0.1.69 개선 결과](workflow-improvement-results.md), [0.1.68 hardening](core-hardening-results.md), [이전 구현 기록](agent-workflow-implementation-results.md), [아카이브](archive/index.md)가 소유한다. 과거 지시와 PASS를 새 작업의 지시·결과로 재사용하지 않는다. 다음 작업은 [실행 지시서](plugin-continuous-improvement-next-session.md)를 따른다.

## 목적과 실제 완료 조건

이 플러그인의 제품 사용 환경은 Codex·Claude Code 같은 agentic coding 도구다. 패키지 CLI 검증에 더해 해당 도구에서 플러그인 식별, Skill 발견·호출, 필요한 hook 전달과 실제 업무 소비를 확인한다. Native 사용 검증을 선택적인 보호 검증기 수락과 묶어 미루지 않는다. 등록·입력 전달만 확인한 실행은 모델의 업무 수행 성공으로 보고하지 않는다.

사용자가 무엇을 왜 검사했는지, 끝난 것과 미확인을 이해하고 다음 관련 업무에서도 개선을 재사용할 수 있어야 한다. 문서·필드·검사·PASS 수가 아니라 잘못된 완료, 결함 누락, 불필요한 차단, 사용자 개입, 재작업과 중복 실행이 줄었는지 판단한다. 비교 조건과 관찰이 없으면 일반 효과·비용 절감을 주장하지 않는다.

| 목표 | 실제 완료 조건 |
| --- | --- |
| 1. 위임과 검증 가시성 | 요청 결과 → 검사와 이유 → 실제 관찰 → 현재 유효성 → 미확인·다음 행동을 연결한다. 현재 요청과 프로젝트 잔여를 분리한다. |
| 2. 업무 규칙과 아키텍처 | 사업 가치 가설과 소프트웨어 규칙을 구분한다. 변경된 호출·상태·데이터 소유자와 관련 FE/API/Domain 동작을 확인한다. 연결 변경은 입력 → API → Domain → 저장 → 새 조회로 검증한다. |
| 3. 피드백과 예방 | 불편을 재현하고 실제 흐름·원인·소유자를 고친다. 구조 → 타입/제약 → 자동 검사 → 최소 문서 순서로 선택한다. 원래 실패·우회 차단과 가까운 정상 허용을 확인하고 다음 업무가 예방을 적용한다. |
| 4. UI 기준 재사용 | 가이드는 의도·상태·행동과 실제 token/component를 연결한다. 값과 동작은 코드가 소유한다. 공유 기준 변경 후 다른 관련 작업에서 발견·재사용을 확인한다. |
| 5. 실행 가능한 검증 가이드 | 기존 runner/parser로 준비·실제 행동·관찰·정리를 실행한다. 실행 중 발견한 오류를 해당 owner의 코드·명령·가이드에 반영하고 다음 업무에서 사용한다. |
| 6. 검사·절차 유지보수 | 검사가 막는 실패와 비용을 설명한다. 같은 결함 검출·정상 허용 근거로 중복 통합 또는 폐기 요구 제거를 판단한다. 제거 후보가 없으면 이유를 남긴다. |

### 상황별 실행·관찰 연결

아래는 필요할 때 선택하는 기준이며 모든 adapter를 선제 구현하는 목록이 아니다.
공통 플러그인은 발견·선택·capture·현재성을, 프로젝트는 조작·기대 결과·판정을 소유한다.
기존 CLI/runner를 우선하고 필요한 도구가 없을 때 구체적인 연결/설치 요구를 제시한다.

| 상황 | 실제 조작과 관찰 | 필요한 반례/경계 |
| --- | --- | --- |
| FE | 브라우저 입력·탐색·키보드, screenshot/DOM/network, 저장 후 reload | 전송값·화면 상태 오류. 시각 결과는 Agent가 실제로 열어 확인. |
| API/Domain/저장 | 실제 HTTP 호출, 정책·권한·전이, 저장값과 독립 fresh read | 거부 요청 무변경, 규칙 우회. 중복/동시성은 관련 변경에서 선택. |
| 비동기 job | 실제 제출→worker→완료 상태와 결과 조회 | 재시도·중복·timeout. 고정 sleep 대신 상태와 제한 시간. |
| 외부 연동 | 승인된 sandbox 요청/callback과 내부 상태 대조 | mock·sandbox·운영 구분. 실제 결제/메일/외부 쓰기 권한 별도. |
| CLI/파일/문서 | 명령 실행, 생성물 재열기·파싱·렌더링 | 종료 코드뿐 아니라 내용·오류·부작용 확인. |

업무 규칙(취소 후 권한 회수)은 자동 검사와 의미 검토로 확인한다. 사업 가치(문의 감소)는
기존 분석 자료의 지표·기간·비교 조건·관찰 한계를 연결한다. 계측이 없으면 미측정으로 남기며
새 analytics 시스템을 자동 도입하지 않는다. 업무/아키텍처 × FE/API/Domain은 영향 지도이고
매 작업의 여섯 칸 의무 검사가 아니다.

### 평가와 제외 범위

효과는 사전에 고정한 결함의 검출/누락, 정상 사례 오탐, 사용자 개입·재작업, 실행 시간과
수집 가능한 비용으로 판단한다. 실패·중단·미실행을 분모에 보존하고 미수집 비용은 unknown이다.
같은 조건의 비교가 없으면 일반 개선율을 주장하지 않는다. 검사 이름·개수나
RESOLVED/CURRENT만으로 행동 성공을 판정하지 않는다.

새 범용 runner/parser, 능력 DB, dashboard, 고정 다중 Agent 절차, 전체 계층 강제 검사,
자동 피드백 수집은 추가하지 않는다. 검사 제거는 V5의 근거가 있는 범위에서만 수행한다.
권한 확대·설치본 갱신·보호 main 통합·push/publish는 이 문서로 승인되지 않는다.
이번 문서 정합성 수정과 V1–V6의 코드·제품 동작 완료는 별개다.

| 유효한 검사만 유지 | 결함 검출·정상 허용 근거로 중복 실행 통합/요구 폐기 판단 | 이번 작업에서 추가 검사 삭제를 정당화하는 근거는 없음 |

이번 패키지 회귀는 저장소 없는 실행·hook 명령·결과 소비와 배포 내부 안내 링크/해시를 확인한다. 별도 required connected-product 검증은 실제 Chromium/API/Domain/SQLite 재조회와 FE 전송 오류 검출을 확인했다. 이는 테스트 제품의 실행 근거이며 상용 제품이나 무도움 모델 완료의 증거가 아니다. 이번 원본 출력은 `.work/plugin-readiness-20261018/`에 보존한다. 과거 실제 제품·native 소비 범위는 [기존 사용 결과](native-plugin-use-results.md)에 남긴다.

여섯 관점의 집중 회귀 12건과 required 브라우저 회귀 2건은 통과했다. 넓게 묶은 기존 회귀는 300초 제한으로 중단되어 전체 통과로 집계하지 않는다. 패키지 선택 검사는 빌드·배포 외부 실행·업데이트 보호를 함께 확인한다. Full 실행과 새로운 모델 비교 실험은 하지 않았다.

이후 사용자 승인으로 현재 Orca 홈에 0.1.76을 등록하고 해당 hook을 신뢰했다. 실제 모델의 격리 제품 수리 1회는 브라우저 RED 5개 실패 → GREEN 14/14 통과와 피드백 RESOLVED를 남겼다. 후속 조회 1회는 제품 명령 0회·파일 해시 불변을 확인했고, READY_FOR_REVIEW와 최종 수용을 구분했다. 기존 설정을 보존했으며 Windows 계정·ACL·방화벽은 변경하지 않았다. 자세한 범위·사용량·제약은 [이번 native 결과](native-plugin-use-results.md#authorized-0176-installation-and-two-native-tasks--2026-10-18)에 기록한다.

따라서 **실제 모델이 소비할 수 있는 플러그인은 제공되지만, 모든 업무를 무감독 위임할 만큼 완전히 검증됐다고 평가하지 않는다.** 이번 실행은 플러그인 호출과 검사 명령을 제공한 fixture 검증이다. 무도움 발견, 운영 제품, 다른 UI 변경에서의 가이드 재사용, 검사 삭제의 효과와 일반적인 비용/재작업 감소는 미검증이다. 사용자 요청에 따라 이 항목에서 멈추며 전체 readiness 계약은 완료 처리하지 않는다.

수정의 새 문맥 소비와 같은 조건의 결함/정상 대조를 기록한다. 예전 description
대조군의 스킬 미사용을 남기며, catalog 소비·소스 검토·실제 제품 fixture 실행을
구분한다. 재현된 제품 저장/Git 전달 대상 오인을 검토 스킬에서, 이전 답 노출을

이것은 readiness 계약 완료나 일반 비용 절감의 증거가 아니다.

일반 속도·비용 개선이나 readiness 계약 완료로 확대하지 않는다.

## 하나의 사용자 흐름

[4단계 결과](stage4-architecture-results.md)는 독립 `architect`의 기술 설계와
`design-goal`의 작업 계약 책임을 구분한다. 공통 영향 분석은 호출자·타입·상태·
데이터 소유권·모듈 경계에서 구현과 회귀를 선택하며 작은 수정에 설계 문서나
계약을 요구하지 않는다. 격리 소비 결과는 위 readiness/native 판정과 별개다.

이후 [3단계 결과](stage3-ui-guide-reuse-results.md)는 기존 UI 스킬 발견 연결,
의도한 차이와 훼손의 시각 비교, fixture 관측기·가이드 수리와 별도 문맥의
History 화면 소비를 확인했다. 제공된 catalog/격리 프로젝트의 한 사례이며
위 native/readiness 판정을 갱신하거나 일반적인 무도움 발견을 입증하지 않는다.

요청 이해 → 기존 기준·코드·가이드 발견 → 필요한 수정·검증 선택 → 실행 → 결과 설명 → 다음 관련 업무에서 재사용.

- `agent-workflow`가 단일 진입점이다. 작은 명확한 수정은 기존 개발 흐름으로 직접 처리한다. 새 Router·DB·dashboard·고정 다중 Agent 절차를 만들지 않는다.
- 전체 검증 연결을 요청하면 setup이 합의한 기능 지도를 조사한다. 작은 업무의 빠진 연결을 보완할 때는 그 경로만 연결한다. 전체 조사 PARTIAL은 독립 업무의 공통 차단 조건이 아니다.
- 기존 task/context를 사용한다. `prepare`는 선택, `execute`는 효과, `lookup`/task `resume`은 읽기 전용이다. 진행 중 캡처는 같은 소유 프로세스·경로에서 기다리고 미확인 launch는 재실행하지 않는다.
- 업무 규칙/아키텍처 × FE/API/Domain은 영향 판단의 지도다. 모든 작은 업무에 여섯 선언·여섯 검사·전수 조사를 요구하지 않는다. 알려진 요구와 실제 영향은 생략하지 않는다. 미선언 범위는 전체 검증으로 승격하지 않는다.
- 결과는 검사 이름만 나열하지 않는다. 요청 행동·기대 결과, 선택 이유, 관찰·근거 위치, 미실행/실패/환경 제약과 다음 행동을 연결한다. 의미 검토와 실행 결과를 구분한다.

## 책임과 보호 경계

| 소유자 | 책임 |
| --- | --- |
| Agent | 요청·영향·원인·검사 가치·시각 결과의 의미 판단, 필요한 검증 선택과 근거 읽기. |
| 공통 workflow/runtime | 기존 task, 발견·연결, 상태 충돌, 실행·캡처, 근거 결합·현재성. 파일 존재나 제출한 RESOLVED는 행동 증거가 아니다. |
| 프로젝트 | 업무 규칙, Feature Map, UI token/component, 실행 가이드, 실제 runner/parser·assertion·서비스·정리. 제품 오류와 공통 연결 오류를 각각의 owner에서 고친다. |
| 지원 host | Codex·Claude Code의 플러그인 식별·Skill 발견/호출·hook 전달을 소유한다. 실제 모델 업무 소비, 로컬 package CLI, 선택적인 보호 수락은 각각 다른 증거다. 설치·신뢰 권한은 해당 호스트 경계를 따른다. |

TaskStore/공개 API, 절대 `--state` 정규화, 필수 검사 누락 차단, 읽기 전용 조회와 atomic capture는 구현된 보호다. 새 재현 없이 다시 만들지 않는다. 상태 유실·오래된 갱신·중복 효과·필수 미실행 성공 방지를 유지한다. 설치본·전역 설정·제품 원본·자격증명은 별도 권한 경계다.

## 피드백·가이드·재사용

제품 결함, 요구 변경, 의도된 차이, 검사 오류, 환경 제약을 구분한다. 실제 호출과 상태/데이터 흐름을 따라 소유자를 수정한다. 자동 회귀는 고정 기준의 실패/수리/정상 근거를 사용한다. 구조·타입/제약 예방은 해당 수단의 실제 경로·우회·정상 사용 증거를 사용하며 동일한 등록 검사/RED-GREEN 형식을 강제하지 않는다. 어떤 방식이든 변경된 소유자·현재 근거·후속 재사용이 필요하다. 규칙 추가나 상태 제출만으로 해결하지 않는다.

UI guide·검증 guide·Feature Map은 기존 프로젝트 진입점에서 발견할 수 있어야 한다. 의도, 사용자 행동, 기대 결과, 실행법, 실패 진단, 소유 자원 정리와 보존 근거를 설명한다. 명령·값·기준을 여러 문서에 복제하지 않는다. 실제 실행으로 가이드를 고치고 다른 관련 업무에서 재사용한다.

## 검증과 남은 경계

실제 문제 재현 → 소유 코드 수정 → 집중 회귀 → 격리 프로젝트의 작은 기능/피드백/후속 재사용 → 고정 패키지 순서다. 기존 실행기와 과거 raw를 재사용하되 이번 결과와 구분한다. Full은 실제 영향상 필요한 시점에 실행하고 새 변경·실패 없이 반복하지 않는다. [Testing](../testing.md)이 상세 정책·명령을 소유한다.

새 문맥 Agent는 발견·재사용이 불확실할 때만 사용한다. 정답 패치·token명·CLI 순서를 준 소비는 도움받은 결과다. 모델/추론/사용량/비용 미수집값은 unknown이다. 벤치마크는 채택 결정을 바꿀 때만 실행한다.

fixture, package CLI, 실제 프로젝트, native 발견/hook, 보호 host, 사업 성과는 별도 증거다. 필요한 경계가 미확인이면 그대로 남기고 전체 플러그인 완성으로 보고하지 않는다. 관련 없는 host 미검증은 독립 업무의 공통 차단 사유가 아니다.

pstack의 호출부/소유권 중심 설계, 구조 우선 예방, 실제 사용자 흐름 실행·갱신을 선택적으로 참고한다. 후속 검토 리비전 `101b274dd991f694e1f7024be2157e5f3adf07de` (0.15.25, MIT, Lauren Tan)는 [실전 비교](pstack-practical-comparison.md)가 소유한다. 앞선 [고정 조사](pstack-analysis.md)는 `23e4138daa01c42d4969f7a5465f82704e64f798` / 0.15.6의 별도 기록이다. 프로토타입은 제품 효과의 증거가 아니다. 원문 재배포 시 출처·리비전·현지 변경·MIT 고지를 보존한다.

0~6단계(4A 포함)의 구현을 마친 도입 계획과 단계별 완료 기준은 [보관된 고도화 로드맵](archive/agentic-coding-improvement-roadmap.md)에 있다. 이는 현재 작업 목록이 아니며 단계별 결과의 검증 범위와 미입증 효과는 유지한다. 기존 pstack 적용 판단과 실행 근거는 [실전 비교 기록](pstack-practical-comparison.md)에 보존한다. 공개 조회는 bundle과 개별 plan 모두 이미 결속한 미추적 파일 내용을 재측정한다. 동일 코드 bytes라는 이유만으로 Git·실행 조건의 변화를 무시하지 않는다.
