현재 source runtime은 **0.1.66 로컬 전달 / 2026-10-17**이다. 0.1.62의 task 우선 summary·호출 내부 읽기 공유·환경 복구와 공식 평가기 연결은 [10월 15일 구현 기록](agent-workflow-implementation-results.md#handoff-runtime-2026-10-15)이 소유한다. 당시 Docker 보류와 평가 미수행은 그 회차의 역사적 상태다. 이후 [10월 16일 실제 평가](luna-benchmark-execution.md)에서 전용 WSL/Docker, 공식 대조 24개, pilot 9회·main 108회와 별도 후속 18회를 실행했다. 공개 과제 해결률 이득은 없었고 인수·재사용은 혼합/부정적 결과였으며 전체 금전 비용은 unknown이다. 격리 native 발견·hook·본문 읽기 관찰과 전역 설치 갱신·보호 host 수락·실제품 전 범위 인수는 서로 다르다. §12는 당시 평가 합의, §13은 지속 목표다.

**목적은 플러그인 고도화이며 연두링크는 실제 사용 평가 대상이다.** 연두링크 화면만 개선하고 종료하지 않는다. 기존 [연두링크 평가](plugin-improvement-next-session.md)와 [지속 고도화 요청](plugin-continuous-improvement-next-session.md)은 수행 범위를 보존한다. 다음 개선 선정은 현재 근거와 §10을 따른다. 과거 `agent-workflow-next-session.md`와 `agent-coding-next-session.md`의 실행 블록도 이미 수행된 범위의 기록이다.

0.1.46 검토의 D1–D3는 기존 결정·hook 소유 코드에서 수리했고 task 조회 요약과 raw 발견 경로를 연결했다. [후속 실제 결과](agent-workflow-implementation-results.md#d1d3-consumption-2026-10-09)가 검증·패키지 소비·독립 새 문맥 평가와 남은 한계를 소유한다. 기존 task/context, 6셀 scope, 실제 runner, feedback/prevention, UI guide와 maintenance를 재사용한다.

[0.1.46 보완 검토](agent-workflow-refinement-review.md#post-0146-review)는 당시의 분류 왕복·새 기준 누락·task/project 공백 혼동을 재현한 기록이다. 이 반례나 과거 실행 블록을 다음 구현 목록으로 다시 실행하지 않는다. 새로운 우선순위는 현재 남은 소비 공백과 아직 확인하지 못한 업무 경험에서 정한다.

Agent는 요구·원인·시각·검사 가치의 의미 판단을, CLI는 상태·실행·근거 결합을, 프로젝트는 정답·runner·코드·UI 기준을 소유한다. 우회 불가 권한/수락이 필요한 경우에만 지원 host 경계를 별도로 검증한다. 로컬 기록의 정합성과 보호된 수락은 같은 보장이 아니다.

현재 실행·권한·Git 정책은 [Agent workflow](../agents/workflow.md), 명령과 검증은 [Testing](../testing.md)을 따른다. 과거 G1–G6/T1–T6와 U1–U7 설계는 기존 범위와 책임을 설명하는 근거이며 일괄 재구현할 목록이 아니다. 과거 문서의 미래형 지시나 승인 기록이 새 작업 권한을 만들지 않는다.

Flask의 최초 90초 timeout은 기존 frozen cgroup 환경 원인이며, 이번 컨테이너의
실행 위치만 바꾼 제한된 재시도와 원래 freezer·후보 보존을 별도로 기록했다.
관련 제품 코드·설치·전역 설정은 변경하지 않았다. 비용 전체와 부모 사용량은
unknown이고, 이전 28.97배 관찰의 인과 해석이나 새 대규모 A/B는 추가하지 않는다.

## 1. 목표와 논의 과정

2026-10-07 현재 구현은 요청 context → 기존 task → prepare/execute → lookup을 연결하고, 독립 시험 프로젝트의 실제 Chromium·API·Domain·SQLite·재시작 조회와 피드백/UI 수리·검사 통합·후속 재사용까지 확인했다. 세부 성숙도와 고정 pstack 비교는 [현재 구현 결과](agent-workflow-implementation-results.md#connected-actual-product-use-2026-10-07)를 따른다. 이는 설치 갱신, 일반 Agent 업무 효과, 보호 호스트 수락의 확인을 뜻하지 않는다.

목표는 Agent에게 많은 업무를 위임하면서 **무엇을 검증했고, 어떤 결과를 신뢰할 수 있으며, 발견한 불편이 어떻게 재발 방지로 이어졌는지** 확인하는 것이다. 최상위 판단은 실제 업무의 효율·효과·정확성과 사용자 개입/재작업 감소다. `Confidence / Verification Cost`는 실제 결함 검출력과 실행·유지 비용을 함께 판단하는 기준이다. 테스트 수·coverage·Skill 수·차단 횟수를 목표로 삼지 않는다. 새 제약의 결함 검출 이득과 정상 과업 오탐·비용을 비교해 이득 없는 제약은 축소/제거하되 기존 권한 경계를 완화하지 않는다.

우선 기능은 (1) 위임 업무의 검증 가시성, (2) 비즈니스 모델·아키텍처 및 FE/BE/Domain 검증, (3) 피드백과 자가 개선, (4) UI/UX 기준 고도화, (5) 검증 기준 고도화, (6) 원인 추적·실질적 가드레일·불필요한 검증 제거다.

기존 인수는 공통 작업 상태 수리 → 범용 프로젝트 연결 → 업무 흐름 시험 → 독립 검증·패키지 고정 → 격리 제품 인수 → 공통 결함 수리 순서로 진행했다. 새 고도화도 제품별 정답을 공통 기능에 먼저 주입하지 않고 범용 반례부터 확인한다. 연두라벨의 가격·인쇄·Cloudflare 구조를 공통 기능의 설계 기준이나 하드코딩으로 삼지 않는다. 연두라벨에 맞춰 연결을 미리 수작업한 뒤 범용 setup의 성공으로 보고하지 않는다.

새 프로젝트의 기존 명령·기준·실행기를 조사하고 실제 연결하는 능력까지 플러그인의 기능이다. 프로젝트별 지도·가이드·최소 adapter는 이 능력을 사용한 결과물이며 해당 프로젝트가 소유한다. 범용성은 공통 작업 절차와 프로젝트별 실행·정답의 분리로 평가하고, 무설정으로 모든 기술 스택을 지원한다고 주장하지 않는다. 실제 사용할 수 있는 실행·관찰 수단과 미지원 범위를 명시한다.

자가 개선은 관찰한 문제의 원인 소유 위치를 고치고 후속 요청에서 개선을 소비하는 흐름이다. 제품 결함은 프로젝트 코드, 연결 결함은 프로젝트 명령·가이드·adapter, 공통 결함은 플러그인 canonical 소스·기존 절차에서 수리한다. 공통 수정은 원래 실패와 다른 프로젝트의 정상 사례로 검증하고 새 패키지로 구분한다. 설치본·전역 규칙의 자동 변경이나 무한 재시도를 뜻하지 않는다.

이전 설계와 수행 완료 프롬프트는 [아카이브](archive/index.md)에 보존한다. 그 안의 미래형 지시는 현재 작업을 승인하거나 다시 실행하는 근거가 아니다.

## 2. 현재 구현, 보완한 오류와 남은 한계

설계의 책임 분리는 유지하되 **구현 결함, 미수행 인수, 외부 근거/권한, 의도된 보호**를 구분한다. 0.1.62의 Full은 447/447 통과했고, lookup/resume/audit는 검사·복구를 실행하지 않는다. 기존 환경 실패와 원인에 맞는 복구·동일 대상 재검사를 연결하되 수동 비활성화를 해제하지 않는다. 아래 표와 0.1.61 Full cleanup 오류는 이전 범위의 기록이며 최신 결과와 함께 읽는다. 제품 후보는 미병합 draft이고 전체 평가 목표는 미완료다.

| 사용자 관점 | 구현·관찰된 범위 | 남은 한계와 다음 판단 |
| --- | --- | --- |
| 많은 task 위임·검증 조회 | 기존 task 선택/재개에 요청·영향·프로젝트·미결정 행동과 기준→검사/의미 검토→명령/가이드→raw→현재 유효성→다음 행동을 연결. 원본을 보존한 실제 3개 task의 새 문맥 인수 평가 | 제공한 선택 경로·도움·노출을 기록한 도움받은 소비이며 무도움 성공으로 보고하지 않음. 묶음 판단은 Agent 취합, 장기 무인 운영은 미입증 |

담당 정정 경로 부재는 0.1.58에서 수리됐고 실제 소비도 끝났으므로 반복 구현하지 않는다. 0.1.60은 [공통 runtime](../../authoring/scripts/project_workflow.py)에 동작 보존 ID 이관을 별도 분류해 추가했다. 새 격리 제품 replay는 계약과 현재 실행을 입증해 PRESERVED가 됐다. 보존 CatalogImport 기록은 baseline/preimage 근거가 부족하므로 BLOCKED를 유지한다. 새 성공을 과거 기록의 정당성으로 소급하지 않는다.

직전 완료 보고의 남은 항목을 모두 “다음 구현”이나 “환경 BLOCKED”로 묶어서는 안 된다. 독립 가이드 소비와 23개 검토의 요청 내/밖 분류는 수행 가능한 인수 잔여다. 시간·회차 종료는 외부 장애가 아니다. host는 현재 패키지 미설치와 설치 변경 금지, 사용자 시안 승인은 실제 사용자 판단, 사업 가치는 실사용 관찰이 각각 필요하다. 전체 인수까지 완료하지 못했다는 한계를 유지한다.

이번 재검토에서 정리 후 보존된 패키지로 실제 제품 task를 다시 조회했다. 여전히 18개 현재 PASS/전체 PARTIAL, producer 0회이며 task state hash는 불변이었다. 이는 새 read-only 확인이며 이전 제품 검사를 재실행한 결과가 아니다. task atomic 교체는 동시 쓰기 손실 방지가 아니고, 모델 합의·hash는 정답이나 승인 인증이 아니라는 경계도 유지한다.

작은 명확한 작업은 직접 완료할 수 있고 Router가 gate가 되어서는 안 된다. 분석 요청은 read-only, 수정 요청은 해당 범위에서 수리한다. 긴 작업·여러 위험 경계는 기존 Work Packet 기준을 적용하고 별도 업무 관리 엔진을 만들지 않는다.

## 4. 검증 관점과 Full-stack 책임

**업무 결과·규칙과 아키텍처는 검토 관점, FE·BE/API·Domain은 논리적 책임 영역, E2E는 연결 확인 방법**이다. runtime의 `business`는 이 업무 결과·규칙 관점을 가리킨다. 사업 모델의 가치·전환·수익 가설 검증은 별도 사용자/운영 관찰이다. 사용자 요구와 합의한 업무 규칙을 기준으로 삼으며 현재 구현 자체를 정답으로 삼지 않는다.

| 책임 영역 | 업무 결과·규칙 관점 | 아키텍처 관점 | 근거 |
| --- | --- | --- | --- |
| FE | 작업 완료, 입력·오류·저장 상태, 기대 값과 실제 결과 | 상태 소유권, 비동기·중복 상태, component/effect 경계 | 실제 조작·reload/readback, 상태·keyboard·관련 화면 |
| BE | 권한·계정 분리, 저장 규칙, 실패 시 데이터 보존 | parse/validation, API contract, transaction, adapter·실패 책임 | API/handler 결과, persistence·rollback, 계정 경계 |
| Domain | 금액 계산, 상태 전이, 불변 이력 등 invariant | typed model, 규칙 소유 모듈, 순수 로직·의존 관계 | 결정적 behavior·계약·필요한 edge case |
| Cross-layer | 사용자 결과가 제품 전체에서 일치 | UI → API → Domain → 저장 → 재조회 연결 | 실제 앱·API·DB/readback 대조, 필요한 print/PDF |

사업 성과 가설(사용자 가치·전환·수익)과 소프트웨어 업무 규칙(가격·권한·상태 전이)을 구분한다. 전자는 적절한 사용자/운영 관찰이 필요하며 단위 테스트 PASS로 입증하지 않는다. 보안·성능·접근성·데이터 무결성은 관련 셀과 흐름의 속성으로 다루며 셀을 무조건 늘리지 않는다.

후속 출력 보완에서는 세 주장을 따로 읽을 수 있게 한다. **사업 가치**는 대상 사용자의 실제 업무·개입·재작업 관찰, **제품 정확성**은 요구에서 나온 기대와 실제 사용자 흐름, **아키텍처 적합성**은 경계·상태/효과 소유권과 관련 실패 복구 근거다. 기존 `business` 저장 키를 성급히 변경하기보다 표시명과 설명을 `업무 결과·규칙`으로 명확히 하는 것이 우선이다. E2E는 6셀의 합산 점수가 아니라 같은 입력·식별자·값으로 연결한 주장이다. 독립 검토자는 구현자가 고른 테스트만 읽지 않고 요구의 출처와 실제 호출 경계에서 빠진 반례를 찾는다.

BE/API와 Domain은 서버를 둘로 나누라는 뜻이 아니다. 같은 모듈이 두 책임을 소유할 수 있다. 지도에는 입력/응답·외부 효과 경계와 규칙 owner를 연결하고 같은 사실의 중복 검사를 만들지 않는다. 사업 가설은 기존 요구 문서에 기대 가치·관찰 대상·현재 미확인 상태를 두고, 필요한 실사용 평가만 합의한다. 제품 analytics나 별도 점수 저장소를 선행 구축하지 않는다.

아키텍처는 실제 caller·상태/효과 owner·의존 방향·계약·실패 경로를 본다. 코드 구조 설명만으로 PASS를 만들지 않는다. 금지 의존, 중복 상태/호출, API 계약처럼 결정적으로 검사할 수 있는 성질은 기존 test/lint에 연결하고, 설계 선택의 적절성은 근거 있는 의미 검토로 남긴다. 같은 실행이 여러 셀을 뒷받침할 수 있지만 각 주장을 실제로 입증하는지 확인한다.

매 변경마다 모든 칸의 테스트나 Agent를 요구하지 않는다. 변경 로직·직접 호출자·상태·공유 자원·계약에서 영향 Feature를 선정한다. 아키텍처 검토는 touched boundary에 집중한다. 불명확한 영향은 조사하며 무조건 Full이나 생략으로 처리하지 않는다.

## 5. Feature Map·검증 실행·결과 조회

프로젝트 Feature Map의 최소 정보는 `ID/이름, 사용자 행동, 기대 결과, business invariant, FE, BE/API, Domain, 데이터 side effect, 실제 검증 방법`이다. 기존 구조를 재사용하고 assertion·특정 실행의 PASS를 영구 지도에 복제하지 않는다. 관련 없는 층에는 해당 없음과 이유를 둔다.

전체 최초 init은 합의한 프로젝트 조사 범위의 모든 기능을 대상으로 한다. 요구/화면/API/CLI/job/역할/flag/데이터/기존 테스트를 교차 조사하고 모든 Feature에 요구 출처·책임·흐름·검증 연결 또는 미연결 상태를 둔다. 범위의 출처·미조사 영역·제외 이유를 보존하며 일부 주요 기능만 조사한 뒤 전체 완료로 줄여 쓰지 않는다. 큰 지도는 업무 영역별 작성 뒤 영역 간 의존/흐름을 통합하며 전체 조사와 최소 의미가 완성되기 전에는 PARTIAL이다. 전체 init의 PARTIAL은 독립적으로 수행 가능한 작은 요청을 일괄 차단하는 이유가 아니다. 지도 완성과 전 기능 테스트 실행 PASS는 구분한다. [전체 init·분할·완료 기준](agent-workflow-completion-design.md)을 따른다.

map/guide는 기준과 방법, 프로젝트 설정은 argv와 실행 연결, `.work/`는 특정 실행 근거를 소유한다. 기존 `.harness/project.yaml`의 명령·영향 선택과 필요한 `extensions`를 우선 검토하되 비-Harness 프로젝트에 설치를 강제하지 않는다. Markdown·JSON·YAML을 사람이 중복 관리하지 않는다.

조회는 기존 `lookup/resume/audit --summary`와 viewer로 시작한다. 여러 task는 사용자가 명시한 제한된 state 묶음을 순서대로 읽어 비교하며 같은 task에 동시에 쓰지 않는다. ID·요청·Feature·관점/영역·기대/실제·run/raw·현재 재사용·미확인·다음 행동을 짧게 연결한다. dashboard·MCP·상태 DB·새 batch 명령은 선행 조건이 아니다.

| 결과에 연결할 정보 | 의미 |
| --- | --- |
| Feature·check·주장·기대 결과 | 어떤 사용자 결과를 확인하는가 |
| 관점·책임 영역·선택/제외 이유 | 무엇을 검증하고 무엇은 영향이 없는가 |
| 실행 상태 | 계획, 실행됨, 미실행, skip, `not_required` 구분 |
| 검사 판정 / 범위 검토 | PASS / ISSUES / BLOCKED와 활성 셀의 미결정·미확인·N/A·범위 밖을 분리 |
| 당시 결과 / 현재 재사용 / 원본 접근 | 현재 유효·STALE·미실행과 raw 존재·상세 생략·누락/만료를 분리 |
| 명령·cwd·source/runtime·fixture | 어느 코드·서버·데이터에서 실행했는가 |
| run ID·native exit·case/skip/error·raw evidence | 요약을 확인할 실제 근거 |
| 구현 commit/diff와 검증 연결 | 어떤 변경으로 어떤 문제가 해결됐는가 |

PASS는 선택한 필수 기준을 실제 확인한 범위에 한정한다. ISSUES는 기대와 다른 실제 행동, BLOCKED는 필수 관찰 불가·미해결 정답·환경 제한이다. `not_required`는 제외이며 PASS가 아니다. 0건·필수 전부 skip·다른 대상·stale 결과·shell 후속 성공은 성공 근거가 아니다.

짧은 조회도 `요청 범위 → 기대 출처/revision → 선택한 검사/관찰 방식 → 실제 결과·근거 → 미확인/제외 이유 → 현재 재사용·다음 행동`을 보여준다. source 조사 완료, 제품 runtime 관찰, 선언한 지도 범위, host 수락 수준을 하나의 PASS로 합치지 않는다. 요청 내 미관찰은 열린 항목으로, 요청 밖 runtime은 미실행/범위 밖으로 표시한다. source-only 요청을 완료하기 위해 브라우저 실행을 강제하지 않는다. 이 조사 계약과 여러 task/raw의 소비는 기존 인수를 재사용하며, scope 미결정 안내는 0.1.48에서 보완됐고, 다음 조회 과제는 §10의 명시적 task 묶음 비교와 실제 소비 비용이다.

여러 업무의 사용성 인수는 “상태를 출력했다”가 아니라 다음 작업자가 **어느 작업이 지금 인수 가능한지, 무엇이 왜 막혔는지, 누가 어떤 근거를 보충해야 하는지** 정확히 결정하는지로 판단한다. 기존 summary를 사용해 요청 내 미완료와 프로젝트 전체 잔여를 나누고, 원본 링크·현재성·다음 행동을 대조한다. task별 집계 분모가 다르면 PASS 비율로 순위를 만들지 않는다. 묶음 CLI가 필요하면 기존 조회의 명시적 state 목록 입력/출력 취합만 검토하며 자동 전체 디렉터리 스캔·새 상태 저장소는 만들지 않는다.

`READY_FOR_REVIEW`는 연결/제출 기록의 검토 준비 상태이지 작업 완료나 full-stack 충분성이 아니다. 읽기 요약에서는 이 뜻과 `검사 현재 PASS / 범위 미결정 / 다음 의미 검토`를 함께 보여준다. legacy 범위 미등록은 명시하되 자동 N/A나 모든 셀 REQUIRED로 추정하지 않는다. Agent가 요청과 영향에서 필요한 셀을 결정하고, 명시된 필수 셀의 누락·stale·실행 여부는 기존 코드가 확인한다. 확인 가치가 없는 셀에는 근거 있는 N/A를 쓰며 실행 수에 더하지 않는다.

현재 capture는 untracked 내용, dependency, fixture, served source, Agent 신원이나 editable evidence 진위를 인증하지 않는다. 중요한 항목은 프로젝트 실행 경로에서 확인한다. 과거 결과 조회는 원래 판정과 현재 재사용 가능성을 구분하고 자료가 없으면 주장을 확대하지 않는다.

## 6. 피드백을 수정과 가드레일로 연결

먼저 요구 위반·요구 변경·의도된 차이·기준/도구 오류·환경 제약/미확인을 구분한다. 기존 요구 위반은 `불편/실패 → 기대 출처 → 재현 → 원인·상태/데이터 흐름 → owner 수리 → 가드레일 → 같은 기준 RED/GREEN·정상 반례 → 다음 관련 요청의 소비`로 수행한다. 요구 변경은 유효한 변경 근거와 새 기준·유지 계약을, tool 오류는 독립 관찰과 도구 owner 수리를 확인한다. 의도된 차이는 적절한 variant/예외로, 환경/미확인은 열린 상태로 남긴다. 설명 요청만으로 수리하거나 전역 규칙·개인 memory를 변경하지 않는다.

| 원인 | 우선 개선 위치 |
| --- | --- |
| 제품 코드·저장 오류 | 상태·데이터·effect를 소유하는 코드 |
| 잘못된 입력·불가능한 상태 | runtime validation, type/model, 필요한 상태 전이 제약 |
| 반복 UI 불일치 | 기존 token·shared component·상태 API |
| 검증의 결함 누락 | 실패를 관찰하는 사용자 flow·경계 검사·guide |
| 대상·report·exit 오판 | 실행 도구·프로젝트 adapter·환경 식별 |
| 지침 미발견·충돌·과잉 | Router·Playbook·기존 지침의 연결 또는 축소 |
| 설치·배포 drift | source/generated·설치 무결성·Harness |
| 환경·접근 제한 | BLOCKED와 가능한 fallback, 제한 보존 |

사용자 검수는 후보/주장 ID·동의한 처분·범위·요구/UI 기준 revision에 연결한다. “문제가 있다”는 동의와 “차이를 유지한다”는 동의를 구분한다. 설명/원인/owner 메모 수정은 이전 동의의 근거를 새 hash로 바꾸지 않는다. 기준 변경·철회는 재검토하고 유효한 동일 결정은 후속 task에서 재사용한다. 0.1.47은 **다른 kind를 거쳐 돌아오는 전이에도 원본 결정 근거를 보존**하며, 다른 분류의 확인 근거와 승인 근거의 소유권을 구분한다. 분류 수정 자체는 허용한다.

기준의 내용 hash뿐 아니라 **적용 기준 집합의 추가·제거·연결 변경**도 판단 대상이다. 0.1.47은 해당 Feature의 모든 연결 기준과 소비 UI guide를 결정에 묶고 연결 변경·불완전한 legacy를 재검토로 남긴다. 무관한 Feature 기준 변경은 정상 결정을 무효화하지 않는다. 더 세밀한 제외는 아직 지원하지 않으며 추후 관련성 근거와 검토 revision을 먼저 마련해야 한다. 의미 관련성은 Agent/사용자 검토, CLI는 명시된 누락·변경·결정 연결을 소유한다. 별도 승인 DB나 자연어 권한 판정기는 만들지 않는다.

담당을 잘못 정했을 때 원본 Feature나 실패를 덮어쓰지 않는다. 0.1.58의 `feedback.supersession`은 같은 task의 올바른 담당 기록, 동일 사건이라고 판단한 이유, 기존 검토 참조를 연결한다. 실제 입력·철회·후속 소비 규칙은 [피드백 수리와 재사용](../../authoring/references/repair-and-reuse.md)을 따른다. 이관 기록은 원본 실패와 구분하고, 후속 담당의 현재 근거를 조회 때 재검사한다. 순환·여러 단계 이관·없는 후속 담당을 지원하지 않으며, 후속 담당 없이 실제 요구가 폐기된 경우를 임의 해결로 바꾸지 않는다.

가드레일은 원래 실패를 검출하고 가까운 정상 사용을 허용해야 한다. 동작 보존은 baseline/equivalent GREEN을 쓸 수 있다. 기대값·skip·visual baseline을 완화해 결함을 숨기지 않는다. 지침이 이미 있었다면 같은 문장 추가보다 적용되지 않은 원인을 고친다.

“다시는 발생하지 않음”은 확인한 원인·입력·호출 경계의 예방으로 한정한다. 예를 들어 FE 표시만 고쳐 저장되는 잘못된 값은 남겨두거나, 타입 선언만 추가해 외부 입력을 허용하는 것은 예방 완료가 아니다. 입력 → API → 규칙 owner → 저장 → 새 조회에서 실제 값/ID와 최초 기대 위반 지점을 추적하고, owner 수리 후 같은 실패·가까운 정상·관련 우회 입력을 확인한다. 설명·guide·추가 테스트만으로 원인 코드의 수리를 대신하지 않는다.

의무의 발생·유지·누락 차단은 환경, 해당 의미를 판단하여 실제 작성·수리하는 것은 Agent, 정형 실행·계산은 code/CLI/runtime이 맡는다. 이 원칙은 요청·구현·검토·검증/조회·피드백·UI·유지보수·설치·자원/재개·완료 전반에 적용한다. 책임/권한의 위치와 처리의 결정성은 별도 축이며 Skill 전체를 하나로 분류하지 않는다. 외부 결과가 변해도 정형 수집/timeout/판정을 LLM에 넘길 이유는 아니다. 지도 갱신은 이 구분의 한 예다. 우회 불가가 필요한 효과는 Agent가 임의로 바꾸지 못하는 권한·수락 경계가 맡으며 선택적 로컬 hook/wrapper나 수정 가능한 PASS 파일은 강제 통제가 아니다. 단계별 분류 기준과 실제 역할 표·최소 context·검증은 [공통 책임 분리 설계](agent-workflow-completion-design.md)에 둔다.

자가 개선은 관찰된 회귀·실패·drift·피드백에서 시작한다. 범위 안의 가역적 개선은 진행하고 제품 결정 변경·전역 변경·외부 비용 등의 경계는 기존 권한을 따른다. 자동 회고·규칙 축적·무한 재시도는 만들지 않는다.

## 7. 지속 갱신의 책임

| 책임자·계기 | 수행할 일 |
| --- | --- |
| 환경 / 요청·변경·실패·설치·재개·완료 경계 | 적용되는 의무와 상태를 발생·유지하고 누락이면 해당 수락/효과를 거절. 정형 처리는 직접 실행하고 의미 작업만 필요한 context와 함께 Agent에 전달 |
| setup / 최초 연결 | 모든 기능의 map/guide/UI 조사, 필요 시 분할·재개·통합, 실행 연결과 미검증 범위 구분 |
| 고도화 수행자 / 기능·코드·UI·검증 추가·수정·삭제 | 영향 Feature·계약·구현/검증 연결을 같은 변경에서 반드시 갱신. 공통 변경은 소비 Feature까지 대조 |
| 검증자 / 완료 검토 | 요구·동작·근거와 지도 누락·기준 유효성 대조 |
| product maintain / 요청된 점검·회귀·drift | 누락 기능·죽은 명령·계층 공백·중복 검사 조사, 실제 실행·수리 |
| UI 작업자 / 관련 변경·반복 불일치 | 디자인 의도·대표 화면·상태 검토, 필요한 token/component·guide 개선 |
| Harness maintain / 관련 무결성 문제 | mapping·배포·retention·cohort 점검 |

UI 기준은 디자인 의도·용어·정보 위계·상태·variant/예외, color/typography/spacing/radius/elevation, layout/component conventions, loading/empty/error, responsive·accessibility, Do/Don't·reference·visual 검증을 필요한 깊이로 연결한다. 의도는 guide, 실제 값·동작은 코드가 소유한다. 한 화면의 의도된 예외를 전역 규칙으로 승격하지 않는다. 관련 desktop/mobile·interaction을 실제 확인한다.

UI guide를 만들 때 현재 화면을 정답으로 복사하지 않는다. 실제 영향받는 대표 소비 화면에서 정상/오류·keyboard·관련 viewport를 확인하고, 새 context의 관련 화면 요청이 그 guide/owner를 재사용하는지 인수한다. 여러 consumer에 공통 변경이 있다면 서로 다른 사용 의미의 정상·variant를 대조하되 매 수정마다 고정 화면 수나 T5 전수 재실행을 요구하지 않는다. 의도된 destructive/일반 action 차이를 결함으로 수리하지 않는다. UI 예외도 기준 변경과 연결해 재검토한다.

제품 버그·오래된 guide·실행 도구 오류를 구분한다. 제품 위반을 guide 변경으로 숨기지 않는다. 영구 문서는 현재 사용법과 lasting 결정, 상세 로그·fixture·screenshot은 기존 `.work` 보존 정책에 둔다.

행동 보존 리팩터링도 영향 Feature의 구현/검증 참조·검토 기준을 확인하고 달라진 부분을 갱신한다. 단순 timestamp나 자유 문구 `영향 없음`으로 기능 고도화의 의무를 대체하지 않는다. 제품 영향 없는 오탈자/작업 기록은 근거에 따라 내용 불변을 허용하며 매번 전수 조사/Full을 요구하지 않는다.

## 8. 검증을 유지·통합·제거하는 기준

`무슨 실패를 잡는가 → 같은 실패를 잡는 다른 근거가 있는가 → 축소/삭제 후에도 검출되는가`로 판단한다. 비용은 측정했을 때만 수치로 말한다.

- 우선 유지: 실제 regression, 핵심 invariant, 권한·계정·데이터 손상 방지, 경계 계약, 주요 flow, cheap deterministic 검사.
- 정리 후보: 구현 세부 고정, 검출 중복, brittle mock, 비용 대비 독자적 검출 부족, enforcement로 대체된 검사.
- 중복 통합: 남기는 검사/구조가 같은 의미의 실패와 가까운 정상 사용을 보존한다는 근거.
- 요구 폐기: 유효한 요구 변경, 제거/변경/유지되는 진입점·호출자, 남은 계약·소비자 영향, 활성 연결 정리와 이력. 규칙만 폐기하면 API는 남을 수 있으며 없는 대체 검사를 강제하지 않는다.
- 구조적 예방 이동: 실제 거부·정상 허용과 해당 우회/호출 경로를 확인한다. type/constraint가 있다는 선언만으로 detector를 제거하지 않는다.
- flaky/도구 오류: 제품 실패와 분리해 관찰 수단을 수리한다. 재시도 중 한 번의 PASS나 skip으로 공백을 숨기지 않는다.
- 동작 보존 바인딩 이관: 같은 검사의 이름/결과 저장 경로 변경은 삭제·중복 제거와 다르다. 0.1.60은 아래 조건의 clean Git/native 경로를 구현했다. 근거가 없는 legacy BLOCKED는 해제하지 않는다.
- 검출 이력이 없거나 오래됐다는 이유만으로 고유 예방 검사를 삭제하지 않는다.
- 소비자 schema·manifest·배포 계약은 문자열 검사처럼 보여도 필요하다. 문구 검사로 Agent 품질을 증명하는 주장과 구분한다.

전수 정리나 mutation framework부터 만들지 않는다. 한 개의 근거 있는 통합·축소로 충분하다. 후보 발견과 삭제 완료를 구분한다.

0.1.60의 `rebind/check_identity_migrated`는 기존 check decision 안의 좁은 **바인딩 이관**이다. 옛 task에 고정된 plan/commit preimage에서 command·cwd·runtime·dependency·fixture·source·criteria·required·assertion 식별자/기대값·coverage/예방 연결을 비교한다. 허용 차이는 check ID와 명시적으로 연결된 결과 경로뿐이다. argv 전체의 임의 문자열 정규화나 참조 파일 전체 무시는 금지한다. 새 경로의 실제 실행 결과도 필요하며 연결된 모든 소비자가 유지돼야 한다. 기존 shared command는 보존하며 일반적인 단독 명령 삭제나 dirty preimage까지 지원한다고 주장하지 않는다.

현재 `check_links`에는 옛 ID/prevention/criteria hash만 있어 일반적인 계약 동등성을 복원하기에 부족하다. 기존 bound plan이 있으면 재사용하고, 없으면 task 시작의 최소 계약 preimage 보존을 검토한다. legacy의 누락은 현재 값으로 채워 과거 값인 것처럼 쓰지 않는다. 이름·경로 외 조건 변경, assertion 제거·완화, required 해제, 소비자 누락, preimage 부재는 이관 경로로 통과시키지 않는다. 기존 failure/prevention이 있으면 그 연결도 보존한다. 이관 성공은 과거에 없던 RED 검출 이력을 만들어 주지 않으며 실제 삭제·통합의 검출 보존 요구는 그대로 유지한다.

검사를 줄이는 최종 판단은 같은 결함 검출과 정상 허용뿐 아니라 실행/유지 시간, flaky 원인, 사용자 개입·재작업을 함께 본다. 부작용 때문에 둘을 함께 실행할 수 없다면 격리 상태에서 대조한다. 근거를 만들 수 없는 제거 후보는 유지하되 무기한 “다음 검토”로 돌리지 말고 부족한 근거와 재검토 계기를 적는다.

### 0.1.61 현재 판단과 완료 경계

2026-10-15 검토 기준은 clean local `main@bf9203a` / runtime **0.1.61**이다. [직전 구현 결과](agent-workflow-implementation-results.md#delegated-handoff-2026-10-15)와 이번 `.work/design-review-20261015/`의 두 독립 검토·환경 실행을 구분한다. 이번 변경은 설계와 안내의 보완이며 아래 미래 runtime 변경을 구현한 것은 아니다. 기존 0.1.59–0.1.60 설계 당시 잔여표는 현재 지시로 사용하지 않는다. 당시 상태와 원본 실패는 Git 이력 및 해당 구현 결과에 보존한다.

완료된 검사 ID/출력 경로 이관, checkpoint 이후 미확인 launch의 BLOCKED 표시, 실제 제품 replay와 고정 패키지 소비를 다시 구현하지 않는다. 0.1.61은 요청/필수 영향/프로젝트 잔여/미결정 분류, 미충족 기준의 명령·guide·raw·현재성 연결, lookup/resume/audit 공통 차단 판정, assertion 파일 변경 감지를 추가했다. 실제 세 task의 네 selector를 도움받은 새 문맥에서 소비했고, 다른 staff-access 업무에서 기존 guide/token/component와 native 56/56·browser 7-suite를 사용했다. 이는 무도움 성공·동시 다수 Agent 운영·스타일 기준 변경 후 재사용·사용자 UI 승인을 입증하지 않는다.

기본 설계는 유지한다. 프로젝트는 요구·기준·등록 명령·기대 결과·token을, Agent는 적용성·업무/시각 의미·원인을, CLI는 실행 사실·연결·현재성을 소유한다. `business`는 **업무 결과·규칙**이며 사업 모델의 수익성·전환·사용자 개입 감소와 다르다. 6셀은 필요한 책임을 발견하는 지도이고, E2E는 층 사이의 연결을 확인하는 방법이다. 모든 작업에 6개 검사나 전체 제품 조사를 강제하지 않는다.

### 환경 실패를 숨기지 않는 실행 원칙과 이번 시도

동일 명령의 default sandbox 실패와 승인된 `require_escalated` 실행을 별도 raw로 보존한다. 권한 상승은 명령 단위 권한이며 Windows Administrator 실행, sandbox backend 설정 변경, 설치 변경과 같지 않다. 명령이 이미 외부 효과를 시작했는지 확인한 뒤 재시도 여부를 정한다. 조회·검사로 해결되는 문제에 전역 sandbox 설정이나 trust bypass를 추가하지 않는다.

- timeout child cleanup 검사: default에서는 `taskkill` exit 1과 임시 디렉터리 정리 오류로 실패했고, 동일 unit을 권한 상승해 **1/1 PASS**했다. 원본 실패와 PASS raw는 각각 `environment/timeout-sandbox.json`, `timeout-escalated.json`에 있다. 이전 Full 433개 중 432 PASS/1 ERROR를 전체 PASS로 소급하지 않으며 이번에는 Full을 재실행하지 않았다. 향후 진단 보완이 필요하면 기존 capture record에 cleanup 명령·stdout/stderr를 남기는 최소 변경을 먼저 검토; cleanup 실패를 성공으로 처리하거나 자동 승격하지 않음.
- `codex plugin list --json`: default의 CODEX_HOME 접근 거부 뒤 권한 상승으로 **조회 성공**, 설치된 plugin 12개와 대상 plugin 미설치를 확인했다. 설치본 변경은 없으며 raw는 `native-discovery-sandbox.json`, `native-discovery-escalated.json`이다.
- codex-cli 0.160.0의 생성 schema를 먼저 확인하고, 임시 CODEX_HOME과 `--no-daemon app-server --stdio`에서 `initialize`→`skills/extraRoots/set`→`skills/list`→`hooks/list`를 실행했다. 고정 패키지 19개 외 기존 `.agents`/system Skill 21개도 발견돼 완전한 Skill 격리로 보고하지 않는다. 패키지 247파일 hash는 전후 불변, model turn 0회. hooks는 빈 목록이며 project trust 경고와 TEMP home의 PATH helper 생성 거부 경고를 `native-isolated-readonly.json`에 보존했다. helper 경고가 이 발견 조회를 막지는 않았다. plugin hook을 등록/신뢰하거나 실행한 결과가 아니다.

현재 [공식 Windows sandbox 문서](https://developers.openai.com/codex/windows)는 권한 profile/approval과 backend를 구분하고, MXC 시험 예시는 CLI 0.162.0 이상을 요구한다. 현재 0.160.0에 이를 가정하거나 도구를 갱신하지 않았다. [공식 hooks 문서](https://learn.chatgpt.com/docs/hooks)는 plugin 설치만으로 hook을 신뢰하지 않으며 변경된 hash의 검토가 필요하다고 설명한다. 따라서 다음 native callback 인수에는 지원 버전·정확한 plugin source·승인된 등록/신뢰와 실제 이벤트 조건을 먼저 준비해야 한다. 전역 설치·provider 변경·신뢰 우회·모델 비용 발생을 이번 읽기 검증의 연장으로 수행하지 않는다.

### 여러 업무의 인수와 검증 비용을 판단하는 방법

기존 상태를 한 writer로 관리하고 독립 task는 기존 host 위임/Git worktree로 분리한다. 동시 소유 파일 변경·중단 후 인수·통합에서 실패가 실제 확인되면 revision 비교와 충돌 거절 같은 기존 write 경계부터 보완한다. 많은 task를 조회할 수 있다는 이유로 장기 무인 scheduler나 동시 writer 안전성을 완료로 주장하지 않는다.

각 후속 평가는 task ID/root/base, 요구·기준 revision, 필요한 책임과 제외 이유, 명령/guide, raw, 현재 유효성, 제공한 힌트·도움·재시도를 연결한다. 구현자와 검토자가 같은 잘못된 oracle을 공유할 수 있으므로 사용자 기대 출처와 원래 실패/정상 반례를 고정한다. 위험·독립성이 필요한 곳에만 별도 Agent를 사용하며 Agent 수나 테스트 수를 목표로 삼지 않는다.

비자명한 구현은 focused RED 또는 동작 보존 baseline GREEN→최소 owner 수리→실패/정상·영향 회귀→실제 소비 순서로 검증한다. 조회 최적화에는 출력 동등성과 다음 호출의 변경 감지가 필요하다. 반복 측정은 조건·편차와 함께 기록하며 효과가 없거나 근거가 부족하면 유지한다. 새 대시보드·DB·스케줄러·범용 정답 판정·자동 승인·고정 6/10개 검사·매번 Full은 추가하지 않는다.


## 11. 요구사항 검토로 구체화한 실행 연결

2026-10-05 [R01–R16 검토](agent-coding-requirements-review.md)는 수정 전 `53865b0`의 설계 검토다. 당시 책임은 `c7c064a`에서 source/generated·직접 조회 CLI로 구현했고 후속 수정과 독립 시험에서 T1–T6을 수행했다. 아래 setup/갱신 책임은 후속 전체-init 합의에 맞춰 확대했다. 당시의 미구현 판단을 현재 전체-init 기능의 부재로 해석하지 않는다. 실제 충족 상태와 환경 BLOCKED는 [구현 결과](agent-workflow-implementation-results.md), 현재 재현된 공백과 다음 개선 순서는 §2와 §10이 소유한다. [0.1.46 보완 검토](agent-workflow-refinement-review.md#post-0146-review)는 완료된 수리의 출발점을 남긴다. 일반적 효율·장기 안정성은 입증하지 않았다.

### 발견, 조합, 실패 처리

주 Agent가 요청의 조회/조사/수정 의도, 허용 범위, 대상 root·base/diff, 요구의 출처, 영향 Feature를 한 번 정리한다. 설치된 진입점의 description과 프로젝트 AGENTS/index의 짧은 연결에서 필요한 절차를 찾는다. 다음 구현의 임시 프로젝트에는 이 발견 경로를 실제 연결한다. 사용자가 Skill 이름·호출 순서를 말하거나 평가자가 매 단계 호출을 지시해야만 동작하면 단일 요청 위임 수용에 실패한 것이다. 전역 지침을 바꾸거나 모든 요청에 Router를 강제하지 않는다.

조사·검사 선택·원본 실행은 같은 대상과 유효 조건에서 공유하고, 한 실행을 여러 Feature가 참조할 수 있다. 공유 사실은 하나의 작업 기록/기존 Harness evidence에 두고 Skill마다 복사하지 않는다. 공통 파일 수정은 주 Agent가 소유한다. 통합 결과는 제품·Harness·UI의 PASS/ISSUES/BLOCKED를 각각 남긴다. 동일 이름의 check라도 대상·기준·조건이 다르면 같은 실행으로 합치지 않는다.

독립 검증이 필요한 경우 주 Agent는 사용자 기준, 해당 base/diff, 실제 실행 대상, 원본 evidence와 쓰기 범위를 검증자에게 전달한다. ISSUES는 재현과 소유자를 붙여 수정 담당자에게 돌려보내고, 새 diff가 무효화한 근거만 재검증한다. BLOCKED는 필요한 관찰·원인·가능한 fallback·재개 조건을 남기고 독립 작업을 계속한다. 같은 원인/근거만 반복되면 가설이나 수단을 바꾸며 무한 재시도하지 않는다. 주 Agent가 raw와 diff를 확인해 최종 판정한다. verifier 파일이나 구현자 PASS 전달은 이 절차를 대신하지 못한다.

| --- | --- |
| Feature 최초 연결 | setup이 전체 기능을 요구/제품 문서/실제 진입점으로 조사하고 최소 의미를 채운 지도를 완성. 분할 작업은 통합 전 PARTIAL. 검사 미연결 기능도 지도에 포함하며 첫 flow로 실행 경로 확인 |
| 모든 고도화·Feature 추가·수정·삭제 | 변경자가 구현 전 기대 결과/invariant·영향을 확정하고, 같은 기능 단위 diff/commit에서 영향 map·guide·활성 selector를 대조하고 실제 변경된 참조·기준을 갱신. 의미·참조 불변이면 그 근거로 기존 내용을 유지. 삭제는 실제 호출/사용 여부를 확인하고 활성 연결만 제거하며 과거 결과는 보존 |
| FE 입력·직렬화·저장·재표시 또는 계층 간 계약 변경 | 관련 UI → API → domain/persistence → 새 조회를 실행. 층별 PASS만으로 대체하지 않음. DB 직접 관찰은 readback으로 확인 못 하는 원자성/중복/이력 규칙에 선택 |
| Domain 계산·상태 전이 변경 | 요구 기반 정상·경계·실패의 결정적 검사. 외부 표현/호출 계약도 바뀌면 해당 adapter와 사용자 flow를 추가 |
| 권한·transaction·외부 실패 변경 | 허용/거절 응답, 실패 뒤 데이터 보존·rollback/readback과 관련 사용자 상태. 실제 계정/외부 서비스 권한이 없으면 그 범위는 BLOCKED |
| UI 표현·공통 component 변경 | 영향 화면·desktop/mobile·keyboard 및 loading/empty/error 등 관련 상태. 저장 경로가 무관하면 제외 이유를 남김. 반복 문제는 가능한 기존 token/component/lint에서 예방하고 후속 요청에서 재사용 |
| 아키텍처만 변경 | touched interface·caller·상태/효과/의존 소유권과 baseline/equivalent GREEN. 행동 영향이 없으면 별도 제품 flow를 억지 추가하지 않음 |
| 완료 검토·요청된 유지보수·escaped regression | 검증자가 요구·diff·실제 관찰과 지도/guide의 누락·죽은 명령·삭제 잔존·계층 공백을 비교. 원인이 제품인지 기준/도구인지 분류해 해당 소유 위치만 수리. 매 작업 전수 조사는 하지 않음 |

아키텍처 판단은 `external boundary → parsing/validation → typed domain model → pure business logic → persistence/external adapter`를 사용한다. FE는 입력/표시/상호작용, BE는 권한/외부 계약/transaction, Domain은 계산/업무 상태/invariant를 소유하는지 실제 caller와 데이터 흐름에서 확인한다. controller·route·UI에 공유 업무 규칙이 흩어졌다면 올바른 기존 소유 위치를 우선한다. 상태 전이 복잡성에는 state machine/reducer, 상호 배타 데이터에는 typed model/discriminated union, 확장 목록에는 registry, 수명주기에는 command/event, 규칙 분산에는 domain module을 검토하되 관찰한 문제 없이 패턴이나 폴더를 추가하지 않는다. 이는 이전 설계의 유효한 책임 원칙을 복구한 것이며 전면 재설계 지시가 아니다.

### 계획·실행·조회 사이의 최소 연결

계획의 Feature/check와 기대 결과는 요구/기준의 출처·revision을 참조한다. 선택/제외 이유와 필수 여부를 실행 전에 정하고, 실제 결과는 그 항목에서 capture의 run ID·명령/cwd·코드 상태·raw 위치 및 native assertion/관찰 위치로 연결한다. 한 실행의 raw는 한 번 보존하고 요약은 그 참조를 소비한다. 실행기는 사실을 캡처하고 프로젝트 adapter/검증자는 업무 의미를 판단한다. 사람이 본 시각 관찰은 관찰자·대상·판단 근거를 표시하며 기계 assertion인 것처럼 쓰지 않는다.

조회는 `당시 실행 상태/관찰/판정`과 `현재 재사용 가능 / stale / 확인 불가`를 분리한다. 필요한 source·기준·명령·dependency·fixture·served build/runtime 조건의 식별값/참조가 없거나 달라지면 현재 PASS로 재사용하지 않는다. 모든 환경을 인증하는 새 시스템은 만들지 않는다. raw가 만료·누락되면 역사적 요약은 읽을 수 있지만 원본 재확인은 불가하다고 표시한다. `.work` 과거 record를 조회 시 수정하거나 새 실행으로 덮어쓰지 않는다.

집계는 필수 관찰이 하나라도 미실행/skip/0건/불명확하면 전체 PASS가 될 수 없다. 확인된 ISSUES와 BLOCKED를 함께 보존한다. `not_required`에는 영향 제외 이유를 붙이고 성공 수에 더하지 않는다. 현재 unittest adapter의 `ISSUES`는 native command 실패라는 check 범위 판정이므로 이를 제품 결함으로 바로 바꾸지 않는다. consumer가 raw에서 assertion 위반과 환경/도구 실패를 구분하며 원인 불명은 제품 판정 BLOCKED로 둔다. 기존 capture/adapter를 대체하지 않고 실제 소비자에 필요한 작은 결과 연결만 구현한다.

### PStack 역할과 배포의 최소 배치

Mode/Router는 의도 선택, Playbook은 조건부 순서, Skill은 재사용 판단, Principle은 기존 기준과 구조적 예방, 실행 도구는 명령·raw 캡처, 프로젝트 설정은 root/argv/selector/예외/보존을 소유한다. PStack Automation은 외부 이벤트·주기 실행을 붙이는 별도 계기다. 이번에는 사용자 요청·변경·실패가 충분하므로 Benny/cron/Slack/webhook를 채택하지 않는다. 반복 수요와 권한·비용 근거가 생기면 기존 절차의 입력으로 연결하며 다른 제품 정답을 만들지 않는다. Plugin은 이 능력의 생성 패키징·설치만 맡는다.

세 공통 Skill의 경계는 업무 조정, 전체 최초 지도와 검증 연결, 기존 경로 유지로 유지한다. 기존 Harness 유지보수는 제품 의미를 소유하지 않아 대체재가 아니며, diagnose는 초기 지도/지속 drift 점검의 대체재가 아니다. setup/maintain이 공유하는 조사·결과 규칙은 한 참조로 유지하고 공통 조정은 기존 AGENTS/Skill 발견 경로와 함께 검증한다. 프로젝트 `verify-product`/`ui-system`은 기존 진입점으로 발견·실행이 충분하면 재사용한다. 추가 Skill 채택은 실제 부족한 책임으로 판단하며 개수에 맞춰 늘리거나 줄이지 않는다.

## 12. 성숙도 판단과 연두링크 실전 평가 합의 (0.1.47 당시 기록)

이 절은 0.1.47에서 합의한 실행 전 판단과 평가 범위다. 아래의 당시 부족한 점과 실행 순서는 역사적 기록이며, 현재 상태는 §2·§10을 따른다. 사용자가 실행 프롬프트를
명시적으로 적용한 2026-10-12 실행에서는 두 공통 공백을 0.1.48로 수리하고,
실제 연두링크의 두 개발 브랜치·독립 후속 작업과 패키지 CLI를 검증했다.
현재 구현·관측·남은 경계는 [실행 결과](agent-workflow-implementation-results.md#yeondoo-plugin-improvement-2026-10-12)가 소유한다.
아래의 실행 전 부족한 점을 새 공백으로 재구현하지 않으며, UI draft·호스트·일반 우월성의 경계는 유지한다.

### 목적과 현재 판단

최종 산출물은 **새 문맥의 Agent가 실제 업무를 더 정확하게 수행하도록 개선된 플러그인**이다. 연두링크의 UI 변경은 이를 평가하는 실제 작업 결과이며 목적 자체를 대체하지 않는다. 사용자 요청은 자연어로 결과를 설명하면 관련 Feature·기준·소유 코드·가이드·검증을 발견하고, 실제 수정·관찰과 다음 관련 작업의 재사용까지 이어지는 체계다.

현재 플러그인은 실제 실행·기록·조회 기반을 갖췄다. [배포 목록](../../distribution/catalog.json)은 19개 Skill, [배포 구조](../plugins.md)는 공통 도구·prompt hook·로컬 패키징을 포함한다. `agent-workflow`와 두 검증 Skill이 일반 작업을 잇고, `core_harness.py`는 큰 작업의 선택적 계약을 관리하며, `project_workflow.py`와 `verification_results.py`가 상태·실행·근거를 연결한다. 금융·한글 문서 등 전문 Skill 수를 개발 위임 성숙도의 증거로 계산하지 않는다. 세션에 제공된 외부 Skill과 실제 평가 패키지의 능력도 구분한다.

현재 강점은 task별 실행과 당시 결과, 현재 재사용 가능성, 기준 변경과 피드백을 명시적으로 연결하는 데 있다. 자체 모델·작업자 서비스·범용 제품 정답 판정기는 아니다. 저장소의 보호 호스트 코드는 일반 패키지에 포함된 자동 승인 기능이 아니며, 로컬 제출·파일 hash는 실제 검토자 신원이나 의미적 정답의 증명이 아니다.

**이 목적에 집중하면 성숙시킬 가능성은 있다. 그러나 현재 방식으로 문서·상태·절차만 계속 추가해서는 입증할 수 없다.** 숙련된 주 Agent가 수동으로 연결해서 성공한 경우와 플러그인 덕분에 새로운 Agent도 성공한 경우를 구분해야 한다. 기존 자연어 견적 과제는 이전판과 현재판 모두 완료했으므로 일반 품질·시간 절감의 우월성은 미입증이다. 달성 확률·기간·완성도 백분율은 측정 근거 없이 제시하지 않는다.

### 수정 전후 평가와 구현 순서

1. **기준 고정:** 현재 플러그인 패키지와 연두링크 source base, 과제, 판정 기준, 모델/호스트·외부 Skill·브라우저 조건을 기록한다. 패키지 밖의 설치 Skill이나 감독자 수동 연결에 의존했다면 플러그인 자체 효과로 계산하지 않는다. 기존 검증·가이드를 발견하는 과정도 평가에 포함한다.
2. **현재판 사용과 공통 RED:** 기존 패키지로 자연어 UI 과제의 발견·콘셉트·대표 화면 적용 경로를 관찰한다. §2의 scope 안내·hook 중복 조사도 현재 실행으로 확인한다. 비교 전 데이터를 보존하고 나서 수정한다. 사용자 판단이 필요한 단계의 대기를 실패로 숨기거나 임의 승인으로 넘기지 않는다.
3. **소유자별 최소 수리:** 제품 결함은 연두링크, 실행 관측 오류는 기존 runner/adapter, 연결은 프로젝트 guide/map, 공통 선택·상태·문맥 실패는 플러그인 소유 코드에서 고친다. 가드레일은 구조·타입/제약·기존 검사·공유 component를 우선한다. 동일 원인의 실패/정상 사례를 확인하며 문서만 늘리지 않는다.
4. **동일 조건 비교:** 수정 전과 같은 제품 base·요청·콘셉트 결정·전제조건으로 수정 패키지를 평가한다. UI와 가이드가 개선된 프로젝트만 현재판에 제공해 효과를 부풀리지 않는다. 플러그인 변경과 프로젝트 변경의 효과를 분리할 수 없으면 그 한계를 남긴다. 평가 중 필요한 힌트·감독자 개입·재시도도 기록한다.
5. **새 문맥 재사용:** 처음 구현을 보지 않은 독립 Agent에게 다음 관련 화면의 자연어 요청을 준다. 확정된 프로젝트 가이드·코드·일반 진입 안내는 읽을 수 있지만 정답 패치·Skill 이름·CLI 순서·평가 기준표·감독자 기록을 주입하지 않는다. 같은 대화의 역할극을 독립 평가로 표시하지 않는다.
6. **상태 조회와 통합:** 명시적으로 선택한 제한된 task 묶음에서 유효·미실행·stale·raw 생략/없음/만료와 다음 행동을 설명한다. 실제 실행 수와 파일 hash로 조회·task 재개가 읽기 전용임을 확인한다. 공유 owner 변경으로 무효화된 근거와 필요한 재검증을 확인하되 기존 동일 인수를 횟수 채우기로 반복하지 않는다.
7. **패키지와 전달:** source/tests/필요한 fixture·schema/reference/generated/docs를 함께 검증하고 로컬 패키지의 소스 커밋·버전·파일 hash를 고정한다. 실제 패키지 CLI와 새 문맥 소비를 확인한다. native 설치본 발견·hook 전달·보호 호스트 수락은 별도 판정하고 불가능한 범위는 BLOCKED/미검증으로 둔다.

첫 파일럿의 범위는 대표 화면에서 기준을 코드로 만든 뒤 다음 관련 화면이 이를 재사용하는 데까지다. 일부 화면 성공을 전체 UI 완료·전체 지도 init 완료로 표시하지 않는다. 전체 최초 조사를 시작했다면 합의한 범위에서 미조사 항목이 남는 동안 PARTIAL을 유지하며, 그 사실만으로 독립적인 작은 작업을 막지 않는다.

### 검증과 개선 효과의 판정

업무 규칙·아키텍처 × FE·BE/API·Domain은 필요한 확인 질문의 지도다. 같은 흐름이 여러 주장을 입증할 수 있으며, 연두링크에 없는 서버 계층은 근거 있는 N/A로 처리한다. 저장이나 계층 경계에 영향이 있을 때만 실제 값·식별자·부작용·재조회를 추적한다. 의존 방향·상태 소유권·계약·실패/복구는 코드와 실제 호출자로 확인한다. 코드 PASS는 사업 가치·전환·수익 가설의 증명이 아니다.

UI 기능 검증은 시각적 적합성·실제 사용자 승인과 분리한다. 긴 네 언어 문구, 필요한 viewport·keyboard, 선택·미확인·오류 복구와 기존 상태 전이를 확인한다. 가격 미확인을 0원/확정으로 바꾸거나 직원 UI 잠금을 인증으로 설명하지 않는다. 기존 browser checks를 재사용하고 의도한 디자인 변경으로 달라진 기준만 합리적으로 갱신한다. 테스트 승인은 fixture임을 표시하고 실제 사용자가 보지 않은 시안을 승인 기록으로 남기지 않는다.

검사는 이유별로 유지·통합·제거한다. 중복은 남는 검사의 같은 결함 검출/정상 허용, 요구 폐기는 변경 권한·기준·소스·과거 실패 범위·유지 계약, 타입/제약 이전은 금지 경계·우회·정상 동작, flaky는 관측기 수리와 남은 검출 공백으로 판단한다. 폐기한 규칙을 검출하는 replacement test는 필요 없다. 현재 불필요함이 입증되지 않으면 유지한다.

평가 기록은 기존 `.work/` 증거에 작업별 **잘못된 완료·놓친 결함·사용자 개입·정상 요청의 불필요한 차단·재작업·중복 실행·소요 시간**을 남긴다. 제품 실행 횟수와 전체 도구 호출 수, 실제 실행 시간과 사용자/환경 대기를 구분한다. 제공된 힌트·오류·재시도를 숨기지 않고 주 Agent가 실제 diff·raw·호출 수를 확인한다. 표본이 작은 결과를 일반 신뢰도나 비용 절감으로 확대하지 않는다.

독립 실행이 불가능해도 공통 코드 수리와 실제 CLI/패키지 검증은 계속한다. 미완료 자연어 평가를 성공으로 채우지 않는다. 효과 없는 제약은 줄이고, 일반 지침의 이득이 반복해서 입증되지 않으면 유효한 검증·조회·재사용 도구를 중심으로 범위를 축소한다.

### 저장소·권한·최종 산출물

- `Skill_Management`: 최신 실제 상태에서 새 전용 branch/worktree로 구현한다. 기능 단위 로컬 커밋, 필요한 검토 문서의 로컬 main 반영, 검증된 구현의 로컬 main 병합, 이번에 만든 작업 공간 정리는 사용자가 승인했다. 병합 전 main 이동을 다시 확인한다.
- `yeondoo-link`: **실제 저장소의 별도 새 브랜치에서 개발**하는 것을 사용자가 승인했다. 필요하면 그 저장소에 속한 worktree로 격리하되, 별개 복제본 시험만으로 실제 브랜치 개발을 대체했다고 보고하지 않는다. 평가에 추가 격리가 필요하면 명시하고 기준을 맞춘다. 이 브랜치·커밋은 검토 가능하게 남기며 main 병합·브랜치 삭제·push는 승인 범위에 넣지 않는다.
- 기존 사용자 변경·기존 branch/worktree·연두라벨 원본·기존 설치본·인증·전역 설정을 보존한다. `.dev.vars`를 읽어 출력·복사·배포하지 않는다. Azure 재개·음성 대량 생성·외부 유료 호출·push/publish/deploy·CODEX_HOME/권한 설정 변경은 포함하지 않는다.
- 샌드박스 쓰기 권한과 사용자의 작업 승인은 별개다. 연두링크 경로 쓰기가 제한되면 허용된 승인 절차로 해당 작업만 요청하고, 거부·환경 제한을 명시한다. 전역 설정·권한을 바꿔 우회하지 않고 가능한 플러그인 작업을 계속한다.
- raw·캡처·명령·평가 기록은 `.work/`에, 장기적으로 필요한 제품/플러그인 결정·사용법·한계는 각 기존 문서와 소유 코드에 둔다. 새 중복 지도·영구 조사 DB를 만들지 않는다. worktree를 지우기 전에 그곳에만 있는 필요한 증거·패키지를 보존한다.

최종 보고는 **플러그인에서 고친 공백**, **연두링크에 남긴 평가용 변경**, **수정 전후와 새 문맥 재사용의 실제 결과**, **유지/통합/제거한 검증과 이유**, **미구현·미검증·BLOCKED**, **두 저장소의 branch/commit·패키지·증거·정리 상태**를 구분한다. 화면이 예뻐졌거나 문서가 늘었다는 사실만으로 플러그인 고도화 완료를 선언하지 않는다.

## 13. 지속 고도화 목표와 완료 판단

2026-10-12 사용자는 다음 세션의 실제 구현 요청과 함께 아래 관점이 충족될 때까지 지속적으로 플러그인을 개선하도록 요청했다. 이 절은 목표·판정 기준이며 추가 구현 완료 기록이 아니다. 승인된 범위는 [지속 고도화 프롬프트](plugin-continuous-improvement-next-session.md), 현재 구현은 [0.1.59 제품 소비 결과](agent-workflow-implementation-results.md#product-consumption-2026-10-14)가 소유한다. §12의 책임·평가·권한 경계와 §4–8의 계약을 유지하며 다음 잔여는 §10으로 한정한다.

| 목표 | 완료 판단에 필요한 현재 근거 | 미완료로 남길 경계 |
| --- | --- | --- |
| 많은 task 위임·검증 조회 | 자연어에서 정확한 task/Feature/기준/owner/검사 발견; 선택 묶음의 당시 결과·현재 reuse·NOT_RUN/STALE/UNKNOWN/BLOCKED·raw와 다음 행동; 공유 owner 변경·통합·중단/다른 Agent 인수; 예상 task 규모의 비용 관찰 | 제한된 CLI 묶음을 장기 무인 운영으로 확대하지 않음. 직접 호출과 native 자동 발견/context 전달을 분리 |
| 비즈니스 모델·업무 규칙/아키텍처 × FE·BE/API·Domain | 기존 6셀의 기대 주장·출처·적용 판단·근거 연결; 실제 영향 사용자 경로와 값/ID·저장/새 조회; 상태/effect/의존/실패 복구 관찰 | 없는 층은 이유 있는 N/A, 미결정은 열린 상태. 코드 PASS로 전환·수익·사업 가설을 인증하지 않음 |
| 자가 개선·불편/피드백·실질 가드레일 | 기대→재현→동작/데이터 흐름→원인 owner 수리→구조/validation/shared component/행동 검사 등 예방→원래 실패·가까운 정상·관련 우회→다음 소비 | 문장 추가·hash·모델 합의로 원인 수리나 실제 사용자 승인 대체 불가. 재발 방지는 확인한 원인/호출 경계로 한정 |
| UIUX 가이드의 생성·갱신 | 의도/상태/variant/반응형/접근성 guide와 실제 token/component 소유권; 관련 화면 관찰; 독립 새 문맥의 다음 소비 화면 재사용 | CONNECTED/테스트 PASS와 시각 적합성·사용자 승인을 분리. 미검토 후보는 draft |
| 실행 가능한 테스트/검증 가이드의 생성·갱신 | 기존 명령/adapter로 Launch→Doctor→Drive→Evidence→Cleanup; source/build·fixture/runtime·assertion/exit/raw·정리 후 보존; 새 작업자의 실제 소비 | 명령 문서·HTTP 200·성공 문자열만으로 실행/제품 정답 판정 불가. 도구 실패는 제품 결함과 분리 |
| 실효성 있는 검사·가드레일 유지/고도화/제거 | 검출 대상과 비용; 중복의 검출/정상 보존, 요구 폐기의 권한/유지 계약, 구조 이전의 거부/우회/정상, flaky 관찰 수리; 다음 작업의 유지 근거 | 오래됨·개수 감소·미검출 이력만으로 삭제하지 않음. 입증된 정리 후보가 없으면 유지하고 이유를 보고 |

기존 root 밖 Git 조상 오류·task 연결·hook 비용과 후속 이관·조회·bundle 비용 수리는 완료 범위다. native host 전달은 여전히 미입증이다. 로컬 main 통합·이전 작업 브랜치 정리도 완료됐으므로 더 이상 blocker로 쓰지 않는다. 다음 구현/인수는 §10에서 선택한다. 원래 consultation task의 13개 PASS/17개 공백과 CatalogImport 후보의 18개 PASS/23개 검토 공백은 서로 다른 분모이며 합산하거나 최신 결과 하나로 덮지 않는다.

한 회차의 수리·인수가 전체 목표 완료는 아니다. 이어서 실제 사용자 업무와 현재 근거에서 다음 공백을 선정해 **재현/기준 고정 → 최소 owner 수리 → 영향 검증/실제 흐름 → 독립 관련 업무 소비 → 효과 판정 → 완결 커밋/통합**을 반복한다. 완료된 D1–D3/G1–G6/R0–R4/A–C를 재구현하지 않는다. 알려진 결함이 해결됐으면 영향 인수로 확인하고 다음 실제 공백으로 이동한다. 모든 목표마다 검사를 새로 추가하는 것이 아니며 기존 근거·구현을 재사용한다.

전체 목표 충족은 표의 각 관점에 현재 통합 source·실제 경로·실패/정상/후속 소비 근거와 지원 규모/조건이 있을 때 판단한다. 필요한 근거·권한이 없으면 PARTIAL/BLOCKED와 재개 조건을 남긴다. 목표와 관련해 남은 중요한 경계를 임의로 지원 범위 밖으로 돌려 완료하지 않는다. 회차별 구현 완료와 전체 목표 충족을 구분하고, 세션이 나뉘면 기존 설계/실행 결과·다음 미완료 항목으로 이어간다.

효과는 거짓 완료·결함 누락·정상 요청 차단·사용자 개입·재작업·중복 실행·비용의 실제 관찰로 판정한다. 측정/전제 차이를 밝히고 효과 없는 제약은 축소한다. 같은 실패의 무한 재시도·자동 규칙 축적·고정 검사/Agent 수는 만들지 않는다. [PStack 고정 분석](pstack-analysis.md)의 실행 경로·측정 기준 분리·전달 시 근거 유효성은 참고하되 최신 구현/우월성이나 일괄 채택의 근거로 사용하지 않는다.

지속 고도화는 다음 실행의 승인된 로컬 구현·인수 범위다. 정기 자동화, 기존 설치본/전역 설정 변경, provider/외부 비용, push/publish/deploy, 제품 main 통합을 추가 승인한 것으로 해석하지 않는다. 사용자 검토·사업 성과·호스트 접근 등의 외부 근거가 필요한 범위는 구현 가능한 독립 부분과 구분한다.
