# Agent 위임 설계 기준

이 문서가 현재 설계의 단일 기준이다. 0.1.87까지의 기준·근거는 [이전 판](archive/agent-coding-system-direction-through-0.1.87.md)과
[아카이브](archive/index.md)에, 버전별 실행 기록은 [docs/index.md](../index.md)에 있다.

## 목적과 판정 기준

사용자가 FE·BE·업무 로직에 걸친 작업을 범위 안에서 더 많이 위임하고, 무엇이 어떻게 검증됐는지
분명히 확인하게 한다. 플러그인은 **켰을 때 결과가 측정 가능하게 좋아져야** 존재 이유가 있다.

판정은 `evals/delegation-v1/`의 고정 held-out 과제에서 플러그인 OFF와 비교한다
([testing](../testing.md#delegation-effect-evaluation)).

| 지표 | 의미 |
| --- | --- |
| 검증된 성공 | 숨긴 수락 테스트와 기존 회귀 검사가 모두 통과 |
| 거짓 완료 | 완료를 주장했지만 숨긴 테스트나 회귀가 실패 (중단·timeout 제외) |
| probe 검출률 | Agent가 남긴 테스트가 인공 결함을 잡는 비율 |
| 비용 | 토큰, 비용, 시간. 검증된 성공 1건당 토큰으로 비교 |

같은 조건 비교 없이 일반 개선을 주장하지 않는다. 0.1.61·0.1.62·0.1.78의 OFF/ON 비교는 해결률이
같고 토큰·시간만 늘었다([Luna](luna-benchmark-execution.md), [0.1.78](luna-0.1.78-benchmark-results.md)).
v1(0.1.88)과 v2(0.1.89)도 같았다([기록](lean-delegation-0.1.88.md)).

OFF가 85% 이상인 세트에서는 +15%p 성공 기준을 수학적으로 넘을 수 없다(v2 OFF 22/24). 다음 플러그인 전체
OFF/ON 비교 전에 기준을 새로 정한다. 결과를 본 뒤 기준을 낮추지 않는다. 새 장치는 전체 비교 전에
[장치 단위 반증](#장치-단위-반증)을 먼저 통과해야 한다.

## 설계 원칙

1. **결과를 바꾸는 장치만 기본 경로에 둔다.** 모델이 이미 하는 일(읽기·수정·테스트)은 다시 지시하지
   않고, 기록에서 반복해 빠뜨린 행동만 다룬다.
2. **자산은 제품 저장소에 실행 가능한 형태로 남긴다.** 테스트, lint·아키텍처 규칙, Feature Map,
   UI token, probe 등록부는 다음 세션·다른 Agent·플러그인 OFF에서도 작동한다. `.work` 상태는 보조다.
3. **매 턴 주입은 0에 가깝게.** 상세는 필요할 때 읽는다.
4. **측정하고 남긴다.** 평가 기준을 넘지 못한 장치는 사용 여부를 확인한 뒤 제거한다.
5. **차이는 모델이 혼자 얻지 못하는 것에서만 난다.** 계산된 사실(호출·쓰기 경로), 구현과 분리된 독립 판정,
   세션을 넘는 실행 자산이 그것이다. 좋은 작업 방식을 글로 설득하는 지침은 기본 모델이 이미 따르므로
   OFF와 차이를 만들지 못했다(v2: Skill 로드 20/24, 결과 동일). 독립 판정도 사람이 판정할 지적을 늘리면 기본
   경로에 둘 수 없다(독립 경로 검증 반증).

## 구조

### 상시 (최소)

- 자동 호출 Skill은 `agent-workflow`, `diagnose`, `recall`, `setup-project-verification`,
  `fixing-accessibility` 다섯 개다. 나머지 17개는 명시 호출 전용(Claude `disable-model-invocation`,
  Codex `allow_implicit_invocation: false`)이고, `agent-workflow`가 필요할 때 형제 Skill의 `SKILL.md`를
  읽어 쓴다([inventory](../architecture/skill-inventory.md)).
- 프롬프트 hook은 선택된 task가 없으면 Git도 runtime도 실행하지 않는다. 요청 유형이 맞을 때만 한 줄
  route를 남긴다. 따옴표 문구 편집과 고치라는 요청이 없는 질문에는 route를 주지 않는다.
- Stop guard는 마지막 편집 뒤 실행이 없거나, 코드 5줄 이상을 바꾸고 독립 검증자를 띄우지 않았거나, 검증자가 지적한
  뒤 probe 등록부를 갱신하지 않았을 때 한 번 막는다.
  막을 때만 컨텍스트를 쓴다(Claude Code만. Codex는 plugin Stop hook이 없다).

### 위임 작업의 핵심 장치 (`agent-workflow`, `diagnose`, 플레이북)

| 장치 | 막는 실패 (기록) |
| --- | --- |
| L1 수락 기준 먼저: 요구사항에서 기대값을 정하고, 현재 코드에서 의도한 이유로 실패하는지 확인 | 자기 테스트 통과·공식 실패 (0.1.78 Carbon 6/6) |
| L2 `probe_check.py prove`: 새 테스트는 소스 변경 없이 실패해야 함. 규칙은 probe로 등록 | 테스트 PASS인데 결함 통과 (Labeler 4/11, yeondoo 3/8) |
| L3 영향받는 기존 검사를 최종 편집 뒤 실행 | 기존 `PublicAPI-test.js` 미실행 |
| L4 같은 규칙을 쓰는 모든 경로 확인, 반박된 가설의 변경 되돌리기 | settle-order 우회 누락 (0.1.85) |
| L5 독립 검증: 구현 맥락 없는 새 하위 Agent가 요청 원문과 diff만 받아 실패 테스트를 쓰고, 구현자가 요청 위반만 고친다. 고친 지적은 probe로, 답을 받은 사용자 결정은 `.harness/decisions.md`로 남긴다 ([reference](../../authoring/references/independent-check.md)) | 구현자와 그 검사가 같은 경로 목록을 공유해 생긴 소리 없는 거짓 완료 (v2 5/5) |
| L6 결과 카드: 요청→동작, 영향 Feature/계층, 최종 편집 뒤 검사, 증명, 독립 검증, 미확인, 사용자 결정 | 무엇을 검증했는지 알 수 없음 |

pstack(MIT, Lauren Tan, 0.15.25 `101b274`)의 test-behavior·tdd·fix-root-causes·attack-the-premise·
blast-radius·build-the-lever·orchestrate 원칙을 위 장치와 swarm 지시서에 반영했다
([비교 기록](pstack-practical-comparison.md)).

### 제품 저장소 자산

`.harness/probes.json`의 probe 하나는 규칙 하나의 인공 결함(파일·find·replace·검사 명령, Feature, 관점
business/architecture/ui, 계층)이다. `probe_check.py probes`는 격리 worktree에서 각 probe를 적용해
Feature × 관점 × 계층의 killed/total을 보여 준다. 이 한 등록부가 다음을 잇는다.

- 검증 가시성: PASS 개수 대신 결함 검출 수
- 피드백·가드레일: 불만의 원래 결함과 우회 경로를 probe로 등록해 재발을 잡는다
- UI 기준: token 하드코딩·간격 변형을 lint·시각 검사가 잡아야 한다
- 검사 정리: 고유하게 잡는 probe가 없는 검사는 통합·제거 후보, 아무도 못 잡은 probe는 공백

probe의 `origin` 첫 단어(`independent-check`, `feedback` 등)별 killed/total이 보고서의 *Origins* 줄이다.
독립 검증이나 피드백에서 자란 가드레일 수가 여기 보인다.

`.harness/decisions.md`는 답을 받은 사용자 결정을 한 줄씩 담는다(날짜, 영역, 질문 → 답, 출처). 구현자는 1단계에서,
독립 검증자는 판정 전에 읽는다. 정해진 해석은 다시 묻지 않고, 엄격한 해석을 채택한 답은 새 요청으로 구현해
검증자 테스트와 probe를 남긴다.

Feature Map(규칙 → 검사 → 계층 책임자)과 UI 가이드·token은 프로젝트가 소유한다. 결과는 `audit --report`
와 probe 행렬로 본다.

## 책임과 권한 경계

| 소유자 | 책임 |
| --- | --- |
| Agent | 요청·영향·원인·시각 결과의 의미 판단, 검사 선택과 근거 읽기 |
| 공통 runtime | 기존 task·조회·capture·현재성, probe 실행. 제출한 상태는 행동 증거가 아니다 |
| 프로젝트 | 업무 규칙, Feature Map, UI token/component, 실행 가이드, runner·assertion, probe 등록부 |
| 지원 host | 플러그인 식별·Skill 발견·hook 전달. 설치·신뢰는 host 권한 경계 |

설치본 갱신, 전역 설정, 보호 branch 통합, push/publish, 유료 실행은 이 문서로 승인되지 않는다.
fixture·package·실제 제품·native host·사업 성과는 서로 다른 증거다.

## 장치 단위 반증

### 진단

v2의 실패는 모두(OFF 2, ON 3) 기존 회귀가 통과하고 숨긴 수락 검사가 실패한 **소리 없는 거짓 완료**였고,
스스로 미완료를 밝힌 실행은 없었다. `rule-all-paths`는 네 실행 모두 복제 경로(`duplicateProduct` →
`insertProduct`, 입력 schema 미통과)를 놓쳤고, 그중 두 실행은 그 함수를 읽고도 놓쳤다. 구현자와 그 검사가
"고려할 경로 목록"을 공유하므로, 경로를 빠짐없이 보라는 지침과 RED/GREEN 증명은 선택한 경로의 정확성만
높인다. probe·prove는 약한 테스트를 겨냥하지만 실제 실패는 고려하지 않은 경로였다.

### 독립 경로 검증: 사용자 결정으로 채택 (0.1.91)

오프라인 반증은 사전 기준에 미달했다([결과](independent-path-check-offline.md)). 검증자는 부분
구현을 모두 잡았다(Claude 10/10, Codex 6/6). 그러나 참조 구현 12개 중 5개(Codex 6개 중 4개)도 미완료로 판정해
오탐 기준(1건 이하)을 넘었다. 경로 후보 계산은 조정에 쓴 과제에서만 적중했다. 오탐을 다시 실행하니 9건 모두
재현됐고, 일부는 숨긴 검사가 덮지 못한 실제 결함이었다. 나머지는 범위 해석 차이였다. 사람이 판정해야 하는
지적이 완료 작업의 약 40%에 붙는다.

사용자는 독립 검증이 대부분의 경우 낫다고 판단해, 추가 측정 없이 플러그인에 넣기로 정했다(2026-10-27).
준비한 짝지은 비교([review loop](../../evals/review-loop/README.md))는 실행하지 않았다. 따라서 OFF 대비 이득은
측정되지 않았다. 반증에서 드러난 약점은 설계로 다룬다. 지적은 판정이 아니라 입력이고, 구현자가 검증자 테스트를
직접 돌려 요청 위반만 고친다. 더 엄격한 해석은 결과 카드의 사용자 결정으로 올린다. 경로 후보 계산(B)은 넣지 않았다.

반증 전 설계는 아래와 같았다. 범위 규칙("모든 저장", "~하지 않게")을 말하는 위임에만 적용한다.

- **경로 후보 계산(모델 없음):** 변경과 연결되지 않은 같은 필드의 쓰기 경로를 근거와 함께 후보로 낸다.
  해석하지 못한 경로는 UNKNOWN이다. 의미 판단은 Agent 책임이므로 완료 차단에 쓰지 않는다.
- **독립 검증자:** 구현 맥락 없이 요청·diff·후보만 받아 진입점 기준 수락 테스트를 작성·실행한다. 남긴 테스트는
  제품 저장소 자산이 된다(원칙 2). 다른 모델 계열은 선택 사항이고, 같은 모델의 새 맥락과 효과를 구분한다.
- **결과:** 막지 못한 경로는 결과 카드에 미검증으로 드러낸다. 성공률이 같아도 소리 없는 실패를 드러난 실패로 바꾼다.

플러그인에 넣기 전에 [오프라인 반증](../../evals/path-check-offline/README.md)을 먼저 한다. v2의 참조 구현과
"회귀 통과·숨긴 검사 실패" 부분 구현에 검증자만 실행하고, 미리 커밋한 기준(부분 구현 검출 75% 이상, 참조
구현 오탐 1건 이하)으로 판정한다. 미달하면 장치를 만들지 않고 플러그인 축소를 검토한다.

검토 후 채택하지 않은 방향: 다중 작업 병렬 모드(병렬 실행은 host와 `swarm`이 이미 제공하고, 작업당 소리 없는
실패율을 낮추지 않은 채 처리량만 늘린다), 지침 보강 후 재평가(원칙 5), 결함→검사 자산 루프 단독(현재 설계와
같고 v2에서 차이가 없었으며, 만든 자산은 OFF에서도 작동한다). Codex 독립 검토와 대조한 판단이다.

## 현재 상태

0.1.88과 0.1.89의 구현·측정 결과는 [기록](lean-delegation-0.1.88.md)이 소유한다. 두 OFF/ON 평가 모두 채택 기준에
미달했다. v1은 성공 79% 대 75%, 비용 +23%였다. v2(조건당 24회)는 OFF 22/24, 0.1.89 21/24, 거짓 완료 2 대 3,
성공당 토큰 +21.67%였다. 기준을 넘기 전에는 플러그인이 위임 결과를 개선한다고 보고하지 않는다.

0.1.91은 독립 검증(L5)을 위임 기본 경로에 넣었다. `agent-workflow`·`diagnose`의 단계와 Claude Code Stop guard가 그것이다.
오프라인 반증이 기준에 미달했지만 사용자 결정으로 채택했고, OFF 대비 이득은 측정되지 않았다.
0.1.92는 독립 검증 결과를 프로젝트에 남긴다. 고친 지적은 `origin: independent-check` probe가 되어 다음 변경에서
기존 검사가 먼저 잡고(Stop guard가 한 번 요구), 답한 사용자 결정은 `.harness/decisions.md`에 남아 같은 질문을 막는다.
만든 자산은 OFF에서도 작동하므로 ON/OFF 이득 주장이 아니라 자가개선·가드레일(목적 3, 6)을 위한 사용자 결정이다.
0.1.93은 위임마다 읽는 `agent-workflow`·`diagnose` 본문을 13.9KB에서 12.7KB로(약 9%) 줄였다. 독립 검증자가 이전 본문과 두 번 대조해
빠지거나 약해진 지시 6개와 범위가 바뀐 조건을 찾았고 모두 되돌렸다. 중복과 근거 설명만 덜어냈고, 환경 실패 절차는 이미 같은 내용을 가진 `repair-and-reuse` 행으로 연결했다.
명시 호출 Skill 표는 한 문단 목록이 됐다. 프롬프트 route는 일치할 때 한 줄만 넣으므로 그대로 둔다.
0.1.93 실제 host 실행 1건(음수 가격 금지, $0.25)에서 Agent는 route를 받고도 Skill을 부르지 않았다. 셸 heredoc과
Python 스크립트로만 61줄을 고쳤는데 Stop guard가 막지 않아 독립 검증이 빠졌다. 0.1.94는 편집 방식과 무관하게
Git으로 변경 줄 수를 잰다. 이번 턴의 파일은 턴 시작 이후 수정 시각으로 가르고, 막을 때 설치된 템플릿 경로를
