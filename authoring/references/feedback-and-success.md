# Feedback and successful procedure reuse

Use this small entrypoint for a correction, a useful successful judgment or a request
to repeat a satisfactory turn/artifact. Ordinary work needs no reflection record,
new task or contract. Use the existing task/report if a record helps; preserve open
connected feedback obligations. This is not automatic personal memory collection.

## Choose the signal and owner

| Signal | Action |
| --- | --- |
| "That is the wrong direction" / failure | State expected versus observed behavior and conditions. Use `diagnose` and [repair and reuse](repair-and-reuse.md); distinguish requirement violation/change, exception, oracle/tool error, environment limit and unknown cause. A clear first correction is actionable. |
| "That judgment worked well" | Identify the decision, evidence, conditions and what a future decision should change. Retain only a durable, actionable lesson at its owner. Praise without such content needs no persistent edit; do not invent causality from coincidence. |
| "Do it this way next time" / "extract this procedure" | One explicit reuse request is sufficient to extract a bounded procedure from the selected turn/artifact. It is not evidence of a general personal preference. |
| "Only this time" | Keep the exception scoped to the current task. Do not promote it into a lasting rule. |

Inspect the current owner and its callers/consumers before adding guidance. Product
defects belong in code and checks; project rules in project guidance; common work
judgment in the existing Skill. If the rule already exists, repair its description,
discovery link or conflicting route rather than repeating it. If it was found but
not followed, identify the conflict or missing enforcement, not just another reminder.
Record a lesson as condition → decision → supporting observation → limits/reconsideration
only when that changes future work. Merge with the existing rule; reject duplicates.

## Extract and use a procedure

1. Read the selected successful result and available execution evidence. Separate
   observed steps from inferred ones. An artifact alone may establish output shape
   but not how it was made: request only the missing input or decision needed for
   reproduction, or label the draft unverified. Never invent a proven recipe.
2. Search existing Skills, project guides and templates by the intended task and
   trigger. Prefer a focused update or discovery repair. Use the host's existing
   `skill-creator` or `write-a-skill` only for a genuinely independent repeatable
   procedure with no suitable owner. Read that available tool's instructions; do
   not install it or create a competing authoring framework. If unavailable, a
   project-owned guide/template can still be written and exercised within scope.
3. Fill the [procedure template](../templates/reusable-procedure.md) only as needed.
   Parameterize names, paths and sample values; retain consequential decisions,
   input contracts, existing tools, output shape, acceptance and failure behavior.
   Keep a minimal nonsecret example when useful. Do not copy whole conversations,
   credentials, irrelevant trial history or incidental machine-specific settings.
4. Connect the result at the existing discovery point and update source/generated
   resources according to repository policy. Existing edit authorization applies;
   installation, global settings, publication and external spending remain separate.
5. Before consumption, define expected outcomes and failure criteria. Exercise a
   fresh context with a short request and essential inputs, without the old chat,
   answer patch or coaching. Keep earlier consumer reports and evaluator answers
   outside the consumer's discovery scope; a fresh conversation alone does not
   isolate a shared workspace. Prefer a clean task/material copy, and explicitly
   bound task evidence when prior outputs remain accessible. Preserve accidental
   exposure as a contaminated attempt, not an unaided success; use another fresh
   context for an uncontaminated retry. Skill/guide pointers make this assisted consumption;
   test unaided discovery separately if making that claim. Inspect actual artifacts,
   executions and relevant failure/normal observations, not the consumer's PASS label.
6. If consumption fails, preserve the attempt, repair the responsible procedure or
   discovery gap and retry in another fresh context when feasible. Record failures,
   retries, non-execution, missing context and extra human intervention. Creation
   alone is not successful reuse. Report the bounded outcome and remaining unknowns.

For correction, use the existing prevention evidence: original failure and alternate
bypass blocked, nearby normal case still allowed, then a related follow-up consumes
the owner change. For success reuse, compare the new artifact/behavior with the
predeclared result criteria. Include one-off exceptions, bare praise and existing-rule
discovery in the review so a successful example does not become a universal rule.
Keep fixture/package evidence, assisted consumption, unaided discovery and native-host
results separate. Do not claim general effectiveness or cost reduction from one case.
